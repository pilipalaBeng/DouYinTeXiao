# 测一测创作规划

> 文档性质：按需 Reference（非 Skill，不参与默认 Skill 发现或向 RootAgent 默认暴露）
> 读取时机：Draft 确认后，结果揭晓本身是核心体验且符合测一测适用条件时读取
> 职责边界：只补充测一测的结果设计与 Brief，不直接生成场景、素材或脚本

## 适用判断
当结果揭晓本身是核心体验时使用，例如性格测试、特征测试、社交测试、有限随机抽取，或根据局内选择与表现生成专属结论。
普通知识答题、仅以分数结算的游戏、普通随机生成玩法不自动视为测一测。若测一测同时使用声音等特殊输入，以本 Reference 负责结果设计，其他专项 Reference 负责输入设计。

## 测一测类型专用区域定义
测试内容区：x:40~680, y:148~921 = 蓝色主内容区
内容流起点：top=148
人脸优先可视区：x:201~516, y:266~704
左侧可用区：x:40~201, y:266~704
右侧可用区：x:516~680, y:266~704
下方可用区：x:40~680, y:704~921
绿色交互区：x:40~680, y:921~1095

## 创作决策

### 1. 选择一种主模式
- **选择测试**：通过少量互斥选择累计标签或倾向。
- **表现测试**：通过局内行为、完成度或偏好映射结果。
- **有限随机测试**：从预先枚举的有效结果池中揭晓一个结果。
- **社交测试**：围绕关系、身份或互动倾向生成有讨论空间的结论。

一次短体验只设一种主模式。辅助交互必须服务于同一结果计算，不并列多个测试系统。

### 2. 建立有限结果池

- 每个最终结果定义稳定的 `result_id`、结果标题、一句核心结论、简短解释、独立视觉意象和揭晓反馈。
- 用户明确给出结果体系、类型数量，或可由规则唯一推导完整结果枚举时，结果池必须保持相同粒度；不得擅自合并为家族、阵营、等级或通用角色。
- 每个最终 `result_id` 必须映射独立的结果视觉资产 key；只有用户明确要求多个结果共用同一视觉主体时才允许复用。UI Brief 定义视觉资产与静态布局，gamelogic Brief 定义 `result_id` 到对象的映射、状态与显隐；主 Brief 只记录结果体系和揭晓体验。
- 结果差异同时体现在语义、情绪和视觉上，不只替换标题、分数或运行时文字。
- 每条有效输入路径都必须映射到有效结果。输入不足、超时或选择不完整的兜底只在用户或 Brief 明确规定该条件时定义；不得自行新增超时或自动选择。
- 结果是可枚举内容，不使用“随机生成答案”“根据情况给结果”等开放描述。

### 3. 设计输入映射

- 选择测试使用清晰的标签累计、权重或结果映射；同分时给出唯一仲裁规则。
- 表现测试使用可观测行为或数值区间，不根据未采集的信息推断。
- 有限随机测试明确随机范围和等权或加权规则。
- 社交测试让问题与结果之间存在可理解的关联，避免先定结果再随意拼接题目。

### 4. 设定图代表状态判定

- **单次测试**：仅包含一次选择、抽取或输入，完成后立即产生结果时，默认选择「结果揭示状态」，完整展示结果主体与必要解释。
- **多轮测试**：包含多个题目、轮次或连续输入收集时，禁止选择结果揭示状态，必须选择「首屏状态」或「游戏中状态」：
  - 首屏已经完整展示题目、选项和主要交互结构时，选择「首屏状态」。
  - 首屏只有标题、开始提示或无法体现实际测试结构时，选择「游戏中状态」，展示具有代表性的题目与选项。
- 多轮测试的代表状态优先展示最长必要题目、最多选项和完整交互结构，用于确定题目容器与选项卡的实际尺寸。题号不是默认元素；确有轮次辨识价值时并入题目气泡或题目容器。正确数、累计分数和结果映射进度默认只在后台维护。

### 5. 设计揭晓体验

状态流程优先使用 `准备 → 输入收集 → 结果计算 → 结果揭晓`；有限随机测试可简化为 `准备 → 触发抽取 → 悬念反馈 → 结果揭晓`。只有设计实际需要时才增加结果停留阶段。
揭晓必须包含结果标题、解释、对应视觉意象和一次明确反馈。结果文案使用运行时 Text，PNG 只承载非文本视觉；不增加重试、下一轮或分享按钮。

### 6. 测试布局准入与模板

- 测一测交互先根据当前阶段确定必要信息，再决定是否创建按钮或结果面板，不得先套用「顶部HUD + 中部玩法 + 底部按钮」结构。
- 测一测输入阶段禁止 `hud_bar`、顶部底板和标题栏。蓝色主内容区最多存在一个从 `top=148` 起排且 `textContainerId=none` 的独立大标题 Text；游戏标题与测试标题视为同一职责，只保留一个，不得同时生成题号、进度、阶段提示或第二标题。
- 题号、轮次、正确数、进度、权重和倒计时默认只在后台维护，不创建可见 Text。只有玩家必须根据题号或轮次改变当前操作时才允许显示；确需显示时必须绑定当前题目、上下文或主操作容器，写入该容器的 `textSafeRect`，不得作为顶部独立 Text。
- 测一测输入阶段使用蓝色主内容区 `x:40~680, y:148~921` 作为统一测试内容区，不在 `y=270` 重新起排。
- 存在标题时只放置一个无底板大标题，完整外接矩形 `top=148`；必要题目或上下文容器按精确文字高度和 `16px` 净间距紧接标题向下排列。不得在顶部放置题号、进度、操作提示或其它独立 Text。
- 人脸优先可视区为 `x:201~516, y:266~704`。输入阶段的实体 UI 容器、可读 Text、卡片和非脸控玩法对象优先避让该区域；内容容量或交互关系要求连续布局时允许局部进入，但不得大面积持续遮挡人脸主体或同时遮挡主要五官。短选项优先放在两侧区域，手指拖拽对象、卡牌或其它横向主体优先放在下方可用区。
- 必要操作提示优先省略；只有操作无法通过玩法对象理解时才允许创建无底板提示 Text。提示必须位于测试内容区内，优先放在两侧或下方可用区，并默认隐藏或短暂显示。
- **按钮准入（唯一判断标准）**：只有玩法明确要求提交确认时才创建确认按钮；点击选项即可推进时不创建确认按钮。选项卡属于核心玩法区，不因具有点击功能就强制放入绿色常驻按钮区。
- 无底部常驻交互时不创建绿色区域按钮；固定合同允许时，蓝色核心复合单元可延伸至空置绿色区域，其余区域保持 AR 透传。
- **结果页面准入**：结果揭示阶段默认不生成独立结算面板、不生成HUD、不生成重试/下一题/分享/确认按钮。结果图像、结果标题、关键词和简短解释组成一个结果复合单元，整体位于蓝色核心区或固定合同允许的蓝绿联合安全空间。只有结果内容确实需要实体承载面时才创建结果容器；结果主体与短文字能够独立清晰显示时，不强制生成传统结算面板。
- **结果候选互斥**：结果池用于计算与候选定义，不用于同屏展示。结果揭示阶段只显示当前命中的一个结果及其对应视觉身份；其他结果、颜色、图像和标题保持隐藏。
- 用户要求不同结果使用不同色块时，将颜色分别绑定到对应结果变体。不得把全部结果色块同时排列成等级列表、阶梯、空白横条、图例或伪按钮。
- 最终正确数、分数或过程统计默认只参与结果计算；只有它能帮助玩家理解当前结果时才作为一行辅助文字显示，不得生成独立统计栏。
- **测试类人脸软避让**：测一测输入阶段优先保留 `x:200~520, y:270~680` 的连续人脸画面，不建立绝对禁止相交的矩形。实体题目框、对话框、选项卡、待操作卡片和独立提示文字优先放在人脸上方、两侧或下方；局部进入允许存在，但不得大面积持续遮挡人脸主体或同时遮挡主要五官。
- 顶部大标题和必要题目或上下文从 `top=148` 起紧凑排列，短选项优先分布在人脸两侧，手指拖拽对象、卡牌或其它横向玩法主体优先放在 `y:704~921`；不得为避让人脸任意放大纵向间距。
- 脸控玩法使用的空心扫描框、关键点或轻量反馈可以进入人脸优先可视区；不得使用实体底板、可读文字或大面积不透明素材持续覆盖该区域。
- 内容无法合理布局时，依次缩短非必要文案、按实际行数缩小容器、隐藏操作提示或改为阶段性显示；仍无法布局时返回容量冲突。
- 结果揭示阶段不执行人脸软避让，继续按结果复合单元规则正常布局。

#### 6.1 布局模板与结构案例
以下案例只用于理解布局关系，不得照搬题材、文案、数量或结果内容。实际布局必须结合输入方式规划并在 `Scene Layout Plan` 中写入最终尺寸与数值坐标。
- 手指点击、拖拽、滑动等手部交互对象优先放在画面下方，避免频繁抬手和遮挡主要内容。
- 脸部动作、表情、视线或头部姿态控制的目标优先放在蓝色核心区靠上位置，便于玩家同时观察人脸反馈和玩法目标。
- 结果揭示阶段不执行人脸软避让。
- 宿主录制按钮负责启动，不创建“开始”或“继续”按钮。

1. **题目选择布局**
适用于通过较长文字、图片、对话或情境内容收集答案。
布局规则：
- 顶部只保留一个无底板大标题作为内容流起点，完整外接矩形从 `top=148` 开始；题号或问题引导不得作为第二个顶部独立 Text，确需显示时绑定当前题目容器。
- 题目正文、对话上下文、参考图片和长文本选项属于后续核心内容，按阅读顺序从上一内容单元 `bottom+16px` 继续向下排列，可以连续跨越顶部信息子区边界 `y=270`，但不得进入绿色按钮区。
- 长文本选项使用内容卡片，不使用短按钮样式。
- 手指点击的内容卡片继续按顶部内容流顺序排列，不单独放到主内容区中部或下部。
- 使用转头、表情、视线等脸控方式选择时，候选内容可以分布在人脸两侧；顶部标题、题目和上下文仍保持紧凑内容流，不得通过增大纵向间距避让人脸。
- 单选且点击即提交时直接进入下一题；全部题目完成后直接进入结果页，不创建额外确认按钮。多选、排序或玩法明确要求主动提交时，允许一个必要的确认或提交按钮。
禁止生成顶部HUD、正确数栏、独立题号栏、结果等级按钮或非必要确认按钮。

布局案例：
- 主内容区顶部：仅放置一个从 `top=148` 起排的无底板测试大标题，不独立显示题号、进度或提示。
- 主内容区顶部：当前问题。
- 主内容区中上部或人脸两侧：2～4个长文本、图片或情境选项卡。
- 中间保留连续的人脸展示空间。
- 绿色区域保持AR透传，不放置选项按钮、确认按钮或提交按钮。

2. **操作测试布局**
适用于通过转头、表情、视线、拖拽、排序、匹配或反应操作生成结果的测试。

布局规则：
- 顶部只保留一个无底板任务名称或测试大标题，完整外接矩形从 `top=148` 开始；简短操作说明默认省略，确需显示时作为蓝色主内容区阶段性提示，不得与标题并列在顶部。
- 必要上下文、当前待操作对象和必要反馈按操作顺序从上一内容单元 `bottom+16px` 继续向下排列，可以连续跨越顶部信息子区边界 `y=270`；不得在主内容区内重新起排。
- 同一运行时内容在同一阶段只能由一个主要对象承载；可拖拽对象已经显示待评价内容时，不得再创建静态气泡、卡片或 Text 重复显示。
- 脸控目标可以位于人脸两侧；手指拖拽的分类区、目标槽和投放区横向排列在绿色常驻交互区，不参与主内容区内容流。
- 拖入目标即使属于核心玩法对象，也必须保留在绿色区域。
- 多个拖入目标先组成完整横向组，目标区视觉、文字、描边、阴影和点击判定范围均不得越出绿色区域。
- 每个拖入目标及整组的完整外接高度不得超过绿色区域内部建议高度 `158px`。
- 松手进入目标区后直接吸附、判定并推进，不创建确认或提交按钮。

布局案例：
- 顶部内容流起点：无底板测试标题，完整外接矩形 `top=148`。
- 主内容区顶部只放置一个无底板测试大标题；必要问题、对话上文或参考内容使用按文字高度计算的紧凑容器并紧接其后。
- `x:201~516, y:266~704` 优先保持连续人脸画面；对话框、待拖拽卡片和独立提示文字优先放在顶部、两侧或下方。
- 当前待拖拽卡片放在下方可用区 `x:40~680, y:704~921`，并位于绿色目标组上方，保证从卡片到目标槽的拖拽路径清晰。
- 可拖拽卡片与带语义标签的目标槽同时可见时交互已经自解释，不生成“拖到下方槽位”等操作提示。
- 绿色区域：两个或多个短标签拖入目标横向排列，完整位于 `x:48~672, y:929~1087`，高度不得超过 `158px`。

3. **单次选择或抽取布局**
适用于点击一个短文本类别后直接进行随机抽取、翻牌或结果生成。

布局规则：
- 顶部只保留一个无底板大标题，完整外接矩形从 `top=148` 开始；简短提示不得作为第二个顶部 Text，确需显示时放入蓝色主内容区并阶段性显示。
- 卡牌、轮盘、抽取器、扫描对象或其它主要视觉主体从上一内容单元 `bottom+16px` 开始，可以连续跨越顶部信息子区边界 `y=270`，不单独居中到主内容区。
- 多个短文本类别作为可点击选择按钮，组成横向按钮组放置在绿色区域，不参与上方内容流。
- 点击任一类别按钮后直接触发对应抽取或进入结果流程，不增加确认按钮。
- 主体本身可直接触发且不存在类别选择时，不生成额外按钮。
- 绿色区域按钮的视觉、文字、描边、阴影和点击热区必须完整落区，整体高度不得超过游戏 UI Reference 规定的高度上限。

布局案例：
- 顶部内容流起点：仅保留一个无底板抽取大标题，完整外接矩形 `top=148`；必要提示 Text 在蓝色主内容区阶段性显示。
- 主要卡牌、轮盘或抽取主体从标题或提示 `bottom+16px` 开始，不单独下移到主内容区中央。
- 绿色区域：2～4 个并列短文本类别按钮，不参与上方内容流。
- 点击类别按钮后直接抽取并进入结果揭示，不出现确认、开始或继续按钮。

4. **结果揭示布局**
适用于测试完成后的最终结果展示。

布局规则：
- 隐藏输入阶段的题目、选项和操作对象，只展示当前命中的一个结果。
- 结果揭晓需要以角色、人物形象、人格化形象、身份形象、职业形象或具象结果意象表达时，必须为当前命中结果规划独立的结果角色或结果插画视觉资产 key，并按实际用途使用现有素材类型；在 UI Brief、gamelogic Brief 和 Runtime Visibility Plan 中建立对应对象 ID、结果映射与显隐合同，不得只用结果面板、徽章和文字替代该结果主体。
- 结果角色或插画、结果名称、关键词和简短解释组成一个结果复合单元；存在结果面板时，角色或插画完整位于面板内容安全区内，结果文字位于角色区下方；没有面板时，整个内容组完整位于结果阶段的规划区域。
- 内容能够独立清晰显示时不创建结果面板；确需共同承载时只创建一个结果面板。
- 创建结果面板后，顶部徽章、耳朵、角花和贴边装饰属于边界装饰层，可以有限突出面板；结果角色、结果名称、关键词和解释文字属于面板内部内容组。强制层级为 `结果面板 < 后景特效 < 结果角色或插画 < 前景特效 < 结果文字 < 边界装饰`，边界装饰不得遮挡角色或文字。
- 存在结果面板时，结果角色完整位于面板内容安全区上部；标题、关键词和解释文字使用角色区下方互不重叠的文字区。结果角色不得突破面板边界，文字不得覆盖角色、徽章、边框或装饰，也不得越出面板。
- 所有结果候选共用同一结果图像槽位并互斥显示。
- 结果阶段不执行人脸软避让。
- 不创建确认、继续、重试、下一题或分享按钮。

布局案例：
- 结果揭示阶段不执行输入阶段的 `top=148` 连续内容流，也不单独在主内容区顶部放置结果标题。
- 当前命中的结果角色或插画、结果名称、关键词和简短解释组成一个结果复合单元，整体位于蓝色主内容区或蓝绿联合安全空间内，并按内容组总高度居中。
- 无面板时，结果角色与全部结果文字按阅读顺序组成纵向内容组并整体居中。
- 有面板时，结果面板承载完整结果复合单元；先划分角色区与文字区，再按“结果角色或插画 → 结果名称 → 关键词 → 解释”连续排列。角色完整位于内容安全区内，文字不得与角色重叠或越出面板。
- 结果角色不是徽章、角花或文字的替代物，必须拥有独立视觉资产 key 和对象 ID。
- 不展示输入阶段标题、题目、选项、操作对象、其他候选结果、等级色块、统计栏或操作按钮。

5. **交互布局检查**
- 所有测一测输入布局的首个非绿色完整内容单元是否满足 `top=centerY-height/2=148`，后续单元是否按上一单元 `bottom + 规定净间距` 连续排列，且没有因跨越 `y=270` 重新起排。
- 长文本、图片、对话、情境选项、待操作对象和主要视觉主体是否位于非绿色内容流中，没有进入绿色按钮区。
- 只有点击后直接触发随机结果的短文本类别，才作为按钮组放在绿色区域。
- 手指拖拽的短标签分类区、目标槽和投放区是否横向放入绿色区域，并完整位于 `x:48~672、y:929~1087`，完整高度不超过 `158px`。
- 是否不存在开始、继续及非必要的确认或提交按钮；玩法确需主动提交时只保留一个必要按钮。
- 绿色区域按钮及点击热区是否完整落区，并符合游戏 UI Reference 规定的高度上限。
- 输入阶段是否保留合理的人脸展示空间。
- 结果阶段是否明确标记为不参与人脸软避让。

- 输入阶段与结果阶段可以使用不同布局，并通过阶段显隐切换。
- 将布局类型、输入方式、主内容区起始对象、人脸展示关系、实际对象、最终尺寸和数值坐标写入 `design_brief_ui.md` 的 `Scene Layout Plan`。
- 案例中的方位描述只用于理解结构，不得替代最终数值坐标。

## Brief 补充

本 Reference 在 Draft 确认后使用，只补充与测一测相关的设计，不覆盖用户确认的主题、核心互动或结果方向。按 `game2d-planner` 识别出的动态模块展开，不增加无关栏目。

- `design_brief.md`：记录测试主题、输入方式、结果价值和总体揭晓体验。
- `design_brief_ui.md`：完整覆盖输入阶段与结果阶段所需视觉资产、Text 和静态布局；每个独立视觉结果映射唯一视觉资产 key。
- `design_brief_gamelogic.md`：在模块清单中加入实际需要的测试模式、输入映射、有限结果池、仲裁或兜底、揭晓、运行时显隐与边界处理，再按体验顺序详细展开。

## 验收
- 所有有效输入和已定义异常路径都能到达一个已枚举结果；无输入、输入不足、超时或选择不完整仅按用户或已确认 Brief 明确规定的规则处理。
- 有限随机结果不少于 2 个，且结果之间有明确语义和视觉差异。
- 结果计算规则唯一、可执行，不依赖下游临时补设计。
- 结果阶段不是只替换一行通知文字，而是形成完整揭晓反馈。
- 主 Brief 的结果体系、UI Brief 的结果视觉资产与 gamelogic Brief 的结果 ID、对象映射和触发条件保持一致，但不重复维护对方的执行表。
- 测一测输入布局必须声明统一测试内容区 `x:40~680, y:148~921`，不得在 `y=270` 重新起排。
- 主内容区顶部只能存在一个从 `top=148` 起排的无底板大标题；必要题目或上下文按精确文字高度紧接其后，不得生成题号、进度或操作提示占据顶部。
- 输入阶段的人脸检查属于构图质量检查，不执行固定人脸矩形零相交测试；局部覆盖不得发展为大面积持续遮挡人脸主体或同时遮挡主要五官。
- 手指拖拽对象、卡牌或其它下方操作主体完整位于 `y:704~921`；绿色目标槽继续遵守 `y:921~1095`，不受测试内容区影响。
- 可拖拽对象与带标签目标槽同时可见时不存在拖拽操作提示；其它必要提示只能阶段性显示在两侧或下方可用区。
- 结果阶段不执行测试类人脸软避让验收。
- 局部题号、进度、倒计时、正确数和错误数均不得出现在 HUD 中。题号或必要提示确需显示时并入当前题目复合单元；其它变量默认后台维护。
- 无提交动作时不存在确认按钮；无常驻操作时绿色区域不得生成占位控件。
- 长文本、图片、对话和情境选项卡位于测一测内容区的合法位置；短文本随机结果选项和手部拖拽的分类区、目标槽、投放区位于绿色常驻交互区。
- 拖入目标不因属于核心玩法对象而留在蓝色主内容区；其完整外接矩形和判定范围均不得越出绿色区域。
- 结果揭示阶段无HUD、无结算统计栏、无重试/下一题/分享/确认按钮。
- 各阶段按实际同时可见集合验算完整外接矩形，不得跨越固定合同禁止的区域。
- 后台累计变量未因“真实运行时变量”身份被自动转化为 HUD。
- 结果代表状态只包含一个命中结果；未命中的结果候选及其色块全部隐藏。
- 不存在由结果池生成的色块列表、等级阶梯、空白结果槽、结果图例或伪按钮。
- 游戏标题或测试标题不构成顶部底板准入理由。标题确需显示时直接使用无底板独立 Text，并按无背景文字规则配置可读性；不得使用 `ui_container`、题目容器或其它素材类型伪装标题栏。
- 存在结果面板时，命中结果角色显示在面板之上，全部结果内容位于面板内容安全区。
- 结果角色和文字作为单一内容组整体居中。
- 不存在角色缺失、角色位于面板后方、文字脱离面板或面板内部上下留白明显失衡。
