# 材质编写 — Custom Shader & Material Authoring

Use this skill when the user needs a **custom visual effect** that cannot be produced by only changing uniforms on a built-in material (Standard PBR / Unlit / etc.).

## Decision tree (run top to bottom — stop at first match)

1. **Just color / texture / tiling** → built-in material, no custom shader needed.
   - First read `asset-manager`skill and call `effect_house_toolbox` `builtinResource.queryResourceKnowledge` when you need to discover resource types or properties. Then call `builtinResource.add_builtin_resource` (e.g., `"Standard PBR"` or `"Unlit"`). Query/read the resource property schema before calling `builtinResource.set_resource_properties`.
   - Follow with `set_component(meshRendererGuid, {materials: [{guid: matGuid}]})`.

2. **Dynamic runtime uniform changes** (color pulse, scroll, blink) → built-in material + APJS script.
   - Use built-in material. In `onUpdate`, call `material.setColor/setFloat/setVector`.
   - Before writing APJS script that reads/writes material uniforms, read `APJS-Material-Runtime-API.md`.
   - Do not infer runtime APIs from `.d.ts` alone; Agent `GameManager.ts` exposes a narrower APJS runtime than internal OrionSDK scripts.

3. **Custom per-pixel math** (dissolve, outline, custom blend, vertex displacement) → create with **`materialAsset.create`** and a custom AUSL shader, then use **`materialAsset.edit`** for later source changes.
   - Build the full OMTL text in the tool payload, call `materialAsset.create`, then assign the returned material GUID. Do not create folders or write/import `.omtl` files yourself.

4. **Post processing** → write custom AUSL that reads from `UseFBOTexture`, create it with `materialAsset.create`, edit it with `materialAsset.edit`, then bind it with `sceneOps` `type: "PostProcess"` (`op: "add"` for creation, `op: "modify"` for rebinding). Use runtime scripts for built-in PostProcess parameter animation or Custom material uniform updates. See "PostProcess materials" below.

## OMTL — the three-section format

Every `.omtl` file has exactly three parts, separated by literal delimiter lines:

```
<JSON header>
---ENDJSON

---BEGIN UIPROPERTY
<property declarations>
---END UIPROPERTY

---BEGIN <auslID>
<inline AUSL shader code>
---END <auslID>
```

The `auslID` in `---BEGIN` / `---END` must match `Pass.Ausl` in the JSON header. Convention: `"a1"`.

### Coordinate convention

Material UV coordinates use a bottom-left origin: `uv = (0, 0)` is the lower-left corner, and `uv.y` increases upward. When passing positions from systems that use a top-left origin, such as Game2D screen coordinates or Vision keypoints already converted to Game2D coordinates, convert the y coordinate with `1.0 - y` before using it as a material/shader UV.

### JSON header minimum

```json
{
  "Shader": "MyCustomUnlit",
  "RenderQueue": 1000,
  "Pass": [
    {
      "Ausl": "a1",
      "Cull": "Back",
      "DepthTestEnable": "True",
      "DepthWriteEnable": "True",
      "ZTest": "LessEqual",
      "BlendMode": "DISABLED"
    }
  ]
}
```

Queue values: Opaque=1000, AlphaTest=2450, Transparent=3000.
BlendMode values: `DISABLED`, `ALPHA_TEST`, `NORMAL`, `MULTIPLY`, `SCREEN`, `ADD`, `SUBTRACT`, `OVERLAY`, `DARKEN`, `LIGHTEN`, `COLOR_DODGE`, `COLOR_BURN`.

| Optional Pass field | Default | Effect |
|---------------------|---------|--------|
| `"InstanceCount"` | (absent = 1) | Number of GPU instances for `gl_InstanceID`. Each instance draws the same mesh; the vertex shader uses `gl_InstanceID` to vary per-instance behavior (e.g., shell extrusion for fur). |

### UIPROPERTY block

Declares editor-visible uniforms and their defaults. Groups use concise Chinese semantic names wrapped in `$...$`; conditional children use `[ParentMacro]`.

```
---BEGIN UIPROPERTY
    $基础色$
    _AlbedoColor (颜色, Color) = [1.0, 1.0, 1.0, 1.0]
    AlbedoTexture (启用纹理, Defs) = 0
    [AlbedoTexture] _AlbedoTexture (纹理, 2D) = "Default_Material_Texture_Icon"
---END UIPROPERTY
```

**Editable material property rule:** every material property that the user, Agent, editor-time resource tools, or runtime script may modify must be declared in `UIPROPERTY` and also declared as a matching AUSL `uniform` in the proper `#pragma fs` or `#pragma vs` block. Do not create hidden tweakable uniforms that exist only in shader code.

**Static texture binding rule:** textures that are known during setup must be resolved before preview, not assigned by runtime `GameManager.ts` with `material.setTexture`. If the shader intentionally samples a built-in default texture, write that default directly in the OMTL `UIPROPERTY` declaration.  For generated image assets, fixed masks, noise textures, and RenderTexture resources used as stable material inputs, assign them in editor time through `builtinResource.set_resource_properties`. Runtime `setTexture` is only for texture references that genuinely change while the effect runs.

**Inspector naming rule:** the left-side labels are driven by the first metadata value in parentheses and the `$...$` group token. Use concise Chinese semantic names such as `(颜色, Color)` and `$基础色$`s.

| UIType | Uniform type | Default example |
|--------|-------------|-----------------|
| `Color` | `vec4` | `_TintColor (颜色, Color) = [1, 1, 1, 1]` |
| `2D` | `sampler2D` | `_OriginTex (纹理, 2D) = "Default_Material_Texture_Icon"` |
| `Vec2` | `vec2` | `_Tiling (平铺, Vec2) = [1, 1]` |
| `Vec3` | `vec3` | `_WindDir (方向, Vec3) = [0, 1, 0]` |
| `Vec4` | `vec4` | `_Bounds (向量, Vec4) = [0, 0, 0, 0]` |
| `Range(min,max)` | `float` (slider) | `_GlowIntensity (强度, Range(0, 1)) = 0.5` |
| `Float` | `float` | `_ShellCount (毛发壳层数量, Float) = 48.0` |
| `Defs` | macro toggle | `UseNoise (启用纹理, Defs) = 1` |


### AUSL block — structural rules

Every AUSL block MUST contain, in order:
- `#version 300 es` — **first non-empty line** of the block, no exceptions
- `#pragma only_renderers glsl30 metal`
- `#pragma multi_compile AE_AMAZING_USE_BONES` (required; bone path toggles off via 0 default but must exist)
- `#pragma shader_feature <MACRO>` — **one per UIPROPERTY `Defs` macro**. Without this, `#ifdef <MACRO>` branches stay disabled even when the UIPROPERTY toggle is ON.
- `#pragma input attributes … #pragma end`
- `#pragma varying varyings … #pragma end` (can be empty; variables have **no `in`/`out` prefix** — bare declarations only)
- `#pragma output targets … #pragma end`
- `#pragma vs attributes varyings … #pragma end` (uniforms + `#include`s for vertex stage)
- `#pragma fs varyings targets … #pragma end` (uniforms + `#include`s for fragment stage)
- `void vertex() { ... }` — vertex entry, **name is fixed**
- `void fragment() { ... }` — fragment entry, **name is fixed**

Language-level contracts (violations silently break the shader):
- **Only `//` single-line comments** — `/* ... */` is not supported by the AUSL preprocessor.
- **Macro guards use `#ifdef <MACRO>`** — `#if <MACRO>` is **not supported** for toggle checks.
- **Dynamic macros (`multi_compile`) must start with `AE_`** — engine convention.
- **`#include` lines belong inside `#pragma vs` / `#pragma fs` blocks**, not at top level.

See "AUSL language reference" at the bottom of this skill for the full pragma grammar and variant-cost rules — consult it when you need a pragma not used by the starter/recipes.

### Engine-reserved uniforms (DO NOT rename)

These uniform names are set automatically by the engine every frame. Use **exactly these names** in your `#pragma vs` block:

| Name | Type | Meaning |
|------|------|---------|
| `u_MVP` | `highp mat4` | Model-View-Projection matrix. **Use `u_MVP`, never `u_MVPMatrix`** — the latter is an LLM hallucination and the engine will not bind it (gl_Position ends up zero → object becomes invisible). |
| `u_Model` | `highp mat4` | Model matrix (object → world) |
| `u_View` | `mediump mat4` | View matrix (world → camera) |
| `u_Projection` | `mediump mat4` | Projection matrix |
| `u_TransposeInvModel` | `highp mat4` | For transforming normals to world space |

For skeletal animation, include the canonical bone UBO and use the provided helper:

```glsl
#ifdef AE_AMAZING_USE_BONES
const int MAX_BONES = 100;
struct BoneMatrix {
    highp mat4 u_Bone[MAX_BONES];
};
layout(std140) uniform highp u_PalatteBuffer {
    BoneMatrix boneMatrix;
};
#endif
#include "Packages/3D/Utilities/VertexTransform.glsl"
```

`VertexTransform.glsl` provides: `getBoneTransform()`, `get_bm_postiton()`, `get_posWS()`, `get_gl_Position()`. Use `get_gl_Position()` — never multiply by `u_MVP` yourself.

### Defs macros — the chain that must be complete

For a `Defs` UIPROPERTY toggle to actually work, **four things must line up**:

1. **UIPROPERTY declaration**: `MyMacro (宏开关, Defs) = 1`
2. **`#pragma shader_feature MyMacro`** at top of AUSL block (enables the macro path)
3. **`#ifdef MyMacro`** guards around the uniform declaration in `#pragma fs/vs`
4. **`#ifdef MyMacro`** guards around the usage in `vertex()` / `fragment()`

If you declare a uniform (e.g., `_AlbedoTexture`) **without** a `Defs` macro guard, the engine still declares it but may not auto-bind the texture from the material's texmap. The safe pattern is: introduce a `Defs` macro that mirrors each optional feature, default it to `1` if you always want it on, and guard everything with `#ifdef`.

Every UIPROPERTY uniform must also appear in a `uniform` declaration inside `#pragma fs` (or `#pragma vs`) — the UIPROPERTY alone does not declare the uniform.

## Safe starter template (textured Unlit)

**This is the minimum viable material — use this as your base, then change only what you need.** It matches the real engine `Unlit_v1.asl` contract (uses `u_MVP`, the bone UBO, and `VertexTransform.glsl`), so the compiled shader is guaranteed to bind against engine-provided uniforms.

```json
{
  "Shader": "StarterUnlit",
  "RenderQueue": 2000,
  "Pass": [{"Ausl":"a1","Cull":"Back","DepthTestEnable":"True","DepthWriteEnable":"True","ZTest":"LessEqual","BlendMode":"DISABLED"}]
}
---ENDJSON

---BEGIN UIPROPERTY
    $基础色$
    _AlbedoColor (颜色, Color) = [1.0, 1.0, 1.0, 1.0]
    AlbedoTexture (启用纹理, Defs) = 1
    [AlbedoTexture] _AlbedoTexture (纹理, 2D) = "Default_Material_Texture_Icon"
---END UIPROPERTY

---BEGIN a1

    #version 300 es
    #pragma only_renderers glsl30 metal
    #pragma multi_compile AE_AMAZING_USE_BONES
    #pragma shader_feature AlbedoTexture

    #pragma input attributes
        in mediump vec3 attPosition;
        in highp vec2 attTexcoord0;
        #ifdef AE_AMAZING_USE_BONES
            in mediump vec4 attBoneIds;
            in highp vec4 attWeights;
        #endif
    #pragma end

    #pragma varying varyings
        highp vec2 v_uv;
    #pragma end

    #pragma output targets
        out lowp vec4 o_fragColor;
    #pragma end

    #pragma vs attributes varyings
        precision mediump float;
        #ifdef AE_AMAZING_USE_BONES
            const int MAX_BONES = 100;
            struct BoneMatrix {
                highp mat4 u_Bone[MAX_BONES];
            };
            layout(std140) uniform highp u_PalatteBuffer {
                BoneMatrix boneMatrix;
            };
        #endif
        uniform highp mat4 u_Model;
        uniform highp mat4 u_MVP;
        uniform highp mat4 u_TransposeInvModel;
        #include "Packages/3D/Utilities/VertexTransform.glsl"
    #pragma end

    #pragma fs varyings targets
        precision mediump float;
        uniform lowp vec4 _AlbedoColor;
        #ifdef AlbedoTexture
            uniform lowp sampler2D _AlbedoTexture;
        #endif
    #pragma end

    void vertex() {
        v_uv = attTexcoord0;
    #ifdef AE_AMAZING_USE_BONES
        highp mat4 boneTransform = getBoneTransform();
        vec4 bm_pos = get_bm_postiton(boneTransform, attPosition);
        gl_Position = get_gl_Position(bm_pos);
    #else
        gl_Position = get_gl_Position(attPosition);
    #endif
    }

    void fragment() {
        vec4 color = _AlbedoColor;
    #ifdef AlbedoTexture
        color *= texture(_AlbedoTexture, v_uv);
    #endif
        o_fragColor = color;
    }

---END a1
```

**Why this template works**:
- `u_MVP` + `get_gl_Position()` from `VertexTransform.glsl` = correct screen-space position
- Bone UBO `u_PalatteBuffer.boneMatrix.u_Bone[]` = real engine bone binding
- `AlbedoTexture` Defs macro + `#pragma shader_feature` + `#ifdef` in three places = texture actually binds from texmap
- Default `AlbedoTexture = 1` means new materials show the default texture immediately; toggle OFF in Inspector for a pure-color variant.

## Full Agent workflow

### DYEH `materialAsset` tool contract

DYEH Agent exposes separate material operations: `materialAsset.create` creates a new Unlit-derived material, while `materialAsset.edit` rewrites an existing material by GUID. Both operations write the full OMTL and then read `GetMaterialCompileStatus`.

- **Never use file-edit tools for `.omtl` material assets**. All OMTL source creation or modification MUST go through `effect_house_toolbox` `materialAsset.create` or `materialAsset.edit`; use `materialAsset.read` only to inspect existing material source before overwriting by GUID.
- **Create a new material**: call `materialAsset` with `operation: "create"`, `assetName`, and full `omtlContent`. Do not create folders, write `.omtl` files yourself, or call a raw import path.
- **Modify an existing material**: you MUST preserve and reuse the existing material GUID. First call `materialAsset.read` with the existing `guid` (or use the known material guid from the previous tool result), then call `materialAsset.edit` with that `guid` and the full corrected `omtlContent`.
- **Never edit an existing material by only reusing the same `assetName`**. `create` always creates a new Unlit-derived material resource, even if the filename looks similar.
- If the user asks to "modify", "update", "fix", "continue editing", or "adjust" a generated material and no material GUID is known, ask for the material GUID or locate/read the existing material first. Do not silently create a replacement material.
- New materials are created from a built-in Unlit material and then overwritten with the requested OMTL. If `compileStatus.result.isError` is true, read `compileStatus.result.errorMessage`, correct the full OMTL, and retry with `edit` using the returned `asset.guid`. Do not create another material while repairing the compile error.

Example for editing an existing material in place:

```json
{
  "operation": "edit",
  "guid": "<existing-material-guid>",
  "omtlContent": "<full updated OMTL text>"
}
```

1. **Confirm custom shader is needed** — run the decision tree above. If rows 1 or 2 match, DO NOT call `materialAsset.create`.
2. **Pick a recipe closest to the goal** — start from the starter + one recipe, not from a blank file.
3. **Call `materialAsset.create`** through `effect_house_toolbox`:
   ```json
   {
     "tool_name": "materialAsset",
     "payload": {
       "operation": "create",
       "assetName": "辉光材质.omtl",
       "omtlContent": "<full OMTL text>"
     }
   }
   ```
   `assetName` is a file name such as `辉光材质.omtl`, not a path. Do not pass `Materials/辉光材质.omtl`, `Effects/辉光材质.omtl`, or create `Assets/Materials/` yourself.
4. **Verify material result** — in priority order:
   1. **`response.result.compileStatus.result.errorMessage`** / **`compile_error`** (authoritative) — the raw `ResItemMaterial.errorMessage` read directly from the engine via `GetMaterialCompileStatus`. This is the reliable channel for OMTL parse errors and AUSL compile errors (e.g., `CrossShader compiled error: 'getBoneTransform' : no matching overloaded function found`). If present, fix the shader and call `materialAsset.edit` with the returned material GUID.
   2. **`response.result.compileStatus.result.isError`** — `true` means the newly written OMTL did not compile cleanly. Fix the OMTL and retry in place with `edit`.
   3. **`compiled` / `success` fields** — broad success signals only. By themselves they do **not** justify concluding that the current branch or project compile chain is broken; check `compileStatus`, binding state, and preview evidence before escalating.
   4. **`response.results[i].warnings[]`** (command-level, non-blocking) — structural risks caught by the static validator (`BAD_MVP_NAME` / `MISSING_SHADER_FEATURE` / `BLOCK_COMMENT` / `BAD_INCLUDE_PATH` / `BAD_BONE_UNIFORM`). These are known LLM hallucination patterns — fix before assigning the material, even if `compiled: true`.
   5. **`response._compileCheck.hasErrors`** (batch-level) — script compile errors and some engine logs. Note: **most material/AUSL compile errors do NOT appear here** because they bypass the `logService` capture layer (`console.error('[ResItemMaterial] ...')` is emitted without the `##tag##` marker that `logService.consoleLog` requires, so `GetConsoleLogs` does not see them). Treat `_compileCheck` as reliable for scripts, best-effort for materials — when in conflict, trust `compile_error`.
   6. **`get_script_logs` is not reliable for material errors.** Same capture-layer limitation as above. Use it only to inspect script runtime output or TS compile errors.
5. **Assign to MeshRenderer** (separate command in same batch):
   ```json
   { "commandType": "set_component",
     "params": { "guid": { "$ref": "cubeObj", "componentType": "MeshRenderer" },
                 "properties": { "materials": [{ "$ref": "myMat" }] } } }
   ```
6. **Verify** with `capture_preview` (reloads the scene + screenshots the fresh runtime).

### Uniform-only changes — DO NOT rewrite material source

If you only want to change a uniform value after creation, use `set_resource_properties`, not `materialAsset.edit`:
```json
{
  "actions": [{
    "tool_name": "builtinResource",
    "payload": {
      "operation": "set_resource_properties",
      "guid": "<matGuid>",
      "properties": { "_AlbedoColor": {"r":1,"g":0,"b":0,"a":1} }
    }
  }]
}
```
`materialAsset.edit` rewrites the whole material file and re-compiles — it is only for AUSL source changes. `edit` requires a GUID and cannot create another material asset.

### After a source edit, re-bind the material to the renderer

The engine side re-runs `createMaterialFromData` on every OMTL rewrite. When the previous edit produced a compile error (setting `isError = true`) and the next edit recovers it, the `APJS.Material` instance may be a fresh object, or any `MeshRenderer.materials[]` that referenced the old error-state material can end up empty. **After any source edit that followed an error or a significant Pass/shader change, re-issue the `set_component` binding**:

```json
[
  { "tool_name": "materialAsset", "payload": {
      "operation": "edit",
      "guid": "<existing-material-guid>",
      "omtlContent": "<corrected OMTL>"
    }, "alias": "mat" },
  { "commandType": "set_component", "params": {
      "guid": "<meshRendererGuid>",
      "properties": { "materials": [{ "$ref": "mat" }] } } }
]
```

If the Agent observes the object rendering as untextured / placeholder after a source overwrite, that is the symptom. If a simple re-bind doesn't fix it, the heaviest hammer that always works is: `delete_component` on the MeshRenderer → `add_component` → `set_component` materials — this forces a fresh binding chain.

## PostProcess materials

Prefer the dedicated `effect_house_toolbox` `sceneOps` path with `type: "PostProcess"`. On branches that expose it, the validated failure mode is usually **material source / compile shape**, not the binding path itself.

### When to use this path

Use this workflow when:
- built-in PostProcess effects like Bloom / FXAA / Distort / Vignette are not enough
- the effect must run on the **camera output texture**, not on a mesh surface
- the user needs custom shader logic for full-screen color, UV, distortion, blur, masking, or compositing

### Hard rules

1. For any non-trivial PostProcess custom material, first use the full validated OMTL from `.agent/skills/effect-abilities/material-authoring/references/PostProcess-CustomMaterial-Reference.md` as the `omtlContent` skeleton.
2. Treat that reference as the canonical whole-file skeleton for this branch — do **not** reconstruct it from memory, snippets, or recipe fragments.
3. Change effect logic first. Keep the validated JSON / Pass shape, fullscreen vertex shape, `#pragma output targets`, `o_fragColor`, and top-level `vertex()` / `fragment()` structure intact unless you have verified evidence that a change is required.
4. Prefer `sceneOps` PostProcess `op: "modify"` only for existing Custom component material rebinding; use runtime scripts when built-in PostProcess parameters need tuned or animated values.
5. Bind screen-space / final-render custom materials to a PostProcess component. Do **not** attach these materials to an Image component as a fullscreen workaround.
6. If a material already went through compile failure and still behaves strangely after rebinding, stop patching that old asset. Create a **brand-new** material from the validated reference and bind the new material GUID.
7. If the PostProcess material depends on touch/finger/keypoint values or runtime-changing textures/uniforms, `GameManager.ts` MUST declare the serialized material/texture fields before preview, and the first workflow MUST call `setupGameScript` with `resourceBindings` so the same material and needed runtime resources are assigned to `GameManager`. Do not leave `GameManager` unbound and rely on a later user reminder.
8. When runtime input drives a visible material parameter, derive the mapping from the final Shader formula as `input key point → uniform value → visible result`; do not infer the result from the parameter name, sign, or sampling-offset direction. Preview both input endpoints and, when present, the neutral point or threshold, then compare each result with the Brief's visible semantics.

### Minimal workflow

1. Read the whole file from `.agent/skills/effect-abilities/material-authoring/references/PostProcess-CustomMaterial-Reference.md` and use its OMTL text as the in-memory `omtlContent` skeleton
2. Change only the `Shader` name and effect logic
3. Create the material with `materialAsset.create`
4. Confirm the material compiled successfully before touching PostProcess. Check `compileStatus.result.errorMessage` first, require no compile error, and call `materialAsset.get_compile_status` if the creation response is ambiguous.
5. Declare intentionally used built-in default textures directly in OMTL. Bind non-built-in static texture inputs with `builtinResource.set_resource_properties` after material creation/update. If runtime data drives the material, update `GameManager.ts` so it declares `@serializeProperty()` fields for the PostProcess material and any runtime-changing texture before binding PostProcess.
6. Add or locate the PostProcess component and bind the material with `sceneOps` `type: "PostProcess"` (`op: "add"` for creation, `op: "modify"` with `componentGuid` and `materialGuid` for rebinding). PostProcess follows the normal scene `add` / `modify` operation model.
7. If runtime fields are needed, bind the same material/texture resources to `GameManager` by calling `setupGameScript` with `resourceBindings` in the same workflow.
8. After binding, confirm `Custom` is present in `postProcessList`, then check preview. `compiled:false` alone is not enough to declare the branch/project PostProcess compile chain broken.

The `assetName` below is only a file name. Do not create a `Materials` folder or pass a folder-qualified path.

```json
]
```

Omit the `revealTexture` `resourceBindings` entry only when the material does not sample a generated texture. Texture entries must use Texture resource GUIDs, not asset file names. Do not omit the material `resourceBindings` entry when runtime code writes uniforms such as finger/touch position, because `GameManager` needs the same material instance as the PostProcess component.

Before any resource-binding retry, inspect `GameManager.ts` and confirm it already declares the serialized fields named by the `resourceBindings` entries. If fields are missing, add them, compile the script, then retry only the `setupGameScript` resource-binding call.

If resource assignment fails because `GameManager.ts` did not have the serialized fields during the first workflow, add the fields and retry only `setupGameScript` with `resourceBindings` instead of recreating the PostProcess component or resynchronizing abilities.

If the PostProcess component already exists, never call PostProcess `op: "add"` again for that same effect. If only script field/resource assignment failed, check/fix `GameManager.ts` fields first, then retry `setupGameScript` with `resourceBindings`. If the material was regenerated, call `sceneOps` PostProcess `op: "modify"` with the existing `componentGuid` and the new `materialGuid`, then call `setupGameScript` with the new material GUID in `resourceBindings`.

### If the result looks wrong

- First assume **OMTL/AUSL source compatibility**, not binding failure
- If the material previously failed to compile and still behaves wrongly after one clean overwrite plus rebind, prefer creating a fresh material asset over continuing to patch the old one
- If the project still contains an older APJS/script bridge, verify that it is not still writing uniforms that no longer exist on the current shader

## Common errors — grep your OMTL before submitting

| Symptom | Root cause | Fix |
|---------|-----------|-----|
| `#pragma output targets` is empty but `fragment()` still writes `o_fragColor = ...` | The output declaration drifted away from the validated PostProcess skeleton | Restore the validated output block and keep `out highp vec4 o_fragColor;` declared explicitly. |
| PostProcess helper functions were moved outside `#pragma fs varyings targets` | The generated shader no longer matches the validated branch structure | Put `_MainTex` / `u_ScreenParams`-dependent helpers back into the `#pragma fs varyings targets` block and keep only `vertex()` / `fragment()` top-level. |
| **Object renders invisible / transparent** (most common failure) | Using `u_MVPMatrix` instead of `u_MVP` | The engine only binds `u_MVP`. `u_MVPMatrix` stays at zero matrix → all vertices collapse to origin → nothing drawn. Use `u_MVP` + `get_gl_Position()` from `VertexTransform.glsl`. |
| **Texture looks black / material renders transparent** | Texture uniform declared without `Defs` macro guard | Wrap the sampler with a `Defs` macro (e.g., `AlbedoTexture`), add `#pragma shader_feature AlbedoTexture`, default UIPROPERTY to `= 1`, guard `uniform lowp sampler2D _AlbedoTexture` and its usage with `#ifdef AlbedoTexture`. |
| **`Defs` toggle has no effect** | Missing `#pragma shader_feature <MACRO>` at top of AUSL block | Add it — without the shader_feature pragma, `#ifdef` blocks stay disabled regardless of UIPROPERTY value. |
| `void main()` | AUSL entry names are fixed | Rename to `void vertex()` / `void fragment()` |
| UIPROPERTY declares `_Foo` but no `uniform … _Foo` in `#pragma fs/vs` | UIPROPERTY alone doesn't declare uniforms | Add the `uniform <type> _Foo` declaration in the fs or vs block |
| `---BEGIN al` (lowercase-L) vs `"Ausl": "a1"` (number-one) | Case-sensitive typo | Match exactly — the block id is case-sensitive |
| Missing `#pragma multi_compile AE_AMAZING_USE_BONES` | Required even for non-skinned meshes | Keep it on; model either enables or disables the bone path |
| Missing `---ENDJSON` | Parser needs the literal line | Cannot omit |
| Transparent material renders opaque | Wrong Pass config | Set `"BlendMode": "NORMAL"` AND `"RenderQueue": 3000` AND `"DepthWriteEnable": "False"` |
| Uniform sets but has no visible effect | Not sampled in shader | Use the uniform inside `vertex()` / `fragment()` — UIPROPERTY writes the value but shader code must sample it |
| Bones "work" on your local test but break for skinned models | Declaring bones as `uniform mat4 u_BoneMatrixes[64]` | Wrong — use the engine's UBO struct pattern (see the starter template's bone block) |
| Vertex shader compile fails with `'getBoneTransform' : no matching overloaded function found` (or similar for `get_gl_Position` / `get_bm_postiton` / `get_posWS`) | `#include "Packages/@amazing/orion-shader-library/..."` — that prefix does not exist on disk, so the include expands to nothing | Use `#include "Packages/3D/Utilities/VertexTransform.glsl"`. The engine rewrites `Packages/` → `<OrionShaderLibrary_root>/`; the first path segment after `Packages/` must be a real subfolder (`3D/`, `core/`, `common/`). |
| Object renders as placeholder / wrong material after a successful source overwrite | MeshRenderer.materials[] can end up empty when the engine re-runs `createMaterialFromData` — especially following a compile-error edit. The shader compiled fine, but the renderer lost its binding. | Re-issue the owning material-assignment operation with the same material GUID. If that still does not fix it, recreate the renderer binding through the owning scene/component workflow. |
| Script reads `renderer.mainMaterial` as null even though the material is bound in the editor | `mainMaterial` is a convenience getter typed `Material \| null`; it can return null during the first frames of binding or around material source rewrites, even when `materials[0]` is populated | Access via `materials[0]` with `mainMaterial` as fallback: `const mat = r.materials && r.materials.length > 0 ? r.materials[0] : r.mainMaterial;`. See `skills/MeshRendererScript`. |
| Shader fails to compile after adding a comment | Used `/* block comment */` | AUSL only supports `//`. Rewrite as single-line comments. |
| `#ifdef` branches flip unexpectedly or compile fails | Used `#if MY_MACRO` instead of `#ifdef MY_MACRO` | Toggle macros use `#ifdef` only. See "AUSL language reference" for full rules. |
| `#pragma multi_compile` doesn't take effect | Dynamic macro name doesn't start with `AE_` | Rename to `AE_MY_MACRO`. |
| `#include` line reports "file not found" or behaves unpredictably | Placed `#include` at top level or outside vs/fs block | Move it into `#pragma vs` or `#pragma fs`. |

## Rules

- **Don't author PBR from scratch.** PBR needs 1600+ lines of light/tone-mapping code. Clone Standard PBR and modify uniforms instead.
- **Don't call `materialAsset.create` for uniform-only tweaks.** It's for shader source; uniforms go through `set_resource_properties`.
- **Don't write `#include` paths as absolute.** Use `#include "Packages/…"` — the engine rewrites these at load/save time.
- **Don't skip the boneMatrix branch.** Even non-skinned models compile the `AE_AMAZING_USE_BONES`-off path; remove the branch and builds break for skinned meshes.
- **Don't rewrite material source only to add a `Pass` option** — if a render-state toggle exists as UIPROPERTY already, let the user change it in the Inspector.
