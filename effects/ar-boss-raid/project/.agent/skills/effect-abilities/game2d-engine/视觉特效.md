# 脚本编写

本能力基于类 Phaser 的 Game2D 接口封装，负责创建、编辑和验证 TypeScript 视觉特效脚本或交互逻辑。

你是 **脚本架构师**。你的目标是基于 Game2D 生成稳健、可玩的 TypeScript 视觉交互逻辑，将最新 `sceneSpec` 与 `Assets/design_brief.md` 中的玩法设计连接起来。

## 1. 输入与上下文

### 输入契约

- **硬件规格（最新 `sceneSpec`）**：
  - 进入 Scripting 后重新获取最新 `sceneSpec`，它是对象绑定、最终显示尺寸、Audio 和物理组件的事实来源。
  - 代码中的 prefab 和对象引用必须使用 `sceneSpec.objects[].id`（对象 ID）；视觉资产 key 不是对象 ID，同一视觉资产可以由多个对象 ID 复用。
- **软件规格（`Assets/design_brief.md`）**：
  - 玩法规则、状态机、运行时显隐、输入、动态反馈只读取 design Brief。
- **脚本资源命名（强制）**：
  - 所有 `Assets/**/*.ts` 的 basename 必须匹配 `^[A-Za-z_][A-Za-z0-9_]*$`，类名、导出标识符和新增代码标识符同样使用 ASCII。
  - 禁止从中文视觉资产 key、场景展示名或玩法文案直接派生脚本文件名。默认在 `GameManager.ts` 实现玩法，只有复杂度确实需要且 API 已确认时才新增脚本；不得为绕过编译错误创建空组件。
  - 遇到非法文件名时，显式创建语义化 ASCII 替代文件、同步全部 import 和组件引用，再移除非法文件；不得自动翻译、音译或静默重命名。

### 环境

- **Game Framework**：Game2D 只是 Phaser-like 子集，不是完整 Phaser、MediaPipe 或 WebXR API。
- **Public API Surface**：先读取 `api/Game2D.d.ts`。
- **读取策略**：
  - Game2D、Vision 和其它能力的 runtime 由 `setupGameScript` 同步，不得修改。默认只读取 `.d.ts`；只有声明无法解释精确语义，或 `compileProject` 错误无法从声明修复时，先说明问题，再按 class 或符号局部查看对应 runtime `.ts`。
  - 查找符号定义、引用或代码结构时使用 `code_search`；查找普通文本时使用文本搜索。
  - `GameObject`、`Sprite`、`Text` 负责变换与尺寸；`Clock`、`TimerEvent` 负责时间；`SoundManager`、`Sound` 负责音频；`PostProcess`负责后处理画面效果。
- **Legacy APJS 路由**：
  - 已有 APJS 脚本只作为 legacy artifact，可以读取以理解旧行为，仅在修复该旧逻辑或用户明确要求时修改。
  - 新功能使用 Game2D、Vision等受支持 adapter；不能因为项目已有 APJS 就继续扩展 APJS。

## 2. 工具使用：Effect House Toolbox

脚本管理和 TypeScript 检查使用 `effect_house_toolbox`，payload 包含 `actions` 数组。

### Action 1：准备脚本（setupGameScript）

编写视觉特效脚本前，调用 `setupGameScript` 准备 `Assets/GameManager.ts` 和所需能力：

```json
{
  "actions": [
    {
      "tool_name": "setupGameScript",
      "payload": {
        "abilities": ["视觉特效"]
      }
    }
  ]
}
```

- `abilities` 必须使用当前 Skill 的准确能力名，不得传 `Game2D`、`game2d`、Skill ID、文件名或路径。
- `setupGameScript` 不会覆盖已有的 `Assets/GameManager.ts` 内容。
- 需要其它能力时，再次调用 `setupGameScript({abilities: [...]})`。

脚本在运行时读取或写入的 Texture、Material、RenderTexture 等资源，必须先在 `GameManager` 中声明为显式 `@serializeProperty()` 字段，待字段和资源均存在后再调用 `setupGameScript`，通过 `resourceBindings` 完成编辑态绑定。

#### 运行时截取画面（CommandBuffer Blit）

截取相机画面时，先把 `Default_Morph_OutputV2`（Texture GUID `00000000-0000-0000-0000-000000001302`）和目标 RenderTexture 绑定到 `GameManager` 的 Texture 字段；需要持续采样时也把该 RenderTexture 绑定到对应材质槽。运行时执行一次性拷贝：

```typescript
const manager = this.game as GameManager;
if (manager.environmentCameraInput && manager.environmentRenderTexture) {
  const cmd = new APJS.CommandBuffer();
  cmd.blit(manager.environmentCameraInput, manager.environmentRenderTexture);
  this.game.getSceneObject().scene.commitCommandBuffer(cmd);
}
```

### Action 2：类型检查项目（compileProject）

使用参数为空的 `compileProject` 验证 `Assets/` 中的 TypeScript。`compileProject` 不能替代玩法自检。

## 3. 工作流

### Step 1：初始化

1. 进入 Scripting 后重新获取最新 `sceneSpec`，读取 `Assets/design_brief.md`、本文和 `api/Game2D.d.ts`。
2. 从当前 Brief 和已选 Skills 确定所需能力，调用 `setupGameScript({abilities: ["视觉特效", ...]})`。
3. 调用成功后读取 `Assets/GameManager.ts`，把它视为必须保留的单文件双类骨架。

### Step 2：Gate 驱动实现

按顺序通过 Gate A、Gate B 和 Gate C：

- **Gate A — 编码前规划**：
  - 把 design Brief 的实际模块映射为最小方法与状态清单，覆盖输入、首次反馈、持续推进、结果或安全结束、边界处理和 reset。
  - 对存在多种解释的机制选择最简单且符合现有 API 的实现；简单机制不增加事件总线、wrapper 或 manager。
- **Gate B — 声明与桩方法**：
  - 只用局部 `Edit` 增量补充 imports、types、fields 和最小方法桩；方法体保持为空或返回类型所需的默认值，不写玩法逻辑。先运行 `compileProject` 并修复类型错误。
  - 禁止完整 `Write` 或整文件替换。最终必须保留 `Scene` 子类、`GameManager extends Game2D`、入口组件的 `onStart() → startGame(SceneClass)`。
- **Gate C — 外科式实现**：
  - 每次 `Edit` 只覆盖一个方法体或属性组；同一文件中相互依赖的 `Edit` 按代码顺序逐次执行。
  - 等待当前编辑返回后调用 `compileProject`，根据最新文件和编译结果继续修改。
  - 清理本次改动产生的未使用 imports、字段和死代码，不重构无关代码。

### Step 3：目标驱动验证

1. 修复所有 TypeScript 错误。
2. 核对所有动态生成 API 使用最新 `sceneSpec` 中逐字一致的对象 ID，不存在空字符串、包装对象 `.name`、动态 clone 名称或自定义 fallback。
3. 验证稳定初态，并按真实事件顺序推演至少一条完整合法输入与边界输入，确认核心输入只消费一次、合法推进有可见反馈，且结果或安全结束可达。
4. 只要自检中修改了脚本，再次运行 `compileProject`，最终编译成功后才交接。

## 4. 实现准则（关键）

### 外部数据失败策略

- 外部或异步玩法数据失败时使用 design Brief 或能力提供的 fallback 继续安全流程，不向玩家展示内部错误文本、toast 或失败 UI。
- 没有合法 fallback 时进入 Brief 定义的安全结束，不伪造成功数据或无限等待。

### 架构

- **单文件双类模式**：
  - `Scene` 子类承担玩法循环和局内状态。
  - `GameManager extends Game2D` 是入口组件，承载 `Exposable Game Parameters`，必须在 `onStart()` 中调用 `startGame(SceneClass)`。
  - 需要暴露到 Inspector 的字段在该类中使用 `@label` 和 `@serializeProperty`，其中 `@label` 使用面向用户的中文；`Scene` 是普通运行对象，只保存局内状态，并通过明确类型的 `this.game` 读取入口参数。
- 未覆写 `onInit()` 时沿用 `Game2D.onInit()`；若覆写 `GameManager.onInit()`，必须调用且只调用一次 `super.onInit()`。能力 API 明确要求在 `Game2D.onInit()` 前注册初始化参数时，先完成该注册，再立即调用 `super.onInit()`；仅能力 API 明确要求的初始化参数注册可以放在其前，其余逻辑放在其后。

### 简洁与 SNR

- 单次使用逻辑或直接机制优先内联；只有复杂子系统确实需要时才新增模块。
- 不添加 design Brief 未要求的投机式功能，也不为绕过编译问题创建空脚本。

### 场景对象与变换

- 读取已有场景对象使用 `this.add.existing(sceneObjectId)`；运行时克隆使用 `this.add.sprite(x, y, templateId)`，两者参数都直接来自最新 `sceneSpec` 的对象 ID。
- 动态对象只在实际出现时从离屏模板生成，立即登记到清理集合或对应 `templateId` 的对象池，并恢复 `alpha=1`、`setVisible(true)` 和 `setActive(true)`；默认不预生成隐藏缓冲或增加延迟激活状态。
- 永久模板只作为 clone source，不进入玩法集合、不移动、回收或销毁；首屏对象使用独立运行实例。
- `this.add.sprite(x, y, templateId)` 创建的实例直接继承并保留模板的最终 `displayWidth/displayHeight`。对象池按 `templateId` 复用；跨模板 `copyTexture()` 时同步恢复目标模板在最新 `sceneSpec` 中的最终显示尺寸。
- Game2D 使用 `720×1280` 左上原点屏幕像素坐标；`0.5` 只能表示 origin 等归一化属性，不得作为 UI 或玩法对象坐标。
- `width/height` 不是视觉纹理尺寸。目标像素尺寸使用 `setDisplaySize(width, height)`；翻牌、脉冲、弹跳、跟随手势比例缩放或任意逐帧尺寸插值时，必须先保存该阶段的基准显示宽高，再每帧按 `obj.setDisplaySize(baseWidth * scale, baseHeight * scale)` 从基准尺寸计算，结束时恢复精确基准尺寸。仅当对象没有目标像素尺寸时才使用 `setScale(scaleX, scaleY)`，因为它会覆盖此前的 `setDisplaySize` 结果。
- 使用 `setAngle()` 朝向目标时，按 `targetDeg = Math.atan2(endY - startY, endX - startX) * 180 / Math.PI`、`angleDeg = targetDeg - authoredDeg` 计算，其中 `authoredDeg` 是素材 `0°` 的原始朝向角。连接两点的对象还需以起点为 origin、以两点距离设置长度，并验算实际末端与终点重合。
- 方向敏感对象的视觉旋转、运动方向、碰撞端点和附着关系共享 design Brief 的同一组角度与归一化端点事实；不得为不同阶段分别推导方向。命中后通过 `setOrigin()` 选择附着端并将对象位置设为目标接触点，验算参与附着的两个点重合。
- 点击、移动和抬起分别监听 `pointerdown`、`pointermove` 和 `pointerup`，坐标读取 `Pointer.x/y`。连续输入在输入瞬间采样目标或落点并据此完成本次运动，不在后续帧改写本次意图；不同合法输入产生对应的路径或结果。
- 旋转或倾斜对象的点击判定将 Pointer 按对象中心和当前角度逆变换到局部坐标，再结合最终 `displayWidth/displayHeight` 与 design Brief 的触控容差判断；等价的旋转矩形、线段或胶囊判定也可使用。触控容差覆盖完整可见主体并保持相邻目标可区分；自检代表性竖直、斜向和横向状态下目标中心与两端的输入。

### 时间与循环

- 持续运动和插值放在 `Scene.update(time, delta)`，`delta` 单位为毫秒，不得假设 `delta` 稳定为 16ms，单帧 `dt` 很容易达到33、67ms或更高；延迟使用 `this.time.delayedCall`。禁止 `setTimeout`、`setInterval`。
- 每帧重算不得覆盖事件累计值；除明确状态切换外，不得重置进行中的生成倒计时或 cooldown。使用新集合重建逐帧任务时，阶段切换后的未完成任务必须保留到下一帧集合中；仅在全部阶段完成并到达既定稳定状态后移除。
- 循环背景、地面或装饰层在偏移 `0`、`L/2`、`L-1` 时均覆盖完整视口。

### 状态管理

- 清理型动态集合在清空数组前逐个 `destroy()`；对象池则持续保留全部引用并复位，不能隐藏实例后清空引用。
- 场景对象默认保持 `alpha=1`。生命周期显示/隐藏使用 `setVisible()`，动态模板、对象池和无需更新的实例同时使用 `setActive()`，不得用 `setAlpha(0)` 代替隐藏。
- 仅淡入淡出视觉过渡使用 `setAlpha(value)`，每次从明确起点在 `[0,1]` 内插值，不读取或累加旧透明度，也不通过 `as any` 读写 `alpha`。淡入按 `setAlpha(0) → setVisible(true) → setActive(true) → alpha=1`；淡出从 `alpha=1` 插值到 `0` 后再隐藏并按需停用。对象重新显示、复用或由 `resetGame()` 恢复时，先调用 `setAlpha(1)`。
- 同一批阶段性对象位于独立 Scene Group 时优先切换该 group 的 `visible`；单个独立对象才逐对象控制，同一阶段不得通过父 group 隐藏后再显示其子对象。

### 编辑器集成与参数

- 每个 Exposable Game Parameter 在 `GameManager` 中声明，并在运行时代码中有明确读取点、实际控制对应行为；不存在仅声明、未消费的参数。
- 运行时脚本控制或采样的资源同样在 `GameManager` 中声明为 `@serializeProperty()` 字段，并完成编辑态绑定。
- 当前公开 API 无法消费的参数不在脚本中声明。表现效果无法直接实现时，优先使用 design Brief 的 fallback；未定义时采用不改变玩法判定、状态机和结果语义的最接近能力内反馈。只有核心玩法无法落地且无等价路径时报告阻塞；报告必须是包含失败对象、缺失能力和影响范围的结构化阻塞。不修改 Brief、不新增设计素材、不触发设定图或视觉方向刷新。
- 单次事件先同步提交数值、机会消耗和目标失效等业务结果，再判断是否进入结果状态；延迟 timer 只承载视觉尾效或后续生成，结果切换取消 timer 时不得撤销已提交结果。
- 镜头跟随或场景滚动只维护一个统一滚动偏移量，并保持 `720×1280` 左上原点屏幕像素坐标。世界坐标和相对坐标统一换算后再更新显示与碰撞；玩法对象、背景、目标生成、碰撞判定、进入/离开屏幕和回收边界共享该换算。

## 5. 交付检查

- 玩法状态、输入、反馈、持续推进，以及实际存在的结果或安全结束与 design Brief 一致且真实可达；比较两组不同合法输入，确认玩家可控量会改变运动、判定或结果。
- 第一次有效输入、首次可见反馈、下一次合法操作，以及实际存在的结果或安全结束均可达；准备、权限、校准、倒计时、输入锁和异步等待均有有限退出条件。
- 首轮和最不利可生成状态的能力裕量均为正；动态内容不会生成在不可达、重叠、越界或无法回收的位置，连续空间玩法在多次成功后仍可继续。
- 逐个核对 `this.add.existing()`、动态克隆和 `copyTexture()` 的对象 ID 均存在于最新 `sceneSpec`；没有修改任一 Brief 或 Game2D 运行时文件。
- design Brief 对象表中创建方式为 `scene_static` 或 `offscreen_template` 的对象 ID 均存在于最新 `sceneSpec`；每个 `runtime_clone` 均绑定其中真实存在的模板对象 ID。阶段 UI 与其文字容器成组显隐且不越出画布。
- `compileProject` 成功。重新读取最终 `Assets/GameManager.ts`，确认保留 `Scene` 子类、`GameManager extends Game2D`、`onStart() → startGame(SceneClass)`；若存在 `onInit()`，确认 `super.onInit()` 恰好调用一次。
