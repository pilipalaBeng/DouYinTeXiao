# 物理系统

## 能力描述

提供基于 Matter2D 的真实物理模拟能力，用于表现力、动量、碰撞响应、角运动、转动惯量及多个物体之间的持续互动。

## 1. Matter2D Applicability
You MUST choose **True Physics / Matter2D** when the core fantasy depends on:
- believable force transfer
- collision response that should emerge from simulation rather than fixed scripting
- angular motion or rotational inertia
- sustained multi-body physical interaction that would become unnatural or overly complex if fully scripted
- contact-driven win/loss where collisions must change pose/stability (tilting, toppling, being squeezed/pushed, repeated contacts with moving obstacles)
Do NOT downgrade these cases into **Kinematic / Scripted Motion** just because a simplified implementation seems easier.
Do NOT use Matter2D just because a game has falling, rising, gravity-like acceleration, jumping arcs, or simple blocking collision. If the gameplay can be implemented cleanly with **Kinematic / Scripted Motion** plus basic collider/overlap handling, prefer the **Kinematic / Scripted Motion** approach.
Note: Joint constraints (linking two rigid bodies), such as ropes or rigid rods, are not supported yet in Matter2D. Use scripted / simulated motion to implement these effects.

## 2. Shared Matter2D Semantics
**Blocking/separation rule**
- Blocking/separation requires BOTH colliders in the contact to be tangible (`isTangible: true`). If either side is non-tangible, the interaction becomes overlap/pass-through (no blocking).
**Units & coordinates**
- Scene layout `width` / `height` are screen pixels.
- Editor physics components store collider geometry in world units.
- SceneBuilder / `sceneOps` collider inputs use screen pixels, and `SceneOpsService` converts them to world units automatically.
- Default collider conversion is `1 world unit = 32 px`.
- Matter2D body motion APIs (`getPosition/setPosition/getVelocity/setVelocity/applyForce`) use screen-space pixels by default (`+Y` down).
- Collider helper APIs in `this.matter2d` treat size / offset / radius inputs as screen pixels.
Examples:
- `128x64` image -> BoxCollider2D `size: { "width": 128, "height": 64 }`
- `96x96` circle -> CircleCollider2D `radius: 48`

## 3. Physics2D Plan Specification
If `game2d-planner` chooses **True Physics / Matter2D**, `Assets/design_brief.md` MUST include a `Physics2D Plan` that follows this section.
Purpose:
- the gameplay-significant physics contract for downstream stages (SceneBuilder + ScriptGenerator)
Scope:
- include gameplay-significant physics objects only
- do NOT include purely decorative/non-interactive visuals
- do NOT turn the plan into runtime pseudocode or API call steps

When a game uses physics, playability depends on state design. Plan collider/layout constraints at authoring time, and plan per-phase physics states at runtime (especially `static`, `useGravity`, visibility, and intentional sensor/collider state changes). Do not “add physics late” in a way that makes the game unwinnable or inconsistent.
### 3.1 Plan Shape
Required fields per physics object:
- `object_id`: canonical object id from the brief/scene
- `rigidbody`: `dynamic` or `static`
- `colliderType`: `Box` | `Circle` | `Polygon` | `Edge` (single-collider summary)
- `colliders`: optional detailed list when an object needs multiple colliders (including multiple colliders of the same type)
- `isTangible`: `true` (blocking/separation) or `false` (overlap/trigger)
- `physicsMaterial`: `default`, `none`, or a custom material name/intent

Writing rules:
- use one row per gameplay-significant object, or one row per object family/template if many spawned instances share the same physics setup
- use canonical ids/names so SceneBuilder and ScriptGenerator can map the plan directly
- add `useGravity` when gravity behavior is important or intentionally disabled
- use `notes` for special expectations such as "sensor only", "starts static, released later", "uses simplified collider", or "rebound should feel bouncy"
- if an object changes physics state during play, describe the default state in the main row and explain the phase/state transition in `notes`
- for script-time dynamic `clone()` guidance (when it is OK vs NOT OK), see section 3.4.
- avoid designing difficulty tiers that rely on tuning physics at runtime by default; the physics itself is part of the gameplay essence.
- if rebound, slipperiness, or stickiness materially affects gameplay, do NOT leave `physicsMaterial` vague
- if you explicitly want no rebound (e.g. two objects collide and then stick together), keep `physicsMaterial` as `none` and implement the "stick" behavior via gameplay state/control instead of relying on a bouncy material.

Forbidden plan shapes:
- vague statements like "enable physics for the player" without collider/tangibility/material semantics
- listing decorative objects that do not participate in gameplay-significant physics
- using `isTangible: false` for objects that are supposed to block/separate
- omitting `notes` when the object has important state transitions such as pinned -> released
- describing implementation code instead of design intent
- planning objects that require full dynamic physics simulation to be spawned via runtime `clone()` instead of preparing them in the scene beforehand

Example table (`notes` optional unless needed):
| object_id | rigidbody | colliderType | isTangible | physicsMaterial | notes |
|---|---|---|---|---|---|
| `player_ball` | `dynamic` | `Circle` | `true` | `bouncy` | gravity on; main controllable ball |
| `ground` | `static` | `Box` | `true` | `default` | floor and blocking surface |
| `score_gate` | `static` | `Box` | `false` | `none` | sensor only; overlap used for scoring |

### 3.2 Physics Feasibility and Collider Fit (Critical)
When you choose **True Physics / Matter2D**, the planned spawn rules and level geometry MUST satisfy these invariants, otherwise simulation becomes unstable (stuck/exploding/jittering) and gameplay tuning becomes unreliable.

- No initial penetration: dynamic bodies must not intersect tangible colliders at start.
- Guaranteed clearance: for any intended passable gap, `minGap >= moverColliderExtent + margin` (margin: 4–16px).
- No solid-solid overlap: tangible static colliders should not overlap each other.
- Entry/exit consistency: if gameplay requires crossing a boundary, do not place a blocking collider on that path.

The following collider rules are the single source of truth for both Physics2D planning and SceneBuilder collider authoring:
- Default fit: use ONE collider per object by default. Start from visual-fit (Box matches Image `width/height`; Circle radius matches half diameter), then apply small gameplay-fit adjustments only when needed.
- Scale consistency: if you change an object's visual size (resize Image width/height), update collider geometry proportionally (e.g. wall scaled 2x → collider size 2x), unless you intentionally keep a smaller gameplay-fit footprint (document it).
- Offset policy: keep `offset` at `{x: 0, y: 0}` unless there is a deliberate design reason; avoid “offset-by-eye”.
- Asset policy: if visuals have transparent padding, prefer fixing/cropping the asset instead of compensating with oversized colliders.
- Gameplay-fit decision rule (keep changes small and consistent):
  - Prefer visual-fit when gameplay requires intuitive “looks like it touches” judgement (precise landing, tight insertion, exact hit zones).
  - Prefer gameplay-fit when physics stability/feel matters more than exact silhouette (many falling/stacking items, dense obstacles, fast movers, snag/jitter).
  - Typical gameplay-fit adjustments: shrink footprint by 2–8px margin; reduce one dimension for slender objects (e.g. thin stem) to avoid overly stable stacking; prefer a more rounded approximation (Circle) when edge-catching is frequent.
  - If you change fit, document the intent in `notes` (e.g. “reduced contact footprint to avoid stacking / snagging”).
- Verification: after manual collider edits, re-run `sceneSpec` and treat `physics2d.colliders[]` as ground truth; use `guid` (preferred) or `index` (fallback) to target a collider in `sceneOps`.

### 3.3 Object Roles and Judgement Strategy
#### Role clarity (MUST)
- RigidBody-only: simulated motion (gravity/velocity/impulse/torque) but no contact/trigger interactions.
- Collider-only: static blocker/trigger zone; participates in collision/overlap events but does not need simulated motion.
- RigidBody + Collider(s): participates in both simulated motion and contact/trigger interactions.
- If an object is meant to block/separate, ensure it has tangible collider(s) and make the state (static/dynamic) explicit.

#### Hybrid patterns
- It is valid to use Matter2D for specific objects/effects while keeping core interaction/judgement deterministic in scripts.
- Plan rule: include physics-bearing objects that materially affect gameplay; exclude purely decorative physics fragments by default.
  - If an effect fragment can block/separate, can trigger scoring, or can be collided with by the player, it becomes gameplay-significant and MUST be included.

#### Hit judgement layering
Use this pattern for "visual-intuitive hits":
- Physics provides motion/contact feedback ("looks like it caught/hit/bounced"); scripts make the final success/fail decision.
- Do NOT make critical scoring/catch/collect/win conditions depend only on overlap/collision callbacks. Use a stable script-side region test in `update` (screen-space or logical zones), and treat physics events as auxiliary triggers/fallbacks.
- Use this pattern when overlap/collision callbacks can miss or feel unfair, such as:
  - fast movers (tunneling / missed frames)
  - small or thin trigger zones
  - a moving/rotating catcher or container that players control directly
  - complex shapes where a single collider is a coarse approximation
  - runtime re-positioning of static bodies/sensors (script-driven transforms)
  - AR / variety-show / light-competitive games where "visual intuition" is the primary success criterion
- Typical patterns (use `notes` to state the split):
  - Fruit slicing: scripted judgement (gesture path / segment intersection) + physics fragments (scatter/fall).
  - Target shooting / hit-scan: scripted judgement (ray/line hit) + physics feedback (recoil/swing/fragments).
  - Balloon pop: scripted judgement (tap/gesture/overlap) + physics fragments (scatter/settle).

### 3.4 Script-time Dynamic `clone()` (Physics2D)
Dynamic `clone()` is conditionally OK. Use this decision rule:
- OK (recommended) when the cloned object has no physics components (pure visuals/UI), or its physics body remains `static=true` for its entire runtime lifetime and script control is used for any pose changes (static blockers, trigger gates, event sensors).
- NOT OK when the cloned object becomes `static=false` and must participate in full dynamic physics simulation after spawn (gravity/impulse/force-driven motion, collision response, stacking/settling), where clone-time physics binding/initialization correctness becomes gameplay-critical.
Dynamic `clone()` with physics components is typically OK for:
- Script-driven static obstacles: objects moved deterministically by script (e.g. pipes in Flappy Bird) that behave as static blockers/sensors, not as simulated bodies.
- Trigger-only gameplay: overlap gates/sensors used for scoring, pickups, checkpoints, where contacts are used as events and the object itself does not need stable physical response.
- Kinematic-style motion: objects that remain `static=true`, whose pose is fully controlled by script every frame, and whose physics components are used only for detection (keep collider shapes simple and stable).
Dynamic `clone()` with physics components is typically NOT OK for:
- Dynamic bodies: any spawned object that must fall, bounce, collide, settle, or stack correctly (gravity on, impulse/force applied, velocity-driven motion).
- Simulation-result judgement: win/loss/scoring depends on a dynamic body's precise contact response or settling result (e.g. "inserted into bottle", "stable landing", "touch sequence").
Practical guidance:
- If you choose dynamic `clone()` for a physics-bearing object, keep it to the “script-driven static/trigger” category and keep colliders simple.
- All-runtime-static clones with multiple colliders or runtime scale/rotation changes remain allowed, but their cloned collider state and geometry MUST be validated before relying on them for gameplay. Do not use collider enable/disable as the default lifecycle model; reserve it for explicit visible-but-non-colliding gameplay states.
- Runtime-cloned static/trigger physics objects MUST keep their intended spawn/reset pose in script state (position, and rotation if relevant). See **Runtime Matter2D Guidance → Motion ownership** for reset sequencing.
- If you need “dynamic body” behavior, prefer a scene-prebuilt pool of instances that scripts only activate/reposition/reset/reuse.
- If you are not sure which category an object belongs to, default to the scene-prebuilt pool approach. Do NOT avoid pooling because the count is large; prebuilding many instances is acceptable when it keeps physics behavior stable and predictable.

## 4. SceneBuilder / sceneOps Physics Expression
**Responsibility split**
- SceneBuilder / `sceneOps`: editor-time/static setup only (components, collider geometry, materials, initial static/dynamic state)
- Script: runtime behaviors (velocity, gravity enabling, forces, callbacks, state transitions)
- `extensions.physics2d` can be used on `Image` and `Text` scene objects.
**Source of truth**
- treat `sceneSpec.objects[].physics2d` as the source of truth for current colliders (types, count, index/order, guid when available)
- re-run `sceneSpec` after any manual editor changes to colliders/components
- if user manually tweak collider geometry (size/offset) in the editor, treat the current editor result as the ground truth and use the refreshed `sceneSpec` output for script initialization. You can detect manual overrides by comparing the post-op collider geometry against the planned values; any mismatch means the editor result wins.
**`extensions.physics2d` schema**
- Mutation semantics (MUST):
  - `ensure: true`: ensure the targeted component exists (auto-add it if missing), then apply any provided property updates.
  - `ensure: false` or omitted: do not create or remove a component; only patch an existing target when update fields are provided.
  - `remove: true`: delete the targeted component independently of `ensure`. If the target is missing and `validateOnly: true`, the operation must error.
  - `validateOnly: true`: assert that the target exists without mutating the scene.
- `rigidBody`
  - operation flags: `ensure`, `remove`, `validateOnly`
  - static properties: `static`, `useGravity`
- `colliders[]`
  - this is the only supported collider form; use a one-element array for the common single-collider case
  - `type`: `BoxCollider2D` | `CircleCollider2D` | `EdgeCollider2D` | `PolygonCollider2D`
  - targeting (choose ONE):
    - `guid`: preferred stable identifier for an existing collider component
    - `index`: optional non-negative integer index in the engine-provided collider list (order-dependent). New colliders can only be appended at the end (`index == existingCount`); removing a collider shifts later indices left.
  - operation flags: `ensure`, `remove`, `validateOnly`
  - common fields: `offset`, `isTangible`, `physicsMaterial`
  - box-only: `size`
  - circle-only: `radius`
  - geometry note: `offset`, `size`, and `radius` here are screen pixels; `SceneOpsService` converts them to world units internally
**Collider defaults:** apply `3.2 Physics Feasibility and Collider Fit` directly when filling `size`, `radius`, and `offset`: Box `size` defaults to Image `width/height`, Circle `radius` defaults to half the Image diameter, and `offset` defaults to `{x: 0, y: 0}` unless intentionally documented.
**Multiple-collider modeling guidance**
- Apply the default fit, scale, offset, asset, and verification rules from `3.2` before choosing a multi-collider model.
- Prefer `BoxCollider2D` / `CircleCollider2D` for most gameplay.
- Decision priority (rules of thumb):
  - Decide semantics next: does this object need blocking (solid) and/or trigger-only detection?
  - Use multiple colliders only when a single collider cannot represent the required contact behavior (open containers, capsule approximation, composite shapes), or when blocking vs pass-through must coexist on the same moving object.
  - Prefer splitting into helper objects when parts will not share lifecycle/toggles/material/collision-group consistently.
- If a single simple collider is not enough, prefer 2-3 simple colliders (Box/Circle) before Edge/Polygon.
  - T-shape / L-shape obstacles: use 2-3 BoxCollider2D pieces.
  - Capsule-like character: use 1 BoxCollider2D + 2 CircleCollider2D (top/bottom).
- Prefer splitting into helper objects over adding many colliders to one object.
  - Example: basketball rim: create two invisible helper objects (left/right posts), each with a single collider that matches its own object size.
  - Do NOT split when the shape is inherently composite but must behave as one object (e.g. capsule approximation for a character).
- Use multiple colliders on one object only when you must separate gameplay roles (blocking vs pass-through) while keeping it as one object.
  - Example: two small CircleCollider2D on the left/right rim posts, while the center gap stays pass-through.
- Use thin BoxCollider2D strips to build boundaries.
  - Example: pinball table: 4 thin BoxCollider2D around the edges to prevent the ball from escaping.
  - Example: open-top container (cup): left wall + right wall + bottom, each is a thin BoxCollider2D strip.
- Pipe / channel corridors: build the pipe as multiple thin BoxCollider2D wall strips so objects/flow move inside the corridor.
  - Straight pipe: 2 long wall colliders (left/right) are usually enough.
  - L/U-shaped pipe: combine multiple wall segments to form the corridor and the turn; avoid gaps/overlaps at corners and keep inner width consistent.
- EdgeCollider2D / PolygonCollider2D: last resort; prefer adding in the editor and adjusting points manually.
  - The `sceneOps` payload intentionally avoids passing raw point arrays (hard to author reliably).
  - Use Edge/Polygon when you must block along an outline/boundary (terrain border, irregular walls), and keep it limited to a small number of key objects.

**Physics material notes**
- Material identity:
  - Use the same `physicsMaterial.name` across objects that should share one material asset.
  - `{ "preset": "default" }` binds the builtin default physics material; `{ "preset": "none" }` clears the physics material.
- `patch` guidance:
  - Use `patch` only when you need to tune gameplay feel (bounce/grip). Always tune it to match the object's intended real-world material (rubber/glass/wood/metal/etc).
  - Common starting points (copy then tune):
    - Basketball (bouncy, moderate grip): `{ "patch": { "dynamicFriction": 0.5, "staticFriction": 0.6, "restitution": 0.75 } }`
    - Glass (slippery, low bounce): `{ "patch": { "dynamicFriction": 0.08, "staticFriction": 0.1, "restitution": 0.08 } }`
    - Ground / concrete (grippy, low bounce): `{ "patch": { "dynamicFriction": 0.9, "staticFriction": 0.95, "restitution": 0.05 } }`
- If bounce/restitution matters to gameplay, configure a physics material explicitly.
- In Matter2D-based games, do NOT treat material/body internals as gameplay tunables by default.
  - Typical internals to NOT expose: restitution/bounce, friction, damping/air friction, mass, gravity scale, `useGravity`, static/dynamic.
  - Follow `.agent/skills/game2d-planner/SKILL.md` (Exposable Game Parameters) for tunables, and keep physics authoring rules here.

**Collider operations (cookbook):**
- Ensure rigidbody only: `rigidBody: { ensure: true, static: true|false, useGravity: true|false }`
- Remove rigidbody: `rigidBody: { remove: true }`
- Modify collider fields: include only the fields you want to set (`offset/size/radius/isTangible/physicsMaterial`)
- Remove a collider:
  - Preferred: `colliders: [{ type: "...", guid: "...", remove: true }]`
  - Fallback: `colliders: [{ type: "...", index: 0, remove: true }]`

## 5. Runtime Matter2D Guidance
- If runtime gameplay will use `this.matter2d`, install the adapter first with `install(this)` inside the Scene before using Matter2D APIs.
- Read `api/Matter2D.d.ts` first for the public runtime API. Consult `api/Matter2D.ts` only when implementation details are necessary.

**Motion ownership**
- `static=true` means physics is not simulating that body, but it can still collide/overlap with dynamic bodies. Use `gameObject.setPosition(x, y)` to move or reposition it.
- `static=false` means physics owns the transform. Use forces/velocity for continuous motion; when code intentionally sets the physics-owned pose, use `body.setPosition(x, y)` so body state remains authoritative.
- Choose the movement API from the body's current state, not its original authored state. If an object starts static and later becomes dynamic, use `gameObject.setPosition(...)` while it is static; after `body.setStatic(false)`, stop driving it through the GameObject transform and use physics APIs instead.
- Common drag interaction: while dragging, temporarily call `body.setStatic(true)` and update `gameObject.setPosition(x, y)` in screen coordinates; when released, call `body.setStatic(false)` before applying impulse/velocity.
- MUST NOT call `body.setPosition()` as the normal movement model for a `static=true` body. Static bodies controlled by pointer/script (paddles, moving blockers, sensors) MUST be moved with `gameObject.setPosition()`.
- In `resetGame()` and recording-start reset handlers, restore runtime-spawned or pooled static/trigger objects from their stored intended pose after engine physics reset; do not derive the reset pose from the object's current transform. If collision must be correct before the next physics tick, first set the GameObject pose, then perform a one-time body pose sync as reset reconciliation. This one-time sync is not the normal movement model for static bodies.

**RecordStart reset pattern for runtime-cloned static/trigger physics objects**
- Runtime-cloned `static=true` / trigger physics objects may be reset by the engine back to their prefab/template pose when recording starts. Do NOT store only `Sprite[]` / `GameObject[]`; store the intended gameplay pose for each clone.
- During reset, put each clone back at its intended gameplay position, not at its current `sprite.x` / `sprite.y`, because engine physics reset may already have moved it back to the prefab/template pose.

```ts
type SpawnedStatic = { sprite: Sprite; x: number; y: number; angle?: number };

const item: SpawnedStatic = { sprite, x, y };
this.items.push(item);

for (const item of this.items) {
  item.sprite.setVisible(true).setActive(true);
  item.sprite.setPosition(item.x, item.y);
}
```

**Visibility vs collisions**
- Use `gameObject.setVisible(false)` / `setVisible(true)` for reusable object lifecycle. Invisible objects disappear from both rendering and gameplay physics in Matter2D and ArcadePhysics; reset/re-enable them explicitly before reuse.
- If an object should be invisible but still collide/overlap (hidden sensor, invisible wall, helper blocker), do NOT call `setVisible(false)`. Keep it enabled in hierarchy and make its art transparent, or separate the visible art from the collider/sensor object.
- If an object should permanently disappear, call `destroy()` instead.
- Use `Matter2DCollider.setEnabled(false)` only when gameplay explicitly needs a visible object whose collider is temporarily disabled (e.g. invulnerability, one-way pass-through, sensor mode changes). Do not use collider disabling as the default way to hide or remove objects.

**Collision and Overlap**
- There are three main ways to handle collision and overlap:
  - pair-based rules for static/known pairs: `this.matter2d.world.addCollider(...)` / `this.matter2d.world.addOverlap(...)`
  - event-style listeners for existing source object(s) with dynamic or filtered targets: `this.matter2d.world.onCollide(...)` / `this.matter2d.world.onOverlap(...)`
  - object-level sugar for the same event-style listener: `gameObject.onCollide(...)` / `gameObject.onOverlap(...)`
- Use collider/overlap callbacks when gameplay behavior is genuinely driven by physical contact; do not replace requested physical contact with ad-hoc distance checks. For fairness-critical scoring/catch/collect/win judgement, follow **Hit judgement layering** in the Physics2D Plan: use a stable script-side region test as the authoritative decision and treat physics callbacks as feedback or auxiliary signals.
- Collision object identity:
  - In callbacks, use `event.gameObjectA` as the listened/source object and `event.gameObjectB` as the contacted target object.
  - Both object-reference routing and name routing are valid. Use whichever matches the data model you are already maintaining.
  - For reference routing, compare stored objects directly (e.g. `event.gameObjectB === this.player`, `event.gameObjectB === this.goal`) or keep a `Map<GameObject, State>` / `Map<Sprite, State>`.
  - For name routing, use only `gameObject.getName()` as the name source (e.g. `event.gameObjectB?.getName() === 'goal'`) or keep a `Map<string, State>` keyed by `getName()`.
  - Do NOT create ad-hoc `getObjectId(object)` helpers or fallback chains that mix `id`, `name`, `templateId`, `sceneObjectId`, native guid, or raw SceneObject access.
- Collision responses must be role-specific:
  - Shared feedback such as sound, camera shake, or particles may be grouped across several object types.
  - Gameplay-changing responses such as setting velocity, changing direction, applying impulses, damaging state, scoring, consuming pickups, or ending the game MUST run only in the branch for the object role that actually owns that behavior.
  - Do NOT put a special response for one role inside a broad condition that also matches walls, sensors, hazards, pickups, or generic blockers.
- Binding happens at registration for pair-based sides and event-style listened sources; do not pass an empty `Group` / array there. Only event-style `options.targets` is re-resolved per event, so a stable target container may start empty and receive later target objects.

Event-style collision routing pattern:
```ts
// Source object exists; collisionTargets is a stable Group<GameObject> or array field.
// Add later targets to it; do not pass a spread snapshot or replace the container.
this.player.onCollide({
  onStart: (event) => {
    const self = event.gameObjectA;
    const other = event.gameObjectB;
    if (!other) return;

    if (other === this.controller) {
      this.playHitFeedback();
      this.applyControllerBounce(self);
      return;
    }

    if (other === this.wall || other === this.barrier) {
      this.playHitFeedback();
      return;
    }

    const target = this.targetByObject.get(other);
    if (target) {
      this.handleTargetHit(target);
      return;
    }

    const otherName = other.getName();
    if (otherName.startsWith('bonus_')) {
      this.handleNamedBonus(other);
    }
  },
}, {
  targets: this.collisionTargets,
});
```
- `gameObject.onCollide(...)` is only shorthand for `this.matter2d.world.onCollide(gameObject, ...)`; the callback identity rules are the same.

## 6. Runtime Visual Replacement
When only the appearance of an actively simulated object changes:
- keep the same GameObject, rigid body, and colliders so velocity, contacts, and simulation state remain continuous
- change only the visual through the sprite texture API; do not destroy, recreate, or `clone()` the object only to swap its appearance
- if the new appearance changes the perceived size or shape, update the collider through an explicit state transition before resuming dynamic simulation

## 7. Anti-Patterns
The following are forbidden when the design clearly implies real physics:
- faking physically meaningful motion with per-frame teleporting while claiming it is physics-based
- replacing requested physical collision behavior with manual overlap math only
- setting velocity every frame when the design actually needs simulated forces, drift, or rebound
- mixing scripted transform control and active simulation on the same body without an explicit state transition plan

```json
      ]
    }
  }
}
```

### 9.2 BoxCollider2D “Line” Colliders (1px Strips)
Use a thin BoxCollider2D strip when the intended contact surface is effectively 1D (stem/rod/wire/string/needle/arrow shaft).
- Example: when the player inserts a flower into a vase/bottle mouth, the flower head is visually large but should not block insertion. Keep the stem as the only tangible "guide" collider, and remove the flower-head collider or set it to non-tangible.
- Thickness: the short side CAN be as thin as 1px (`width: 1` or `height: 1`) to approximate a line. Use 2-4px only if tunneling/jitter happens.
- Alignment: keep the strip aligned with the intended interaction path; do not inflate it to match decorative volume if that hurts playability.
- More examples: fishing line / hook shaft; key blade in a keyhole; thread-through straw/tube; sword/knife blade as a thin hit-strip while the hilt stays non-colliding; thin wire/rail the player must follow.

Thin-strip multi-collider example. This creates a new object, so it uses `op: "add"`:

```json

  "y": 400,

  "textureKey": "cup",

      "rigidBody": { "ensure": true, "static": true, "useGravity": false },

          "type": "BoxCollider2D",
          "index": 0,
          "ensure": true,
```
