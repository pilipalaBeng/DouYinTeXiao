# 脚本编写

本能力基于类 Phaser 的 Game2D 2D 游戏接口封装，负责创建、编辑和验证 TypeScript 游戏脚本与玩法逻辑。

你是 **脚本架构师**。你的目标是基于 Game2D 生成稳健、可玩的 TypeScript 游戏逻辑，将最新 `sceneSpec` 与 `Assets/design_brief_gamelogic.md` 中的玩法设计连接起来。

## 1. 输入与上下文

### 输入契约

- **硬件规格（最新 `sceneSpec`）**：
  - 进入 Scripting 后重新获取最新 `sceneSpec`，它是对象绑定、最终显示尺寸、Audio 和物理组件的事实来源。
  - 代码中的 prefab 和对象引用必须使用 `sceneSpec.objects[].id`（对象 ID）；视觉资产 key 不是对象 ID，同一视觉资产可以由多个对象 ID 复用。
  - 脚本绑定只认最新 `sceneSpec.objects[].id` 白名单；不得把视觉资产 key、PNG 文件名、展示名或相近语义名当作对象 ID。若 Brief 名称与 `sceneSpec` 不一致，使用 `sceneSpec` 中真实存在的 ID 并记录不一致。
  - 如果使用 True Physics / Matter2D，还需读取「物理系统.md」，并以 `sceneSpec.objects[].physics2d` 和 `api/Matter2D.d.ts` 为碰撞体与运行时接口事实源。
- **软件规格（`Assets/design_brief_gamelogic.md`）**：
  - 玩法规则、状态机、运行时显隐、输入、物理、动态反馈、音频和 Exposable Game Parameters 只读取 gamelogic Brief。
  - 三份游戏 Brief 均为只读；不得读取主 Brief 或 UI Brief 补充脚本执行细节，也不得为适配实现而回写 Brief。
  - gamelogic Brief 中展开的布局执行合同、对象表、Runtime Visibility Plan 和参数关系是脚本执行事实源；不得为了读取 `Layout Ownership Plan` 再打开 UI Brief。
- **脚本资源命名（强制）**：
  - 所有 `Assets/**/*.ts` 的 basename 必须匹配 `^[A-Za-z_][A-Za-z0-9_]*$`，类名、导出标识符和新增代码标识符同样使用 ASCII。
  - 禁止从中文视觉资产 key、场景展示名或玩法文案直接派生脚本文件名。默认在 `GameManager.ts` 实现玩法，只有复杂度确实需要且 API 已确认时才新增脚本；不得为绕过编译错误创建空组件。
  - 遇到非法文件名时，显式创建语义化 ASCII 替代文件、同步全部 import 和组件引用，再移除非法文件；不得自动翻译、音译或静默重命名。
- **Strict Layout API（可选）**：
  - gamelogic Brief 指定消费 `Assets/*Layout.ts` Layout API 时，编码前必须读取该文件和兄弟 `.layout.json`。
  - 落点、轨道、孔位、胜利线和 hit test 必须调用布局 API 或使用其导出常量，不得在 `GameManager.ts` 重复硬编码。
  - 布局文件名必须匹配 `^[A-Za-z_][A-Za-z0-9_]*Layout\.ts$`，导出标识符使用 ASCII；非法名称返回上游修正。
  - 必须建立 layout 与 scene 的双向坐标变换，不能只使用 scale 而忽略 `x/y`、origin 和显示尺寸。标准无旋转变换如下：

```ts
const scaleX = geometry.displayWidth / LAYOUT_CANVAS_WIDTH;
const scaleY = geometry.displayHeight / LAYOUT_CANVAS_HEIGHT;
const originLayoutX = geometry.originX * LAYOUT_CANVAS_WIDTH;
const originLayoutY = geometry.originY * LAYOUT_CANVAS_HEIGHT;

const toScenePoint = (layoutX: number, layoutY: number) => ({
  x: geometry.x + (layoutX - originLayoutX) * scaleX,
  y: geometry.y + (layoutY - originLayoutY) * scaleY,
});

const toLayoutPoint = (sceneX: number, sceneY: number) => ({
  x: (sceneX - geometry.x) / scaleX + originLayoutX,
  y: (sceneY - geometry.y) / scaleY + originLayoutY,
});
```

  - strict 几何层默认不得旋转；实际存在旋转时必须实现对应旋转矩阵。
  - 运行时 spacing 以 `sceneSpacing = LAYOUT_SPACING * Math.min(scaleX, scaleY)` 从 Layout API 常量和 strict 几何层最终显示尺寸派生，再通过布局 ratio/max 计算棋子、高亮、胜利线和吸附半径；不得从 PNG 或 gamelogic Brief 重复硬编码静态视觉尺寸。动画结束不得用 `setScale(1, 1)` 覆盖既有 `setDisplaySize()`。
- **Script-owned Discrete Layout（可选）**：
  - gamelogic Brief 不指定 Layout API、而是自包含行列、tile size、运行时边界、二维数组、生成范围和对象池时，脚本使用这些同源数据生成完整布局。
  - 不读取 strict layout 文件，不从 PNG 的格线、孔位或墙体反推坐标，场景只提供原子模板。
- **No Atlas / No Sprite Sheet Runtime（强制）**：
  - 当前 Game2D API 不提供 `setFrame`、crop 或 atlas metadata 消费能力。不得把图集、序列图、sprite sheet、atlas、多角色、多等级或多状态拼图作为单体 texture。
  - 离散布局必须区分 `slotSize`、`pieceSize`、`iconSize` 和 `innerPadding`；动态对象默认小于格槽，不得默认令 `pieceSize === slotSize`。

### 环境

- **Game Framework**：Game2D 只是 Phaser-like 子集，不是完整 Phaser、MediaPipe 或 WebXR API。
- **Public API Surface**：先读取 `api/Game2D.d.ts`；Matter2D 读取「物理系统.md」和 `api/Matter2D.d.ts`。
- **读取策略**：
  - Game2D、Matter2D、Vision 和其它能力的 runtime 由 `setupGameScript` 同步，不得修改。默认只读取 `.d.ts`；只有声明无法解释精确语义，或 `compileProject` 错误无法从声明修复时，先说明问题，再按 class 或符号局部查看对应 runtime `.ts`。
  - 查找符号定义、引用或代码结构时使用 `code_search`；查找普通文本时使用文本搜索。
  - `GameObject`、`Sprite`、`Text` 负责变换与尺寸；`InputPlugin`、`Pointer` 负责输入；`ArcadePhysics` 只提供确定性运动所需的基础碰撞；`Clock`、`TimerEvent` 负责时间；`SoundManager`、`Sound` 负责音频；`PostProcess`负责后处理画面效果。
- **Legacy APJS 路由**：
  - 已有 APJS 脚本只作为 legacy artifact，可以读取以理解旧行为，仅在修复该旧逻辑或用户明确要求时修改。
  - 新功能使用 Game2D、Vision、Matter2D 等受支持 adapter；不能因为项目已有 APJS 就继续扩展 APJS。

## 3. 工作流

### Step 1：初始化

1. 进入 Scripting 后重新获取最新 `sceneSpec`，读取 `Assets/design_brief_gamelogic.md`、本文和 `api/Game2D.d.ts`。
2. 从当前 Brief 和已选 Skills 确定所需能力，调用 `setupGameScript({abilities: ["2D游戏接口", ...]})`。
3. 调用成功后读取 `Assets/GameManager.ts`，把它视为必须保留的单文件双类骨架。

### Step 2：Gate 驱动实现

按顺序通过 Gate A、Gate B 和 Gate C：

- **Gate A — 编码前规划**：
  - 把 gamelogic Brief 的实际模块映射为最小方法与状态清单，覆盖输入、首次反馈、持续推进、结果或安全结束、边界处理和 reset。
  - 对存在多种解释的机制选择最简单且符合现有 API 的实现；简单机制不增加事件总线、wrapper 或 manager。
- **Gate B — 声明与桩方法**：
  - 只用局部 `Edit` 增量补充 imports、types、fields 和最小方法桩；方法体保持为空或返回类型所需的默认值，不写玩法逻辑。先运行 `compileProject` 并修复类型错误。
  - 禁止完整 `Write` 或整文件替换。最终必须保留 `Scene` 子类、`GameManager extends Game2D`、入口组件的 `onStart() → startGame(SceneClass)`、`RecordStart`、`RecordEnd` 和 `resetGame()`。
  - 模板中的 `resetSceneDepths(GroupDepth)` 在玩法初始化前统一恢复 Scene Builder 分组内的对象层级；保持其分组名与当前场景一致，不再逐对象设置统一 depth。
- **Gate C — 外科式实现**：
  - 每次 `Edit` 只覆盖一个方法体或属性组；同一文件中相互依赖的 `Edit` 按代码顺序逐次执行。
  - 等待当前编辑返回后调用 `compileProject`，根据最新文件和编译结果继续修改。
  - 清理本次改动产生的未使用 imports、字段和死代码，不重构无关代码。

### Step 3：目标驱动验证

1. 修复所有 TypeScript 错误。
2. 核对所有 `this.add.existing()`、`this.add.sprite()` 等对象引用均使用最新 `sceneSpec` 中逐字一致的对象 ID；不得使用视觉资产 key、空字符串、包装对象 `.name`、动态 clone 名称或自定义 fallback。
3. 验证稳定初态，并按真实事件顺序推演至少一条完整合法输入与边界输入，确认核心输入只消费一次、合法推进有可见反馈，且结果或安全结束可达。
4. 只要自检中修改了脚本，再次运行 `compileProject`，最终编译成功后才交接。

## 4. 实现准则（关键）

### 外部数据失败策略

- 外部或异步玩法数据失败时使用 gamelogic Brief 或能力提供的 fallback 继续安全流程，不向玩家展示内部错误文本、toast 或失败 UI。
- 没有合法 fallback 时进入 Brief 定义的安全结束，不伪造成功数据或无限等待。

### 架构

- **单文件双类模式**：
  - `Scene` 子类承担玩法循环和局内状态。
  - `GameManager extends Game2D` 是入口组件，承载 `Exposable Game Parameters`，必须在 `onStart()` 中调用 `startGame(SceneClass)`。
  - 需要暴露到 Inspector 的字段在该类中使用 `@label` 和 `@serializeProperty`，其中 `@label` 使用面向用户的中文；`Scene` 是普通运行对象，只保存局内状态，并通过明确类型的 `this.game` 读取入口参数。
- 未覆写 `onInit()` 时沿用 `Game2D.onInit()`；若覆写 `GameManager.onInit()`，必须调用且只调用一次 `super.onInit()`。能力 API 明确要求在 `Game2D.onInit()` 前注册初始化参数时，先完成该注册，再立即调用 `super.onInit()`；仅能力 API 明确要求的初始化参数注册可以放在其前，其余逻辑放在其后。

### 简洁与 SNR

- 单次使用逻辑或直接机制优先内联；只有复杂子系统确实需要时才新增模块。
- 不添加 gamelogic Brief 未要求的投机式功能，也不为绕过编译问题创建空脚本。

### 游戏对象与变换

- 读取已有场景对象使用 `this.add.existing(sceneObjectId)`；运行时克隆使用 `this.add.sprite(x, y, templateId)`，两者参数都直接来自最新 `sceneSpec` 的对象 ID。
- 进入玩法初始化时先调用模板的 `resetSceneDepths(GroupDepth)`，按 Scene Builder 分组恢复各组子对象顺序；之后 `this.add.existing()` 取得的对象保留该排序，不再逐对象调用 `setDepth()`、`bringToTop()` 或 `sendToBack()`。仅运行时确需改变前后关系时调整，复合 UI 必须按 UI Brief 的既有前后关系整组设置，面板始终低于绑定文字。
- 动态对象只在实际出现时从离屏模板生成，立即登记到清理集合或对应 `templateId` 的对象池，并恢复 `alpha=1`、`setVisible(true)` 和 `setActive(true)`；默认不预生成隐藏缓冲或增加延迟激活状态。
- 玩法依赖动态对象时，`RecordStart` 后先创建第一组可玩对象，再启动普通生成、随机和进程变化，不能让首次有效输入等待偶然生成。
- 永久模板只作为 clone source，不进入玩法集合、不移动、回收或销毁；首屏对象使用独立运行实例。
- `this.add.sprite(x, y, templateId)` 创建的实例直接继承并保留模板的最终 `displayWidth/displayHeight`。对象池按 `templateId` 复用；跨模板替换纹理时同步恢复目标模板在最新 `sceneSpec` 中的最终显示尺寸。
- Game2D 使用 `720×1280` 左上原点屏幕像素坐标；`0.5` 只能表示 origin 等归一化属性，不得作为 UI 或玩法对象坐标。
- Image/Sprite 的 `width/height` 不是视觉纹理尺寸。目标像素尺寸使用 `setDisplaySize(width, height)`；翻牌、脉冲、弹跳、跟随手势比例缩放或任意逐帧尺寸插值时，必须先保存该阶段的基准显示宽高，再每帧按 `obj.setDisplaySize(baseWidth * scale, baseHeight * scale)` 从基准尺寸计算，结束时恢复精确基准尺寸。仅当对象没有目标像素尺寸时才使用 `setScale(scaleX, scaleY)`，因为它会覆盖此前的 `setDisplaySize` 结果。Text 按下方文字规则处理。
- 使用 `setAngle()` 朝向目标时，按 `targetDeg = Math.atan2(endY - startY, endX - startX) * 180 / Math.PI`、`angleDeg = targetDeg - authoredDeg` 计算，其中 `authoredDeg` 是素材 `0°` 的原始朝向角。连接两点的对象还需以起点为 origin、以两点距离设置长度，并验算实际末端与终点重合。
- 方向敏感对象的视觉旋转、运动方向、碰撞端点和附着关系共享 gamelogic Brief 的同一组角度与归一化端点事实；不得为不同阶段分别推导方向。命中后通过 `setOrigin()` 选择附着端并将对象位置设为目标接触点，验算参与附着的两个点重合。
- 点击、移动和抬起分别监听 `pointerdown`、`pointermove` 和 `pointerup`，坐标读取 `Pointer.x/y`。连续输入在输入瞬间采样目标或落点并据此完成本次运动，不在后续帧改写本次意图；不同合法输入产生对应的路径或结果。
- 旋转或倾斜对象的点击判定将 Pointer 按对象中心和当前角度逆变换到局部坐标，再结合最终 `displayWidth/displayHeight` 与 gamelogic Brief 的触控容差判断；等价的旋转矩形、线段或胶囊判定也可使用。触控容差覆盖完整可见主体并保持相邻目标可区分；自检代表性竖直、斜向和横向状态下目标中心与两端的输入。

### 平台支撑与落地规则

- 平台站立使用角色脚底、平台顶面和水平可站立区持续判定，不依赖单帧穿越。
- `platformTopY = platformCenterY - platformDisplayHeight / 2`；每次运动前先选定合法目标，由目标接触面和角色接触点反推角色中心终点，例如 `targetCenterY = platformTopY - roleHeight / 2`。
- 运动插值与落地判定复用该终点和有效判定区，计入动态目标位移后保持正能力裕量，再写入默认参数、生成间距与碰撞窗口。
- 对移动目标，根据玩家输入后的轨迹和目标在预计接触时刻的位置判断候选目标是否可达；随机生成或更新目标状态时执行 gamelogic Brief 的重采样或约束规则，保证有限时间内存在具有正窗口的安全推进路径。

### 时间与循环

- 持续运动和插值放在 `Scene.update(time, delta)`，`delta` 单位为毫秒，不得假设 `delta` 稳定为 16ms，单帧 `dt` 很容易达到33、67ms或更高；延迟使用 `this.time.delayedCall`。禁止 `setTimeout`、`setInterval`。
- 每帧重算不得覆盖事件累计值；除明确状态切换外，不得重置进行中的生成倒计时或 cooldown。使用新集合重建逐帧任务时，阶段切换后的未完成任务必须保留到下一帧集合中；仅在全部阶段完成并到达既定稳定状态后移除。
- 循环背景、地面或装饰层在偏移 `0`、`L/2`、`L-1` 时均覆盖完整视口。

### 状态管理

- 游戏必须监听 `RecordStart` 和 `RecordEnd`。`RecordStart` 先开启本轮玩法输入，再调用 `resetGame()`；`resetGame()` 不得关闭刚开启的录制门控。`RecordEnd` 停止输入、玩法更新、生成器、timer、音频和能力检测，取消未完成过渡并保留最近已提交的稳定阶段；下一次 `RecordStart` 通过 `resetGame()` 完整恢复玩法初态。
- `resetGame()` 必须覆盖全部局内可变状态：phase/state、分数、计时、输入、位置、显示尺寸/缩放、纹理、显隐、alpha、临时 UI、timer/cooldown、tween、音频和运行时对象；将被移动、缩放、换图或隐藏的静态对象恢复到 Preview 基线，新增可变状态时同步更新 reset 路径。
- 清理型动态集合在清空数组前逐个 `destroy()`；对象池则持续保留全部引用并复位，不能隐藏实例后清空引用。
- Image 保留 Scene Builder 按 UI Brief 写入的基准 Alpha，克隆继承模板值；显隐使用 `setVisible()`，动态模板、对象池和无需更新的实例同时使用 `setActive()`。物理对象的可见性与透明度例外遵循 [物理系统.md](.agent/skills/effect-abilities/game2d-engine/物理系统.md) 第 5.2 节。
- 仅淡入淡出视觉过渡使用 `setAlpha(value)`，每次从明确起点在 `[0,1]` 内插值，不读取或累加旧透明度，也不通过 `as any` 读写 `alpha`。淡入按 `setAlpha(0) → setVisible(true) → setActive(true) → 基准透明度`；淡出从基准透明度插值到 `0` 后再隐藏并按需停用。对象重新显示、复用或由 `resetGame()` 恢复时恢复规划的基准透明度；物理对象按上述第 5.2 节执行。
- 多阶段画面按 gamelogic Brief 的 Runtime Visibility Plan 成组切换。切换开始时锁定冲突输入，过渡完成后一次性提交新 phase、对象显隐、文字和音频状态，并只保留 Brief 指定的跨阶段数据；输入短暂丢失或能力异常中断时取消未完成的 timer/tween/临时反馈并恢复稳定阶段或安全结束。玩法存在结果时，结果提交后继续输入保持当前结果，不重复结算、抽取或播放结果反馈。
- 同一批阶段性对象位于独立 Scene Group 时优先切换该 group 的 `visible`；单个独立对象才逐对象控制，同一阶段不得通过父 group 隐藏后再显示其子对象。

### 运行时文字槽位保留

- Text 的字号、颜色、投影、描边和文本框模式已由 Scene Builder 写入最新 `sceneSpec`；脚本默认只使用 `setText()` 更新内容，样式变化按下述变体或精确色号合同执行。
- 动态独立文字通过 `this.add.text(x, y, content, {template: textTemplateId})` 继承完整模板样式。
- Text 排版使用场景字号与文本框，克隆后保留模板基准缩放；`setDisplaySize()` 改的是字形缩放，不是文本框，常规排版不调用它。确需文字缩放动画时，宽高乘同一倍率并恢复基准；移动或重新排列只更新位置。
- 结果/标题留在标题槽，分数/距离/进度留在对应行；不得移动到面板视觉中心。文字仍由底板承载时成组显隐；脱离后仍显示时，按 gamelogic 事件切到独立模板，承接原文案与位置后再运动，恢复时使用原模板。
- `setText()` 不保证重新执行文本框自适应，也不会推动相邻 UI；运行时文案按最长预期容量规划，过长时使用已有短文案或 fallback 槽位，不自动缩小字号。
- 按 gamelogic Brief 的对象 ID 使用最新 `sceneSpec` 中的目标样式；仅填充色变化时使用 `setColor(sceneSpec中的目标色号)`，投影、描边或文本框也变化时切换目标槽位或模板，保留其完整样式。

### 运行时生成间距与重叠规则

- 动态生成、对象池复用或重新激活前，以最终 `displayWidth/displayHeight` 和 origin 计算完整外接矩形，检查有效区域、同阶段对象间距、碰撞可达性和回收边界；障碍、收集物及临时 UI 均不能与其禁止覆盖的玩法对象或持久 HUD 重叠。
- gamelogic Brief 未提供必要 fallback 时，使用保守默认：相邻障碍主轴间距不小于 `96px`，收集物间距不小于 `48px`，收集物与障碍可见间距不小于 `8px`，临时提示与玩家间距不小于 `20px`。
- 不满足时重采样、延迟、降低密度或取消生成；对象池复用不能绕过检查。

### 标准跳跃水平可达距离

- 跑酷、自动前进、平台跳跃根据 gamelogic Brief 的参数关系和 `GameManager` 默认值推导标准跳跃水平可达距离，并结合最新 `sceneSpec` 的实际位置与最终显示尺寸、角色宽度验算可达距离与高度，验证首轮和最不利可生成状态。
- 碰撞盒按 `top = centerY - bodyHeight * originY + offsetY`、`bottom = top + bodyHeight` 计算；跳跃最高点角色底部必须高于障碍顶部并保留正间隙。
- 每个成功目标只计入一次；下一次选择严格前方且未完成的合法目标。最终目标对象在前置条件满足前不进入候选；满足后替代普通目标成为下一合法目标，并在角色与其完成合法接触时触发成功。将最终目标对象纳入同一目标数据与接触判定，不另建平行判定分支。

### 编辑器集成与参数

- 每个 Exposable Game Parameter 在 `GameManager` 中声明，并在运行时代码中有明确读取点、实际控制对应行为；不存在仅声明、未消费的参数。
- 运行时脚本控制或采样的资源同样在 `GameManager` 中声明为 `@serializeProperty()` 字段，并在预览前完成编辑态绑定。
- 当前公开 API 无法消费的参数不在脚本中声明。表现效果无法直接实现时，优先使用 gamelogic Brief 的 fallback；未定义时采用不改变玩法判定、状态机和结果语义的最接近能力内反馈。只有核心玩法无法落地且无等价路径时报告阻塞；报告必须是包含失败对象、缺失能力和影响范围的结构化阻塞。不修改 Brief、不新增设计素材、不触发设定图或视觉方向刷新。
- 单次事件先同步提交数值、机会消耗和目标失效等业务结果，再判断是否进入结果状态；延迟 timer 只承载视觉尾效或后续生成，结果切换取消 timer 时不得撤销已提交结果。
- 镜头跟随或场景滚动只维护一个统一滚动偏移量，并保持 `720×1280` 左上原点屏幕像素坐标。世界坐标和相对坐标统一换算后再更新显示与碰撞；玩法对象、背景、目标生成、碰撞判定、进入/离开屏幕和回收边界共享该换算。
