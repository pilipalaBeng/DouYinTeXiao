# 游戏 Preview 视觉验证
仅当 [preview-verification/SKILL.md](../SKILL.md) 路由判定为“完整游戏”且用户明确要求视觉验证时，在开始截图前阅读本规则文档。

你是 **Preview 视觉质量审查专家**。本规则文档只负责视觉质量审查，不负责通用 Preview 操作或独立的运行时行为验证。

- 通过分阶段截图检查文案与教程可读性、主玩法资源语义、控件一致性、布局层级和反馈质量，判断最终画面是否精致、统一并符合设计目标；
- 只修复资产或场景层的视觉载体缺陷；
- 脚本、玩法或状态机负责的缺陷只报告可见现象与疑似归属，不在 VQR 中修改；
- 用户只要求截图、点击、拖动、录制或行为验证时，改用 [preview-tool](../effect-abilities/preview-tool/SKILL.md)。

## Visual Quality Review Hard Gates

Before starting Visual Quality Review, apply these gates as higher-priority rules than any screenshot interpretation:

- **Brief routing**: The active visual brief is `Assets/design_brief_ui.md` and the active gameplay brief is `Assets/design_brief_gamelogic.md`; use `Assets/design_brief.md` only as the parent game brief.
- **Do not evaluate real-person occlusion**: Game elements overlapping, covering, or visually competing with the camera person's face, body, or background subject is outside Visual Quality Review. Do not treat face visibility, "遮脸", "遮挡人物", "面部保护", "face-zone", "face-overlap", or real-person background cleanliness as a defect, unless the game mechanic explicitly depends on face/gesture tracking.
- **Do not repair for face avoidance**: Do not move, shrink, hide, delete, delay, or de-scope game-owned elements merely to avoid a real person's face/body/background subject. In particular, do not shrink the active playfield, move rule/tutorial text away from its game-appropriate position, weaken HUD/readability, or change gameplay lanes because of face-area overlap.
- **Do not rewrite game rules or briefs from VQR**: Treat `Assets/design_brief.md`, `Assets/design_brief_ui.md`, and `Assets/design_brief_gamelogic.md` as read-only sources of truth. Visual Quality Review must not modify them, user-facing rule text, tutorial semantics, gameplay area targets, win/loss rules, scoring, controls, or core mechanics to justify a visual fix.
- **Do not modify game logic from VQR**: VQR fixes must not edit gameplay, scoring, win/loss, control mapping, input handling, ranking dependency, settlement progression, state-machine, spawn, timer, difficulty, or reset logic in `Assets/GameManager.ts` or equivalent runtime scripts. If a screenshot defect appears to be script-owned, report the suspected owner and the visible symptom, but do not patch script logic as part of VQR unless the user explicitly asks for a separate script/gameplay fix.
- **Do not remove planned game elements**: VQR fixes must preserve game-owned elements that are required by the active gameplay brief or already implemented, including gameplay objects, HUD, controls, tutorial UI, feedback effects, settlement panels, and ranking lists. If an element creates clutter, hierarchy conflict, wrong-phase visibility, overlap, or poor readability, fix visual placement, size, style, layer/depth, opacity, grouping, contrast, density, or scene-level appearance while preserving the element. Do not delete, hide forever, de-scope, remove dependencies, disable built-in ranking, or rewrite the brief to remove the element as a visual fix.
- **Preserve gameplay readability first**: For movement/action games, keep or expand the intended playable area and interaction clarity. If there is tension between avoiding a camera face and keeping the game playable, prioritize the game rules, readable controls, and genre-appropriate playfield.
- **Text and tutorial readability must be graded first**: VQR output must start its mandatory status list with `文案可读性（Text readability）` and `教程/规则提示可读性（Tutorial / rule prompt readability）` before asset or control checks. Grade HUD labels, hints, tutorial/rule copy, result text, ranking text, score labels, combo labels, and any other player-facing text from the captured screenshots at preview size. Do not pass VQR merely because text objects or backing panels exist. Judge readability against the worst background segment behind the text, including pale/bright camera backgrounds, hair/face edges, bright panels, busy texture transitions, and low-contrast AR backgrounds. If any visible/applicable text-readability status is omitted from the final answer or `task_done` summary, the Visual Quality Review is incomplete and must not be reported as passed.
- **Primary gameplay assets must match their intended semantic role**: The main player/subject, body parts or sub-parts when present, collectibles, enemies, hazards, projectiles, and key props must be visually recognizable as the entities and gameplay roles described by the active gameplay brief. Do not pass VQR just because an image exists, is colorful, or is bound in the scene. Judge the visible screenshot semantics generically: (1) the player/subject identity matches the brief, (2) the player/subject role is distinguishable from other gameplay roles, (3) direction/action affordance is readable when the gameplay depends on facing, aiming, movement, attack, or steering direction, and (4) collectibles, enemies, hazards, projectiles, and props are visually separated by shape language, silhouette, color role, scale, iconography, or graphic-semantic family. Genre-specific traits are examples, not universal requirements: a plane game may only need a readable plane body and flight/attack direction; a snake game may need head/body role separation and body continuity; a puzzle game may not need facing direction. If the primary subject reads as another role, a generic sticker/decorative object, or shares the same graphic-semantic family as targets/hazards so gameplay roles are unclear, mark VQR as FAIL and route the fix to asset regeneration plus scene rebinding.
- **Control groups must be visually coherent**: Semantically paired or symmetric controls (left/right, up/down, previous/next, accept/cancel, primary/secondary actions, D-pad directions) must read as one consistent UI group. Do not pass VQR merely because controls exist, are clickable, or are safely placed. Check that the group uses consistent style, size, backing, stroke/shadow, icon language, label treatment, color weight, spacing, mirrored orientation rules where applicable, and graphic-semantic family. Icons in one control group must express actions with the same graphic grammar; do not pair a direct directional symbol with a return/refresh/loop/confirm/decorative symbol, or mix symbols whose visual metaphor implies different operation types.
- **Mandatory status output**: VQR output must explicitly list PASS / FAIL / NOT_VISIBLE or NOT_REACHED for mandatory gates. The first mandatory statuses must be `文案可读性（Text readability）` and `教程/规则提示可读性（Tutorial / rule prompt readability）`, followed by `Primary gameplay asset semantic match` and `Control group visual consistency / affordance`. `Primary gameplay asset semantic match` is incomplete if it is only reported as one generic PASS/FAIL line: it must include the four role-based sub-statuses `Player/subject identity`, `Player/subject role distinguishability`, `Direction/action affordance if gameplay-dependent`, and `Core role separation from collectibles/enemies/hazards/projectiles/props`, using `NOT_APPLICABLE` only for direction/action when the gameplay truly does not depend on direction. If any visible/applicable text-readability, tutorial/rule prompt readability, or primary-asset sub-status is omitted, the Visual Quality Review is incomplete and must not be reported as passed. If visible paired controls exist but the output does not name and grade that control group, the Visual Quality Review is incomplete and must not be reported as passed.
- **Reload after visual-carrier fixes**: After fixing screenshot-observed defects that change icons, image/resource bindings, scene object references, prefab/object replacement, material/texture carriers, or runtime-created visual carriers, recompile when needed, then reload the effect package/scene before screenshot re-review. In this workflow, use a standalone `previewTool` call whose `commands` array contains only `reset_preview` as the reload gate before `start_preview_record` and new screenshots. Do not combine `reset_preview` with `start_preview_record`, `screenshot`, `wait`, `touch`, `drag`, `pause_preview`, `resume_preview`, or any other command in the same `previewTool` call. Do not judge the fix from a stale preview session.

## 视觉质量审查流程

This mode answers "does it look good and feel well-crafted?". Read the active visual brief for visual assets, layout, text, controls and UI lifecycle, and the active gameplay brief for gameplay roles, pacing and state transitions; then route defects back to the layer that owns them.

**Core principle: visual completeness is not the same as asset completeness.** Visual quality must be judged from what the player actually sees on screen, not from whether formal PNG assets exist. Visual carriers may include PNG/Image assets, runtime Text, emoji characters, procedural shapes/effects, particles, tweens, screen shake, UI containers, spacing, color rhythm, hierarchy, and motion. Text/emoji/procedural visuals are first-class visual outputs, not fallback debugging aids.

**No-image / hybrid rule**: "No PNG assets" MUST NOT be treated as a reason to skip or downgrade visual quality review. If the game uses Text, emoji, procedural effects, or a hybrid of carriers as its primary visual language, review it with the same product-level standards. Temporary placeholders also must be visually intentional: placeholder does not mean unstyled, inconsistent, or debug-like.

**When to run**: MANDATORY for a brand new game or a large overhaul (run it once after compilation succeeds). For small or local edits, skip Visual Quality Review unless the user explicitly asks for effect / visual verification; a visual-related change alone is not enough to trigger this mode. A request that only asks to capture the current preview image (for example, "截取预览图片") is **not** an effect / visual verification request; use [preview-tool](../effect-abilities/preview-tool/SKILL.md) instead.

**Game2D engine handoff contract**: For a brand new game or a large overhaul, after compilation succeeds, the script workflow MUST run one round of this `preview-verification` **Visual Quality Review** mode: capture the initial and mid-gameplay stages, try to capture the settlement/result stage through a short controllable path when possible, then self-assess each captured screenshot against the final player-visible screen, not only asset completeness. Do not run a separate runtime-interaction verification pass before VQR. The VQR reset gate must be a standalone `previewTool` call whose `commands` array contains exactly one command, `reset_preview`; never merge `reset_preview` with `start_preview_record`, screenshots, waits, interactions, pause/resume, logs, or any later capture command in the same `previewTool` call. Do not block the whole review only because settlement/result capture is unreachable; report it as a verification gap and do not claim that stage was verified. Treat runtime-created Text, emoji characters, procedural shapes/effects, particles, tweens, screen shake, UI containers, spacing, color rhythm, and PNG/Image assets as first-class visual carriers. The checklist must cover composition, visual hierarchy, style consistency, ranking-list / overlay style integration, ranking-list aspect ratio / row density, settlement/ranking information hierarchy, contrast against the camera feed, HUD not crushing the play area, stale phase-based UI, leaked hidden answers, feedback/juice quality, placeholder quality, asset completeness when PNG is part of the design, primary gameplay asset semantic match against the active gameplay brief, readability, independently readable tutorial/rule prompts, tutorial text contrast against the worst background segment behind the text, and visual consistency / affordance of semantically paired control groups. Primary gameplay asset semantic match is a generic role-based gate, not a snake- or character-specific rule: explicitly grade `主控/主体身份匹配（Player/subject identity）`, `主控/主体职责可区分（Player/subject role distinguishability）`, `方向/动作可读性（Direction/action affordance if gameplay-dependent）`, and `核心角色分离度（Core role separation from collectibles/enemies/hazards/projectiles/props）`; use `不适用（NOT_APPLICABLE）` for direction/action when the gameplay does not depend on direction. VQR review results should output Chinese display names first and keep English rule keys in parentheses when useful for trace/search compatibility. A single generic line such as `主玩法资源语义匹配（Primary gameplay asset semantic match）: PASS` is not sufficient; if any visible/applicable primary-asset sub-status is omitted from the VQR result, final answer, or `task_done` summary, the VQR is incomplete and must not be reported as passed. The VQR result must explicitly output PASS / FAIL / NOT_VISIBLE or NOT_REACHED for mandatory gates, including `主玩法资源语义匹配（Primary gameplay asset semantic match）` and `控件组视觉一致性 / 可供性（Control group visual consistency / affordance）`; this status must name the paired controls being checked (for example `左右方向按钮（left/right direction buttons）`), and VQR is incomplete if visible paired controls exist but this status is omitted. Do not evaluate face-zone, face-overlap, real-person occlusion, or whether game elements cover the camera person's face/body as part of Visual Quality Review; judge only whether game-owned elements are reasonable for the game rules, genre, interaction path, readability, feedback, and phase hierarchy. VQR must not modify gameplay, scoring, win/loss, control mapping, input handling, ranking dependency, settlement progression, state-machine, spawn, timer, difficulty, reset logic, or the active gameplay brief; if a screenshot-observed defect appears to require `Assets/GameManager.ts` or equivalent runtime-script changes, report the visible symptom and suspected script owner as a follow-up task instead of patching it during VQR. If a screenshot-observed defect is found, fix only asset/scene visual-carrier issues and re-review: send asset-semantic defects and control-icon graphic-semantic family mismatches to the asset generation layer plus scene rebinding, and send layout / contrast / backing / placement / carrier-polish / ranking style / overlay density / tutorial readability / control-group visual-style defects to the scene layer via `sceneOps`. Do not fix visual defects by deleting planned game elements or changing game logic; preserve planned gameplay, HUD, ranking, settlement, tutorial, feedback, hazard, collectible, decorative, and control elements; adjust position, size, layer/depth, opacity/style weight, grouping, density, visual hierarchy, or regenerate/rebind semantically correct assets instead. Iterate at most **2 rounds**; if defects remain, hand off honestly and report the residual issues.

**Screenshot defect debt contract**: This section is the single source of truth for screenshot defect debt; do not duplicate or reinterpret it in `game2d-engine`. If a mandatory defect was discovered from preview screenshots (including visual layout defects, primary gameplay asset semantic mismatch, control-icon graphic-semantic family mismatch, ranking-list or overlay style conflicts, ranking-list aspect ratio or row-density defects, confusing information hierarchy in settlement/ranking/help overlay phases, unreadable or squeezed tutorial/rule prompts, inconsistent visual style or affordance in a semantically paired control group, visible pacing defects, visible stale UI, visible settlement timing issues, visible gameplay-effect issues, weak feedback, poor genre readability, or difficulty/density problems that prevent the intended experience from appearing), any asset/scene visual-carrier fix creates a screenshot verification debt. VQR must not create or pay this debt by modifying gameplay logic, ranking dependencies, settlement progression, scoring, win/loss, controls, input mapping, reset logic, or the active gameplay brief; script-owned defects should be reported as residual issues or follow-up tasks. Face-zone, face-overlap, real-person occlusion, and game elements covering the camera person's face/body are out of scope for Visual Quality Review and do not create screenshot debt. Missing settlement/result screenshots are verification gaps, not automatic visual defects. Compile checks, type errors, backend/toolchain issues, log checks, reloads, or script-tail inspection are allowed as intermediate steps, but they DO NOT close this debt. Before handoff, you MUST re-enter `preview-verification`, capture the relevant stage(s), and confirm the screenshot-observed asset/scene defect is fixed, unless the 2-round visual iteration limit has been reached and the residual defect is reported honestly. If the fix changes icons, image/resource bindings, scene object references, prefab/object replacement, material/texture carriers, or runtime-created visual carriers, the screenshot re-verification must reload the effect package/scene first via `preview-verification`'s standalone `reset_preview` gate; that gate must be one isolated `previewTool` call with only `reset_preview`, and the follow-up `start_preview_record`/screenshot sequence must be a later `previewTool` call. Do not judge the fix from a stale preview session. Defects discovered only from `consoleLog` or invisible runtime state do not automatically require screenshot re-verification unless they also affect the visible preview.

**Non-removal repair gate**: Visual Quality Review MUST NOT remove, delete, or retroactively de-scope game-owned elements to make screenshots cleaner. This includes built-in ranking lists, settlement panels, HUD, controls, tutorial UI, feedback effects, hazards, collectibles, decorative game elements, and any element planned in the active gameplay brief or already present in the scene. If an element is visually unreasonable, cluttered, poorly placed, appears in the wrong phase, overlaps another game element, or conflicts with the intended hierarchy, preserve it and fix position, size, layer/depth, style weight, opacity, grouping, contrast, phase timing, reset path, or show/hide order. Do not rewrite the active gameplay brief to remove a planned element, shrink the gameplay scope, or change rule/tutorial semantics as a visual fix. Never use real-person face/body/background overlap as the reason to modify the active gameplay brief, shrink the active playfield, move gameplay instructions out of their game-appropriate location, or change the game rules.

### Step 1: Capture staged screenshots and gameplay keyframes

Reset the effect first so you review a clean run, then start recording so gameplay actually begins (games reset state and gate interaction on `RecordStart`, so the real initial gameplay frame only exists after recording starts). Capture the target baseline stages (initial frame, mid-gameplay frame, settlement or fail/result frame when reachable), then add gameplay-specific keyframes when the genre has important visual/feel details that the baseline stages may miss.

**Reset gate first**: The first preview operation in Visual Quality Review MUST be a standalone `previewTool` call containing only `reset_preview`. This means the `previewTool` payload's `commands` array MUST have exactly one item: `{ "commandType": "reset_preview" }`. Do not batch `reset_preview` together with `start_preview_record`, `pause_preview`, `screenshot`, `touch`, `drag`, `wait`, `resume_preview`, `stop_preview_record`, `consoleLog`, or any other command/action. Check that this reset command succeeds before running any recording, screenshot, interaction, wait, or log commands. If reset fails, stop the visual review and report the reset failure instead of grading stale screenshots.

**Ordering after reset succeeds**: After the standalone reset succeeds, `start_preview_record` MUST be the first command in the next preview sequence, before the initial-frame capture — otherwise the initial screenshot shows the pre-`RecordStart` idle state instead of the actual gameplay start.

**Pause around every capture**: freeze the preview with `pause_preview` right before each `screenshot`, then `resume_preview` immediately after so the flow continues. This guarantees a stable, non-blurred frame and prevents animation drift between the pause and the capture. Always pair each `pause_preview` with a matching `resume_preview` — never leave the engine frozen.

**Gameplay-aware operation plan**: Before writing commands, infer the core mechanic from the active gameplay brief, visible UI, and the recent script/scene changes. Insert the minimum gameplay actions needed between the staged screenshots so the review covers real play, not only idle waiting:

- **Tap / timing games**: use one or more `touch` commands on the actual play target, button, lane, or safe interaction area.
- **Drag / aim / swipe games**: use `drag` or `touch_down` → `touch_move` → `touch_up` with coordinates that exercise the main control path.
- **Hold / charge games**: use `touch_down`, wait for the charge/hold state, then `touch_up`, and capture the feedback after release.
- **Dodge / collect / endless games**: wait long enough for hazards/items to spawn, then perform a few representative moves before the mid-game screenshot.
- **Quiz / memory / matching games**: make at least one meaningful selection (correct or intentionally wrong, depending on the state you need), and if possible advance to feedback/settlement.
- **Fail-state / settlement review**: if natural settlement takes too long, intentionally trigger a miss, wrong choice, collision, forced hazard contact, score/time shortcut, or timeout using the cheapest supported interaction. Prefer short, controllable paths over long waits; avoid relying on a single long `wait` that may hit preview client timeouts.
- **Vision / audio-driven games**: if the required face/gesture/audio signal cannot be simulated reliably, still capture the reachable visual states, use `consoleLog` if needed, and explicitly report which visual stage could not be driven by preview commands.

**Control group consistency check**: Before grading visible controls, identify the intended input actions from the active gameplay brief, visible UI labels, and `GameManager.ts` input handlers when available. Then compare those actions against the screenshot's button group. Controls that are semantically paired or symmetric (left/right, up/down, previous/next, accept/cancel, primary/secondary actions, D-pad directions) must also look like a coherent UI group: same visual style, size, backing, stroke/shadow, icon language, label treatment, color weight, and mirrored orientation rule where applicable. Mark it as a VQR defect if two symmetric controls are clickable and correctly placed but use mismatched visual languages, inconsistent icon families, asymmetric decoration, different visual weights, or symbols that make one side look like a different kind of action. Do not pass VQR with "controls are present" unless the control group visually communicates its paired operation model.

**Gameplay keyframe strategy**: Add 1-3 extra screenshots when needed to inspect game-effect quality, not just layout. Examples:

- **Main character / player avatar keyframe**: capture a low-density moment soon after `RecordStart` to inspect the default pose, facing direction, scale, readability, and relationship to the intended action direction.
- **Control feedback keyframe**: for drag/steer/aim games, capture during or right after movement to inspect banking/tilt/rotation, aiming clarity, and whether control feedback is expressive without hurting readability.
- **Action readability keyframe**: capture a moment with projectiles, targets, hits, combo, or collision feedback to inspect whether attack direction, hit feedback, and gameplay lanes are visually understandable.
- **Density/ramp keyframe**: for action/endless games, capture early and mid-run density separately if needed to verify that difficulty and visual clutter ramp up instead of overwhelming the screen immediately.

The sample below is only a default tap-based scaffold. Replace or add commands between screenshots to match the actual gameplay and the needed keyframes. Do not use a center tap blindly when the game has a clearer target/lane/button.

```json
      "tool_name": "previewTool",
      "payload": {
        "intention": "Visual quality review reset gate: reset effect before capture",

      }

}
```

Only after the reset result is successful, run the capture sequence:

If the settlement/result stage cannot be reached with available preview commands, first try a cheaper path (for example: intentional collision, wrong choice, miss, timeout shortcut, or reduced waiting). If it still cannot be captured reliably, do not block the whole Visual Quality Review on that screenshot alone. Continue reviewing the captured initial, mid-gameplay, and gameplay-keyframe evidence, and report the missing settlement/result capture as a **verification gap**. Do not claim that the settlement/result visual state is verified unless it was actually captured.

**Screenshot progression check**: Compare captured screenshots before grading them as a complete VQR set. If all screenshots are nearly identical, or the mid-gameplay frame does not show any meaningful state change after the intended wait/interaction path, treat it as insufficient gameplay progression evidence. Try one more genre-appropriate interaction or wait path (for example target tap, lane drag, control button press, intentional collision, or longer early-run wait). If screenshots still do not progress, report a verification gap and route the likely issue to script/runtime progression instead of claiming the gameplay or visual flow passed.

### Step 2: Self-assess each screenshot against the final-screen checklist

Grade every captured frame against this checklist. Each item maps to a rule owned by `game2d-planner` (design intent) or `game2d-engine` (runtime lifecycle).

**Screenshot validity precheck**: Before grading visual quality, confirm that each screenshot actually contains a visible game layer. A successful `previewTool` screenshot command only proves the capture tool worked; it does not prove Visual Quality Review succeeded. If a frame is blank, near-blank, or shows only the camera/background placeholder with no meaningful game-owned visual carriers, treat the screenshot as invalid evidence. Do not pass VQR on such a frame. Re-check `RecordStart`, scene object visibility, alpha, position, depth/layer, asset binding, and reset state, then re-capture. If the game layer still cannot be made visible with available tools, report a verification gap or visible-game-layer defect instead of claiming the stage passed.

**Non-defect precondition**: Game elements covering, overlapping, or visually competing with the camera person's face/body/background subject is NOT a Visual Quality Review defect. Do not treat "遮脸", "遮挡人物", "面部保护", "face-zone", or "face-overlap" as failures. Only evaluate game-owned problems such as wrong phase visibility, confusing information hierarchy, gameplay elements competing with each other, unclear interaction area, stale UI, or unreasonable game-element layout.

**Overall Visual Read first**: Before checking individual items, write a 1-3 sentence overall read for each captured stage: does the screen feel like one coherent designed game screen, or like a collection of unrelated/debug elements? Explicitly mention the overall style, layout balance, hierarchy, and completion level. Do not skip this overall judgment even if every individual checklist item looks acceptable. If the settlement/result stage was not captured, state that gap separately instead of inventing a judgment for it.

**Ignore non-game background placeholders**: Do not grade the aesthetics, style consistency, face visibility, or asset quality of the camera/background placeholder itself (for example: a person's avatar, stock face image, or temporary AR background used only during production). Treat it as non-game background context, not as a visual carrier owned by the game. Visual Quality Review should judge the game layer's final player-visible design: layout, hierarchy, readability, style, feedback, pacing, and genre feel.

**Do not evaluate real-person occlusion**: Visual Quality Review MUST NOT fail or fix a game because game elements overlap, cover, or visually compete with the camera person's face/body/background subject. Judge only whether game-owned elements are reasonable for the game rules, genre, interaction path, readability, feedback, and phase hierarchy. Face-zone, face-overlap, and real-person visibility are outside this review unless the game mechanic explicitly depends on face/gesture tracking.

**AR layout adjustments must not break genre integrity**: AR/camera context is a design constraint, not a command to distort the genre's natural playfield. For genres whose natural playfield crosses the portrait center (for example vertical shooters, falling-object dodgers, rhythm lanes, or aim/target games), preserve the genre's expected spatial grammar while managing density and readability. Prefer genre-preserving fixes such as density ramping, smaller or lighter transient objects, staggered spawn timing, believable lanes, clearer safe gaps, and moving persistent HUD/settlement panels away from active play. Do NOT solve layout concerns by making the gameplay layout obviously unnatural, such as forcing every enemy in a vertical shooter to spawn only from the far left/right edges when the genre expects enemies above the player and a readable vertical combat lane.

**Gameplay Effect Review**: After the overall visual read, inspect whether the game effect itself feels correct for its genre. This is not only a layout check. Infer the genre from the active gameplay brief and the running preview, then explicitly review the core gameplay presentation. For example, vertical shooters should read as "player at the lower safe area, stable upward attack, enemies/hazards above, clear combat lanes, density ramping over time"; matching games should read as "clear hidden/revealed states, obvious selection feedback, no passive answer leakage"; rhythm/timing games should read as "clear target timing, readable hit/miss feedback, and satisfying beat/impact response".

- **No over-decorated / oversized backing panels**: Large UI backings are not solid filled rescues for oversized UI. Prefer compact, game-appropriate elements, phase-based UI, or no-fill / outline-only frames.
- **Minimum visible game layer**: Each captured stage must show enough game-owned visual carriers to make the stage reviewable. Initial frames should show at least core HUD, hint, main gameplay subject, controls, or other planned opening elements; mid-gameplay frames should show the gameplay subject plus visible state/progression; settlement/result frames should show the result UI when that stage is reached. If the screenshot contains only a mostly empty background/camera placeholder with little or no game UI, sprites, Text, controls, feedback, or panels, the frame is invalid or failing visibility, not a visual pass.
- **Contrast against the camera feed**: UI/sprites remain visible against complex or bright real backgrounds (white walls, grey studio backgrounds, busy scenes) using enough drop shadow, outline, backing, color separation, scale, or opacity. If the game layer technically exists but nearly disappears into a bright/low-contrast background, treat it as a visibility defect.
- **Theme expression**: The screen communicates the intended theme through its available carriers: PNG art, Text styling, emoji choice, color coding, symbol shape, motion, and feedback rhythm.
- **Overall style coherence**: Text, emoji, procedural effects, colors, outlines, shadows, UI containers, and PNG/Image assets (if present) feel like one visual system instead of unrelated defaults. The initial, mid-gameplay, and settlement stages should keep a recognizable shared style.
- **Layout reasonableness**: Main gameplay area, HUD, tutorial hints, buttons, transient feedback, and settlement UI have clear spatial roles, enough breathing room, and sensible alignment. Watch for over-crowding, over-scattering, edge-hugging, feedback stealing focus from gameplay, or settlement panels fighting with old gameplay UI.
- **Composition and visual hierarchy**: The player can immediately tell what is primary, secondary, and temporary. HUD, gameplay objects, tutorial hints, transient feedback, and settlement are clearly separated and balanced. The screen reads like a designed game composition, not a debug overlay.
- **Settlement / ranking style integration**: Result panels, built-in ranking lists, score cards, and other overlay components must not look like unrelated default widgets pasted on top of the game. If a ranking list is required, its container, timing, scale, contrast, and surrounding settlement UI should preserve the game's style system and not fight the main result message.
- **Ranking list aspect ratio and density**: Ranking / leaderboard cards must have a readable portrait-friendly aspect ratio and content density. Treat it as a defect if the leaderboard looks too wide and flat, has compressed title/header space, cramped rows, tiny avatars/names/scores, excessive horizontal squeeze, or a default-table feel that does not match the settlement card. Fix by adjusting the card width/height ratio, row height, title area, padding, font size, avatar scale, and spacing while preserving the ranking element.
- **Information hierarchy in overlay phases**: In settlement, ranking, help, pause, or other overlay phases, the screen must have one clear primary message and a small number of secondary details. Watch for result panels, ranking lists, HUD, player objects, combat remnants, hints, and buttons all competing at once; this is a mandatory visual defect when it makes the final screen hard to parse.
- **Text readability**: HUD, hints, result panels, ranking text, score labels, combo labels, and tutorial copy must remain readable at preview size. Watch for small fonts, low contrast, white or yellow text on pale panels, insufficient stroke/shadow, crowded multi-line text, clipped text, and decorative backgrounds that reduce legibility.
- **Tutorial / rule prompt readability**: Opening hints, rule prompts, and tutorial copy must be independently readable in the captured preview, not merely present in the scene. Grade readability by the worst background segment behind the text, not by the average screen contrast: pale grey/white camera backgrounds, bright panels, hair/face edges, and busy texture transitions can make thin white or yellow text with a light outline unreadable at first glance. Treat it as a defect if the prompt is too small to read at preview size, is squeezed against the HUD or panel edge, blends into a pale/bright background, relies only on a thin stroke/glow, crosses high-contrast background edges, lacks a dedicated high-contrast backing/shadow/outline, is clipped, or uses a long single-line sentence that visually collapses into decoration. Fix by increasing font size, using darker or higher-contrast text/fill, thickening stroke, adding shadow, adding or strengthening a compact translucent backing, increasing line spacing, box height, or text grouping; do not move rule text to a game-inappropriate position just to avoid real-person overlap.
- **HUD not crushing the play area**: Score/lives/timer HUD does not dominate or overlap the main gameplay subject; secondary interactive elements are decoupled into separate lanes or phase-based reveals.
- **Preview host control safe area**: Game operation controls must not sit in the preview app's bottom-center recording/control area or the bottom system gesture area. For portrait previews, treat the bottom-center zone as reserved host UI space (roughly the lower 20-25% around the horizontal center, especially where the record button or confirmation button appears). Direction pads, joystick centers, primary action buttons, confirm buttons, or drag handles placed there are mandatory visual/interaction defects because they conflict with recording controls. Move or split them to side lanes, upper-bottom corners, or another game-appropriate control zone without deleting the controls.
- **Control group visual consistency / affordance**: Visible operation controls must visually communicate both the action they trigger and their relationship to other controls in the same group. Visible controls that represent semantically paired or symmetric operations must also be visually consistent as one UI group, including left/right, up/down, previous/next, accept/cancel, primary/secondary actions, and D-pad directions. Use a shared visual system within the group: matching backing shape, size, stroke/shadow, icon family, graphic-semantic family, label treatment, color weight, spacing, and mirrored orientation rules where applicable. Direction buttons should form a consistent directional system (for example mirrored left/right arrows, up/down arrows, or a coherent D-pad). Icons in one control group must express actions with the same visual metaphor; do not mix direct movement arrows, curved return arrows, refresh/loop signs, check/confirm marks, cancel marks, or decorative flourishes in a way that makes symmetric or paired operations read as different operation types. Semantically symmetric controls must not look visually asymmetric through mixed icon styles, inconsistent graphic semantics, asymmetric decoration, different visual weight, inconsistent button treatment, mismatched backing shapes, mismatched stroke/shadow, different scale, unrelated color weight, or label treatment that makes paired actions look unrelated. This check is mandatory for every visible control group in the screenshot; do not mark controls as PASS based only on placement, size, or clickability. If the mismatch is caused by the icon PNG/Image assets themselves, regenerate a coherent icon set through the asset generation layer, then rebind the scene objects and re-review screenshots after standalone `reset_preview`. Fix scene-owned issues by restyling/replacing icons, labels, backing, grouping, spacing, and visual weight so the control group reads as one coherent UI system. If restyling, moving, or replacing a control would require script hit-area or input-mapping changes, report that as a follow-up script task instead of editing gameplay/input logic during VQR. Do not delete controls.
- **No stale phase-based UI or state leakage**: Help/hint/settlement/power-up/selection UI is not left permanently visible; previous-phase controls are hidden/deactivated on phase change and reset on `RecordStart`. Explicit leakage examples include settlement panels visible on the first or mid-gameplay frame, ranking lists shown before the settlement phase, fail/burst/eat/combo effects left visible on the initial frame, old gameplay objects fighting with the result phase, and previous-run score/result text persisting after reset.
- **No leaked hidden answers**: For memory/matching/card-flip/reveal gameplay, hidden answers are not passively exposed (no low-alpha / pale / small-font weakening as a substitute for hiding).
- **Player / subject readability**: The primary game-controlled player object, avatar, cursor, reticle, or controlled subject is immediately identifiable as the player's focus. Its default pose, facing direction, scale, and screen position match the genre and do not compete with HUD, enemies, projectiles, or feedback effects. Do not apply this item to the real camera person or background face/body.
- **Primary gameplay asset semantic match**: PNG/Image assets and other first-class visual carriers used for the main player/subject, body parts or sub-parts when present, collectibles, enemies, hazards, projectiles, and key props must visually match their intended role in the active gameplay brief. Check screenshot-visible semantic identity and gameplay role, not only asset presence, file name, object name, colorfulness, or binding success. Apply a generic role-based checklist:
  - **Player/subject identity**: the controlled subject reads as the entity named in the brief, such as a plane, ship, animal, character, cursor, reticle, vehicle, ball, tile, or other game-specific subject.
  - **Role distinguishability**: the player/subject is visually separable from collectibles, enemies, hazards, projectiles, props, and feedback effects by silhouette, shape language, color role, scale, iconography, or graphic-semantic family.
  - **Direction/action affordance when applicable**: if gameplay depends on facing, aiming, movement, attack, steering, or growth direction, the visible asset should communicate that direction/action well enough for the player to understand how it behaves. If the genre does not depend on direction, mark this sub-check `NOT_APPLICABLE` rather than failing it.
  - **Role separation across core assets**: targets, rewards, hazards, enemies, projectiles, and props should not be mistaken for the player/subject or for each other in the captured stage.
    Genre-specific criteria are examples only. A plane game may require the subject to read as a plane with clear flight/attack direction; a snake game may require head/body role separation and connected body readability; a memory or puzzle game may only require controlled tiles/cards to be distinct from inactive or revealed states. Treat it as a mandatory VQR defect if the primary subject reads as another gameplay role, a generic sticker/decorative object, or if core assets share a graphic-semantic family so strongly that gameplay roles are unreadable. Fix by regenerating the asset prompts/PNGs or visual carriers, replacing bindings, recompiling when needed, running standalone `reset_preview`, and re-capturing screenshots.
- **Action direction clarity**: The player's facing direction, projectile/attack direction, movement direction, and target/enemy layout are visually consistent. For shooters, the ship nose, bullets, enemies, and combat lanes should make the intended attack direction obvious.
- **Control feedback polish**: Movement/drag/aim/steer feedback (tilt, banking, squash/stretch, rotation, alpha, trail, or emoji/text motion) is expressive but not excessive. It should support control feel without making the subject look mis-aimed, unstable, or off-style.
- **Gameplay lane / interaction-zone clarity**: The active gameplay region, enemy/hazard spawn region, player safe region, and feedback region are spatially understandable and genre-appropriate. Avoid sustained clutter that hides the player, targets, hazards, or key feedback, but do not over-correct by destroying the genre's expected lanes, spawn direction, or attack direction.
- **Playable area coverage for movement games**: For snake, dodging, chasing, lane-running, projectile survival, and other continuous-movement games, the active playfield must be large enough to support the intended duration and maneuvering. In portrait preview, the default target is for the main playfield to occupy roughly the upper 70-75% of the visible game area while keeping operation controls out of the bottom host recording/control zone. If the snake/player/runner can hit a boundary almost immediately because the arena is too small, narrow, or cramped, treat it as a gameplay-effect defect. Fix by expanding/repositioning the playfield, tuning world bounds, spawn lanes, object scale, camera-space mapping, or movement speed; do not delete gameplay elements to create space.
- **Difficulty and density ramp**: Visual clutter, hazard density, enemy count, projectile count, or decision pressure should ramp toward the intended peak instead of overwhelming the screen immediately or ending the experience before the designed duration can be felt.
- **Genre feel**: The frame should look like a mature version of the intended genre, not merely a functional prototype. Check genre-specific expectations such as stable upward hero readability for vertical shooters, clear covered/revealed states for memory games, satisfying target impact for action games, and obvious timing windows for rhythm/timing games.
- **AR / genre balance**: The game should feel adapted to camera preview constraints without losing the core genre fantasy. If a layout fix makes the game feel less like the intended genre (for example enemies only appearing from side gutters in a vertical shooter), treat that as a gameplay-effect defect and seek a balanced fix instead.
- **Feedback / juice quality**: Hits, misses, combo growth, score changes, failure, settlement transitions, and other key events have visible feedback (particles, screen shake, tweens, scale/alpha pulses, emoji/text motion, or equivalent effects). The result should not feel like static text updates.
- **Visual carrier quality**: Text and emoji carriers are sized, placed, colored, layered, and animated intentionally. Procedural shapes/effects and runtime-generated visuals look deliberate, not like raw debug primitives.
- **Placeholder quality**: If placeholders are used, they are styled consistently with the design brief's color logic, hierarchy, safe-zone rules, and composition. A placeholder may be temporary, but it must still be reviewable and polished enough for the current iteration.
- **Asset completeness (only when assets are part of the design)**: If the brief explicitly relies on PNG/Image assets, check that they are rendered and not missing, broken, empty, or accidentally replaced by obvious placeholder squares. Do not use this item to penalize a deliberately Text/emoji/procedural visual design.
- **Readability**: Text fits its box, is not clipped/overflowing, has enough contrast against its own panel/background, and is legible at preview size.

For each item, state PASS or the concrete defect you see (with the stage and rough on-screen location). Combine with `consoleLog` only when a defect's cause is invisible in the screenshot (e.g. a missing asset vs. an object not visible in the captured frame).
