# 2D 游戏 UI 与布局规范

本 Reference 由 `ui-layout` 在 2D/AR 游戏规划或场景布局时加载。通用容器、文字容量、可读性、图文组合和生命周期原则以 `ui-layout` 为准；本文件只补充游戏画布、HUD、视觉资产、代表性状态和场景布局规则。

`game2d-planner` 将视觉与静态布局事实写入 `Assets/design_brief_ui.md`，将状态、事件和运行时显隐写入 `Assets/design_brief_gamelogic.md`；`scene-builder` 汇合两份执行 Brief 落地场景，2D Game Engine 只按 gamelogic Brief 与 `sceneSpec` 实现运行时状态。本 Reference 不建立第二套 Brief schema 或执行流程。

---

## 1. 规范职责与执行优先级

### 1.1 规则优先级

所有布局决策按以下优先级执行，低优先级规则不得覆盖、修改或绕过高优先级规则：

1. `fixed-layout-reference.md` 指定的固定坐标、尺寸、边距、区域范围及锁定位置。
2. 用户针对固定合同未指定对象提供的明确坐标、尺寸、边距和锁定要求。
3. UI Brief `Scene Layout Plan` 的项目级位置、尺寸、区域归属、容器关系和锁定状态。
4. gamelogic Brief 的同时可见集合，以及 UI Brief 的文字安全区、图标安全区、点击区域和复合构图关系。
5. 最小间距、避让、视觉平衡和未锁定对象的自主布局。

执行规则：
- 当前输入坐标与全局基准冲突时采用全局基准；输入坐标只用于全局基准未指定具体位置的对象。
- 固定坐标只允许数学等价换算，换算后的最终外接矩形必须完全一致。
- 禁止重叠、最小间距、人脸避让和自动布局不得改变固定坐标。
- 发生冲突时，只能调整未锁定对象的尺寸、位置或内部排版；不得通过改写 gamelogic Brief 的阶段显隐解决静态布局冲突。
- 调整未锁定对象后仍无法解决时必须报告冲突，不得修改规范固定坐标。

### 1.2 唯一规则源

- 固定坐标只在 `fixed-layout-reference.md` 定义。
- HUD 排版只在“顶部 HUD 信息栏”定义。
- 结算面板结构、字号、Text 对象和排版只在“结算面板、结果页面”定义。
- 重叠、叠层和最小间距只在“重叠、叠层与间距”定义。
- 其它章节只能引用对应规则，不得复制数值、建立第二套规则或改变原意。

## 2. 全局画布与布局基准

### 2.1 运行环境
- 游戏叠加在用户实时摄像头画面上，摄像头画面是唯一背景。除用户指定生成元素外禁止生成或规划天空、远山、水面、建筑、森林、房间、景观铺底及其它纯环境背景 PNG。仅当道路、平台、地面或通道直接承担移动边界、碰撞、落点、生成基准或操作范围时，才作为最小玩法结构使用 `gameplay_sprite`，并归入玩法层；题材或风格描述本身不构成准入理由。
- UI 和贴图通过合理位置、高对比度、描边或投影，在复杂真实背景上保持清晰可见。
- AR 游戏采用人脸软避让，不要求为完整人脸预留绝对不可进入的矩形。布局应在满足固定区域、玩法可读性、点击效率和视觉平衡的前提下，尽量为人脸保留较大的连续可视空间。
- 玩法对象可以合理覆盖额头、头发、脸部边缘或其它非关键区域；不得用大面积密集元素持续遮住人脸主体，也不得同时遮挡眼睛、鼻口等主要识别部位。禁止为了完全避让人脸而将内容挤压、缩小、拆散或排成失衡布局。
- 测一测必须在 UI Brief 中记录人脸可视空间与内容分布关系，但不建立绝对禁止相交的人脸安全矩形。题目、选项和操作对象优先围绕人脸上方、两侧或下方组织；局部覆盖与合理穿插允许存在，只要人脸仍保持清晰、连续且具有足够视觉占比。
- 结果面板、结果复合单元及其结果文字不受人脸软避让限制，按结果阶段的信息层级、固定区域和内容容量正常布局。
- 测一测类型无 HUD；输入阶段首个非绿色完整内容单元的完整外接矩形固定坐标为 `top=148`。完整内容单元包括独立标题 Text、题目容器、对话容器、待操作卡片及其绑定文字；容器与绑定 Text 视为同一单元，不重复参与纵向排列。后续内容单元按上一单元 `bottom + 规定净间距` 继续向下排列，并允许连续跨越 `y=270`。绿色常驻交互区对象不参与该内容流。

### 2.2 固定布局参考图与 Visual Assets 落区合同

固定布局参考图的完整文字释义位于 `.agent/skills/ui-layout/references/fixed-layout-reference.md`。Planner 在 Brief 阶段将图片与该合同共同理解，把项目实例写入 `Scene Layout Plan`；Scene Builder 只消费已落盘布局，不重新解释参考图。固定区域与 `hud_bar` 特例以该合同为准，普通素材最终比例以 `Assets/visual_asset_final.md` 为准。

## 3. 通用 UI 设计原则

### 3.1 UI 容器

- UI 容器先满足信息职责、内容容量、文字安全区和点击区域，再根据独立 Style RAG 链路提供的 LockedStyle 确定轮廓、结构、材质与表面语言。存在 LockedStyle 时必须产生可识别的样式适配，不得无视其形状语言而统一使用普通圆角矩形或胶囊；只有 LockedStyle 明确支持，或组件功能确实要求时才使用胶囊结构。不存在 LockedStyle 时使用简洁、实体不透明的功能性容器，不自行虚构主题风格。
- 形状变化不得破坏文字安全区、点击区域、完整外接矩形和安全区落位；仍禁止发光、玻璃态、半透明、空心、镂空、仅轮廓和多重嵌套边框。
- 禁止半透明、无填充、仅轮廓、空心、镂空、仅框架或背景模糊式容器。
- UI 底板描边服从独立 LockedStyle；布局规则不建立第二套表面样式。
- LockedStyle 包含白色、近白色或深灰容器时，只调整容器实体填充色为 LockedStyle 中合规的非白颜色或浅中性灰；保留其轮廓、结构、材质和其它风格特征。该抠图安全约束高于容器表面配色，不得为忠实还原风格继续使用禁用颜色。
- **UI 容器抠图安全色**：所有 `hud_bar`、按钮、卡片、题目容器、选项容器、结果容器、标签和面板的实体填充面禁止使用白色及视觉上接近白色的颜色，避免素材主体在白底抠图阶段被误删。灰色容器只能使用与白色保持清晰明度差的浅中性灰，禁止使用深灰和彩色灰。
- 本限制仅适用于需要生成并抠图的 UI 容器实体填充面，不得扩展为文字、图标、特效或玩法主体的通用禁色规则。
- 除非功能必要，不添加内轨、双重边框、嵌套页签、重复胶囊、装饰点、状态灯、分割条、迷你标签或装饰性角部组件。
- 禁止生成无意义、无交互形式、对游戏玩法毫无作用的全屏装饰框、屏幕边框、AR 叠层、角括号环绕框等镂空 PNG 资产。
- UI 过大时，只能调整未锁定尺寸、拆分为更小的功能容器，或由 Planner 在 gamelogic Brief 中规划合理的阶段显示；Scene Builder 不得临时改显隐，也不得通过降低透明度解决。
- 结构性模块高度必须 `≥48px`，最小宽度必须 `≥80px`；使用圆角矩形/圆角胶囊形状时圆角半径为模块高度的 `1/3~1/2`，其他形状（横幅、牌匾、卷轴、木板、金属铭牌、石板、布条等）按LockedStyle设定轮廓，不强制圆角。

### 3.2 文字承载

- PNG 不得包含可读文字；所有可读文案必须使用场景 Text 对象。
- 常驻、状态类、可交互或结构性文字必须位于其绑定的 UI 容器内部，并遵守文字安全区。
- 短暂提示、操作反馈、飘字反馈、受击反馈和装饰性大标题可以作为独立文字。
- “短暂”“阶段性”或“互斥”只能根据 gamelogic Brief 的 Runtime Visibility Plan 判断，不得为了规避布局冲突自行分类。
- 独立文字必须具有明确文字矩形，并通过高对比颜色、粗字重、描边或投影保证可读性。
- 只有图片本身是按钮、卡片、标签底板、结算面板或信息栏等真实文字容器时，文字才可放在图片上。

### 3.3 文字安全区与内边距

- 每个承载文字的 PNG 容器必须定义文字安全区；含有小图标的容器还必须定义独立图标安全区。
- 文字安全区必须避开描边、圆角、斜切角、图标、装饰和功能性强调区域，不能直接等同于 PNG 完整尺寸。
- Text 对象在 UI 内部时，两侧必须留有安全边距 `≥20px`；可能超出安全边距的多行文本使用 `fixedWidth + autoLineBreak`。
- 单行文字容器：水平内边距 `≥16px`，垂直内边距 `≥10px`。
- 按钮文字：左右内边距 `≥20px`，上下内边距 `≥10px`。
- 多行提示框、结果卡和说明卡：水平内边距 `≥24px`，上下内边距 `≥20px`。
- 图标与文字间距 `≥12px`，图标区域不计入文字可用宽度。
- 文字不得接触容器描边、圆角、图标或装饰，不得以自动缩小字号代替内边距。

### 3.4 通用文字排版

- 每个 Text 对象必须根据 UI 类型显式指定水平对齐和垂直对齐，不得依赖引擎默认值。
- 每个 Text 对象必须显式选择 `boxDimension`：`dynamic` 用于独立短标签，`fixedWidth` 用于限宽多行正文，`fixedSize` 仅用于严格容器安全区；文本框自适应不得解释为自动缩小字号。
- `lineBreakType` 按用途选择 `autoLineBreak`、`cutOff` 或 `clamp`；运行时变化文案按最长预期内容预留容量。
- 结算面板排版遵守 4.2 专属规则。
- 数值型信息：水平居中或右对齐，同组必须一致。
- 不允许使用空格、全角空格或无意义换行模拟对齐。
- 同行多个 UI 模块按容器外框对齐，不得只按文字中心对齐。
- 特殊类型规则（图标右侧标签、数值型信息）优先于下方通用纯文字容器规则。
- **纯文字容器**：文字对齐跟随容器在画布中的定位（左→左对齐、中→居中、右→右对齐），垂直居中；垂直居中以**有效内容区**（比如去掉气泡尾巴、装饰角等非对称元素后的主体矩形）为基准，不以容器整体边界框为准。
- **多行说明、结果详情和阅读型正文**：对齐方式同上，顶部对齐，设正值行距。
- **图文组合容器（含 Image 子元素）**：文字在各自子区域内居中，内容组整体对齐遵守 4.5 复合构图单元规则。

### 3.5 容器容量

- 容器尺寸必须先在 `design_brief_ui.md` 和设定图阶段根据实际文字容量完成规划；最终输出容器与 UI Brief 中的尺寸差异较大时，须按最终尺寸重新调整容器和文字安全区。
- 每个文字容器按 `ui-layout` 的文字容量合同计算，并记录最长预期文案、字号、单行/多行、最大行数、内边距、图标宽度、图文间距、文字安全区、图标安全区和最终建议尺寸。
- 纯文字 UI 容器必须通过高度贴合验收，不得出现容器高度为文字块高度 `4~10` 倍的空框；含角色、插画或图标等真实槽位的复合容器按完整内容组总高度验算。
- 容量不足时必须先检查锁定状态：
  - 未锁定容器可以在所属区域内扩大，但不得造成新的布局冲突。
  - 锁定容器不得扩大、移动、缩小字号或减少内边距，只能缩短文案、合规换行或切换备用文案。
  - 仍无法容纳时必须报告容量冲突。

### 3.6 文字字号尺寸、内容与可读性

| 文字层级 | 字号范围 | 用途说明 | 典型场景 |
| --- | --- | --- | --- |
| 标题 | `36px~46px` | 页面或信息组的核心名称，层级最高、视觉权重最强，承载页面主题、结算标题、游戏名称或核心结果判定 | 结果揭示标题（如「命运之轮」）、面板大标题、游戏开场主标题、胜负判定主文案 |
| 一级正文 | `28px~30px` | 核心信息正文，字段标签前缀，承载用户需要优先阅读的主要内容、实时数据和关键结果 | HUD 实时数值（分数/倒计时/生命）、HUD 字段标签前缀（如「得分：」「时间：」）、结果关键词、核心选项文案、主要操作提示、结果正文结论段 |
| 二级或辅助说明 | `25px` | 辅助说明、补充信息和次要提示，视觉权重最低，不抢占主要信息焦点 | 辅助说明短句、提示引导文字、标签小字、评分/评价后的补充解释、非核心状态提示 |
- 标题与正文的字号差保持 `6px~8px`。
- 重要数字、分数、倒计时和关键状态不得小于 `30px`。
- 游戏文字必须简短清晰，不得把完整说明、密集规则或长篇描述直接放入画面。
- 有实体底板的文字与底色对比度必须 `≥7:1`，不足时按第3.7节选择合格的深色或浅色；摄像头上的独立文字使用该节的无背景样式。
- 浅色背景使用深色文字，深色背景使用白色或高明度文字。
- 渐变、纹理或动态背景上的文字必须增加清晰描边、投影，或放入实体不透明结构性底板。
- 无底文字描边建议 `2~3px` 深色实线；投影模糊 `3~5px`、偏移 `2~3px`，颜色与透明度按第3.7节。
- 禁止使用发光、光晕、辉光、霓虹或大对比渐变效果。
- 无论 Text 是首屏可见还是阶段性 UI，都必须显式配置文本框模式：独立短标签使用 `dynamic`，限宽多行正文使用 `fixedWidth + autoLineBreak`，严格容器文字区使用 `fixedSize`；运行时 `setText()` 只更新内容，不得覆盖该布局模式。
- `fixedSize` 文本框按 `ui-layout` 的文字容量合同预留最大行数和内边距。

### 3.7 文字配色

以当前实际承载面判断：可见且完整覆盖文字区的实体填充才是底板；底板隐藏、破裂、淡出、中心透明或文字移出后，仍可见的文字使用无背景样式。

1. 有背景文字：
   - 亮色背景（相对亮度 `>0.6`）和中亮背景（`0.39~0.6`）使用当前游戏中最深的颜色；可不添加投影，如需添加固定使用暖白 `#F7F1E6` 中性投影。
   - 临界暗背景（`0.25~0.38`）和暗色背景（`<0.25`）使用当前场景中最亮的颜色，并添加背景同色系低明度深投影。
   - Planner 用每个实际运行时文字样式反推文字承载面，保证正常、警告、成功和错误等实际颜色分别达到 `≥7:1`；容器主色不满足时，在容器内使用合同已有最深/最亮色建立实体文字承载区。Scene Builder 仅在候选颜色符合最终底色的深浅方向且达到 `≥7:1` 时保留，否则依次回退合同最深/最亮色与黑/白；投影只保留模型的强度、距离、角度和模糊参数，色相按本节规则归一化。
2. 无背景文字（无实体底板、直接叠加在摄像头画面或场景上的独立 Text）：
   - 直接叠加实时摄像头的普通文字统一使用 `#FFFFFF`，开启 `#000000`、alpha=`0.5` 的投影；包括标题、词条、列标签及脱离底板后的原文。只有明确持续的浅色承载面才使用 `#000000` 配 `#F7F1E6`、alpha=`0.5` 的投影。
   - 内容本身明确表达警告、成功、错误时，分别可用 `#FFEE00`、`#008A1C`、`#FF1E34` 并开启投影；命中、下落或进入结果不会改变普通词条的语义。
3. 投影核心逻辑：深字浅投影、浅字深投影。
4. 有背景文字的投影色相：深色文字使用暖白中性投影；浅色文字搭配背景同色系低明度深投影。无背景文字沿用第2项的完整样式。

### 3.8 文字配色层级

同一容器内同时包含标题、标签、正文、数值等多个语义层级时，必须通过颜色、字号或字重建立层次，不得全部使用同一颜色：
- **标题/结果名称**：使用游戏主强调色和最高字重，作为容器视觉焦点。
- **字段标签前缀**：如“关键词：”“建议：”“得分：”“评价：”，使用高可读主文字色，字重略高于正文。
- **正文说明内容**：使用同色系低饱和辅助文字色，与底色保持 `≥7:1` 对比度。
- **关键词标签内容**：与字段前缀同色或同色系，通过字号、字重或间距与标题区分。
- **数值/关键结果**：使用强调色或高饱和主文字色，字号可等于或大于标题。

禁止正文使用高饱和强调色导致标题层级失效；同一容器不超过 `3` 种文字色相。单段文本容器继续直接遵循“文字配色”规则。

## 4. 指定 UI 组件规则
- **测试型顶部文字准入**：答题、选择测试、分类评级、内容测评和输入采集类游戏禁止生成 `hud_bar`、顶部底板和标题栏。蓝色主内容区最多放置一个从 `top=148` 起排且 `textContainerId=none` 的无底板大标题；游戏标题、测试标题和任务名称属于同一职责，只保留一个。题号、进度、轮次和阶段提示不得作为第二个顶部独立 Text；题号确需显示时绑定当前题目或上下文容器，必要操作提示只允许在主内容区阶段性显示。

### 4.1 顶部 HUD 信息栏、首屏标题底板

#### 4.1.1 固定布局与内容准入
- 非测试型游戏未启用 HUD 时，蓝色主内容区顶部默认保持 AR 透传；测一测专项从 `top=148` 开始连续布局，最多放置一个无底板大标题，必要题目或上下文容器可紧接其后；不得放置独立题号、进度或操作提示，也不得创建 `hud_bar`、顶部底板、统计栏或伪 HUD。具体内容顺序与人脸软避让遵守测一测专项规范，内容水平安全范围为 `x:48~672`。
- HUD 准入同时要求“真实运行时变量”和“玩家决策必需”。玩家必须跨阶段持续读取该指标，并依据其改变后续策略、时机或操作时，才能放入 HUD。仅供后台累计、内部判定、最终评级映射或结果页总结的分数、正确数、权重和进度不得创建 HUD。
- 单项信息即使确需显示，也不自动创建 `hud_bar`。能够归入当前玩法复合单元时并入局部信息区；不需要实体承载面且可保持清晰时使用无底板独立 Text，并遵守无背景文字规则。
- 实时指标模式中同一信息不得重复展示；标签、数值和单位可以按 UI Brief 使用一个或多个 Text，但拆分后必须组成同一信息段并保持清晰层级、对齐和间距。
- 非测试型游戏的实时指标模式中，全部指标 Text 的 `textContainerId` 绑定唯一 HUD 底板对象；独立图标与对应 Text 先组成内容组，再在同一 HUD 安全区内分段排列。标题底板模式同样仅适用于非测试型游戏。
- 测试型小游戏的标题必须使用 `textContainerId=none`，直接叠加在画面中，并按照“无背景文字”规则配置文字颜色、描边或投影；不得为了承载标题改用 `ui_container` 伪装 HUD。
- HUD 文字按最长预期文案选型：绑定 HUD 且要求居中的 Text 使用与所属 `textSafeRect` 相同的 `fixedSize` 矩形并按需 `autoLineBreak`；局部独立文字使用 `dynamic` 或 `fixedWidth + autoLineBreak`。须预留运行时增长空间，禁止用 `fixedSize + cutOff/clamp` 截断。
- 内容定位信息与表现统计不得合并成 HUD。题号或当前轮次确需显示时属于当前题目内容，应嵌入题目气泡、题目卡或主操作窗口；正确数、累计分数、准确率和结果映射进度不影响玩家后续决策时只在后台统计。
- 多个不符合准入条件的信息组合后仍不构成 HUD，不得因为题号与正确数可以组成两段均分结构，就创建顶部底板。

#### 4.1.2 纯文字模式
- 按实际段数 `N` 将 HUD 内可用宽度等分为 `N` 份，每段占 `1/N`，最多 `3` 段。
- 仅一段时直接水平居中。

#### 4.1.3 图标加文字模式
- 每段先组成“图标 + 间距 + 文字”整体组，再对所有组执行等量均分。
- 图标必须位于文字左侧，组内图标与文字间距统一为 `16px`，并垂直居中对齐。

#### 4.1.4 通用均分规则
- 无论是否存在左侧图标，标题、数值和说明 Text 都应统一在同一层级。
- 无独立贴边元素时：
  - 奇数段的中间段同时居中于 HUD 和画布中心 `x=360`。
  - 偶数段的两组中心间界线对齐画布中心，两侧等距对称。
- 有独立贴边元素时，在剩余可用宽度内重新均分，以剩余区域中心为基准。
- HUD 不放置独立贴边按钮；只有 Brief 已规划且确属核心玩法的信息图标可以作为贴边元素。
- 最左段左边缘距 HUD 左内边距 `≥16px`；最右段右边缘距 HUD 右内边距 `≥16px`。
- 左段左对齐，中间段水平居中，右段右对齐。
- HUD 内全部图标和文字位于底板上方的前景层级。
- Scene Builder 按“先组后分”和固定 `16px` 间距定位 Text 与独立图标；`sceneOps` 只执行给定矩形、保护最终安全区并返回冲突，不自动重排或关联图标与 Text。
- HUD 素材高度超过固定上限时，只允许重新生成、裁切或合规调整内部排版；不得改变固定位置和宽度，不得把文字或图标缩小至不可读。当前 `hud_bar` 后处理与场景尺寸仍按 Visual Assets 生成规则执行。
- 特定玩法类型（如测一测、AR互动等）的HUD/按钮准入例外与布局模板，参见对应玩法类型 `quiz-result.md` 专项规范；通用规则与专项规范冲突时专项规范为准，但不得突破固定合规安全区与完整外接矩形放置规则。

### 4.2 结算面板、结果页面

#### 4.2.1 固定布局与结构
- 测一测等测试型玩法的结果揭示阶段不强制使用传统结算面板，具体准入条件与布局模板参见测一测专项规范；本节规则适用于brief明确要求传统结算面板/胜利页/失败页的场景。
- 结算面板和结果页面使用“固定布局参考图与 Visual Assets 落区合同”规定的中心点、最大尺寸和所属区域。
- 挑战类游戏仅展示短 Text 结果时，结果面板完整外接尺寸不得超过 `348×410px`，中心固定为画面中心 `x=360、y=640`。
- 测试类游戏同时展示结果素材图与长文本说明时，结果面板完整外接尺寸不得超过 `478×600px`，中心固定为画面中心 `x=360、y=640`。
- 内容无法容纳时，优先缩短结果文案或缩小未锁定结果角色；不得扩大面板超过对应类型上限。
- 面板必须先划分并记录互不重叠的内部安全区：顶部徽章或图标区、结果角色或插画区、标题区、数值区、正文区和装饰保留区。文字、结果角色和功能图标不得占用彼此安全区；角花、徽章、贴纸、装饰条和边框占用不计入内容可用区域。
- 面板视觉结构和文字生成方式统一遵守“UI 容器”与“文字承载”，本节不建立第二套容器规则。
- 有限结果池在结果阶段只展示本次命中的一个结果。结果名称、对应视觉意象、该结果专属色彩强调和必要说明组成单一结果复合单元。
- 用户为多个结果指定不同颜色，只表示每个结果各自的视觉身份，不表示结果页需要同时展示全部色块。禁止将未命中的候选结果排列为等级阶梯、色卡列表、空白横条、图例、按钮或装饰槽位。
- 结果页不得保留输入阶段的 HUD、题目、选项或分类目标。如有多个目标需先确认信息层级，最终成绩只有在确有解释价值时作为一行辅助文字出现，不得为其单独创建 HUD 或第二层统计底板或不同阶段的结果内容同时出现在一个面板中。
- 一旦创建结果面板，当前结果角色或插画、结果名称、关键词、解释文字和揭晓特效必须全部声明为该面板的同一结果复合单元成员，不得作为面板外独立对象布局。
- 结果复合单元的面板、结果角色、特效、文字和边界装饰必须位于同一 `Scene Group`，并记录面板对象 ID、面板内容安全区、成员对象 ID、互斥结果候选、成员最终矩形和固定层级顺序：结果面板 < 后景特效 < 当前结果角色或插画 < 前景特效 < 结果文字 < 边界装饰。结果面板必须先创建，边界装饰不得遮挡角色或文字。

#### 4.2.2 排版模式
标题文字无论采用以下哪种模式，都应在其标题安全区内与面板中轴关系明确，不得因图标或其它字段挤压而偏离记录的对齐规则。
包含多个纵向内容块时，按阅读顺序组成一个内容组并使用 `ui-layout` 的图文组合算法；文字字段间距 `≥12px`，顶部图像与标题间距 `≥16px`。

1. **存在左侧IMAGE和右侧文字**
   - 所有图标排列在左侧图标安全区内，图标中心使用相同的 `x` 坐标。
   - 右侧文字按阅读顺序从上到下排列，所有文字左边缘使用相同的 `x` 坐标，统一左对齐。
   - 每个图标的中心 `y` 坐标与对应文字字段的垂直中心对齐。
   - 图标与对应文字之间的水平间距 `≥12px`。
2. **无IMAGE，存在多个文字字段**
   - 标题、数值和说明按阅读顺序从上到下排列。
   - 标题和单行数值水平居中。
   - 多行说明在自身文字安全区内左对齐、顶部对齐。
3. **无IMAGE，只有单一文字字段**
   - 文字在面板内部可用区域水平居中、垂直居中。
4. **顶部徽章 + 面板内结果角色 + 下方文字字段**
   - 顶部徽章、耳朵、角花、边框贴纸和其它边界装饰属于面板装饰层，可以贴边或有限突出面板外接矩形；它们不属于内容组，不占用结果角色槽位，也不得承载文字。
   - 当前结果角色或插画属于面板内容组主体，完整外接矩形必须位于面板内容安全区内，不得突破面板边界、压住边框、角花、徽章或其它装饰。
   - 结果角色、结果名称、关键词和解释文字使用互不重叠的角色区、标题区、关键词区和正文区；角色区在内容安全区上部，全部文字区位于角色区下方，文字不得覆盖结果角色。
   - 强制层级为：`结果面板 < 后景特效 < 当前结果角色或插画 < 前景特效 < 结果文字 < 边界装饰`。边界装饰可以位于最前层，但不得遮挡角色区和任何文字安全区。
   - 先从面板完整外接矩形扣除边框、圆角、角花、顶部徽章和底部装饰，得到内容安全区；再计算角色区和各文字区。不得仅按面板中心或画布中心分别目测坐标。
   - `groupHeight = 结果角色高度 + 标题高度 + 关键词高度 + 正文高度 + 全部字段间距`。
   - `startY = contentSafeRect.top + (contentSafeRect.height - groupHeight) / 2`，角色、标题、关键词和正文从 `startY` 起按阅读顺序连续排列。
   - 结果角色、标题和单行关键词的水平中心统一等于 `contentSafeRect.centerX`；多行正文使用独立正文区，`fixedWidth + autoLineBreak`、左对齐、顶部对齐。
   - 所有互斥结果候选共用同一个角色区与坐标。
   - 正文最大行数、文字矩形和面板高度必须按最长结果文案预留。内容组超出安全区时，调整未锁定角色尺寸、面板尺寸或切换已规划短文案；不得让角色越出面板、文字越出面板或将字号降至 `25px` 以下。

#### 4.2.3 文字层级与 Text 对象

- 无论是否存在左侧图标，标题、数值和说明 Text 都应统一在同一层级。
- 无图标时，标题和单行数值水平居中，多行说明左对齐、顶部对齐。
- 每个逻辑字段使用一个独立 Text 对象，例如标题、分数和评价分别为三个对象。
- 同一逻辑字段内部需要换行时保留为一个 Text 对象，不按视觉行数拆分。
- 不同逻辑字段必须使用互不重叠的文字安全区。
- 文字超出安全区时先合规换行；仍无法容纳时按“容器容量”处理，不得突破面板外接矩形和规定内边距。

### 4.3 按钮、标签与短卡片
- 用户录制按钮负责启动游戏，游戏 UI 禁止创建“开始游戏”“点击开始”“继续游戏”“点击继续”等按钮、按钮底板、按钮文字和点击热区。对应引导确需显示时只能使用非交互 Text。
- 所有独立按钮，无论常驻、首屏、阶段性或临时显示，其按钮视觉、绑定文字和完整点击热区都必须位于绿色常驻交互区 `x:40~680, y:921~1095`。
- “开始”“确认”“提交”“继续”等阶段性命令按钮不得进入蓝色主内容区。
- 直接参与玩法的棋盘格、卡牌和长内容选项属于核心玩法内容，位于蓝色主内容区。
- 分类目标不得统一按核心玩法对象处理：脸控分类目标位于蓝色主内容区靠上或人脸两侧；手指拖拽的短标签分类区、目标槽和投放区属于手部操作终点，必须横向排列在绿色常驻交互区。
- 手部拖入目标不是命令按钮，但属于常驻可交互内容，执行与绿色区按钮相同的完整落区和高度验算。
- 按钮组先按成员完整外接矩形计算组宽，再以目标区域的画布绝对中心确定每个按钮中心坐标；不得把区域局部坐标直接写入 `Scene Layout Plan`。组内任意相邻按钮的视觉主体、描边、阴影、绑定文字和点击热区之间必须保留净间距 `≥16px`，不得相交。
- 横向按钮组总宽度 = 全部按钮完整宽度之和 + 相邻按钮间距之和；总宽度超过绿色区内部安全范围 `x:48~672` 时，先等比缩小未锁定按钮，再减少按钮数量或改用其它合法布局，不得通过重叠解决。
- 按钮组使用完整外接矩形验算：每个成员及整体均须满足 `left≥40`、`right≤680`、`top≥921`、`bottom≤1095`，且相邻成员净间距 `≥16px`。任一条件失败都不得写入 UI Brief。
- 禁止大面积 UI 框、竖向长面板、`2:3` 竖向卡片、`1:1` 方形大卡片和多行说明面板。
- 无法完整放入时，调整未锁定元素的高度或等比缩小，不得侵入红色非重要交互区或其它对象占用区域。
- 多个运行时实例具有完全相同的尺寸、比例、形状、材质、视觉状态和交互职责时，共用一个通用底板资产；不同文案使用独立运行时 Text 对象。
- 只有确认核心输入是全屏点击、玩法对象点击或无需按钮的输入方式后，才能判定“无底部常驻交互”。此时不创建绿色区域按钮，绿色区域保持 AR 透传，不得生成占位控件；操作提示仍是非交互 Text。
- 固定合同允许时，蓝色核心复合单元可在不跨入红区的前提下延伸至空置绿色区域；该延伸以完整外接矩形验算，不得压越其他已落位元素。
- 绿色区域除独立按钮外，也承载手指点击的短文本随机选项，以及拖拽玩法中的短标签分类区、目标槽和投放区。
- 手部拖入目标组完整位于 `x:48~672、y:929~1087`；视觉主体、文字、描边、阴影和判定范围的完整高度不得超过 `158px`。

### 4.4 临时提示与独立文字

- 临时提示仅用于开场引导、状态变化、操作反馈、得分飘字、受击反馈或装饰性大标题。
- 临时提示属于辅助文本，但为保证独立显示可读性固定使用 `28px`。
- 非必要不对 Text 对象增加底板，但必须按照“文字配色”规则进行色彩和投影判定。
- 必须记录明确显示阶段、隐藏时机、文字矩形和对齐方式。
- 临时提示不得遮挡不属于其语义单元的玩法主体、点击区域或必要信息。

### 复合构图单元

- 先按最终画面中的完整可见组合划分复合单元，不按素材类型或文件名拆分。一个 UI 容器与位于其内部或表面的图片、角色、图标、文字和阶段特效组成同一复合单元。
- 规划时在 `Scene Layout Plan.布局约束` 中记录容器对象 ID、成员、前后层级、点击区域以及允许和禁止遮挡的部分，不新增硬字段。
- 文字通过 `textContainerId` 精确引用实际 Image 容器对象 ID；同一底板资产复用于多个实例时，每个实例使用独立对象 ID，不得用视觉资产 key、位置词或自然语言注释代替对象关系。
- 同阶段候选的互斥关系由 gamelogic Brief 的状态、事件和 Runtime Visibility Plan 表达。
- 复合构图内部允许外接矩形相交，但关键文字安全区、点击热区和主体识别区域不得被遮挡。
- 复合构图整体与其它独立 UI 模块之间仍须遵守禁止重叠和最小间距。
- 移动未锁定单元时整体移动；存在锁定子对象时，锁定对象保持不动，只允许调整未锁定子对象。
- 图文组合内容组：容器底板内含结果角色或插画和文字时，面板、角色、特效与文字位于同一 `Scene Group`，角色与所有文字组成内容组并整体位于容器内容安全区内；结果角色完整外接矩形必须位于面板边界内，文字使用角色区以外的独立文字安全区。边界徽章、耳朵、角花和装饰条不属于内容组，可以有限突出面板边界，但不得遮挡角色区、标题区、关键词区或正文区。结果面板按“面板 < 后景特效 < 结果角色或插画 < 前景特效 < 结果文字 < 边界装饰”创建。

## 5. 视觉风格与配色

- UI Brief 的 `## 全局风格合同` 逐字投影流程工具结果中的 `lockedStyle`，是视觉执行中的统一风格输入；不得自行选择、改写或叠加第二套风格。
- 主要玩法对象、UI 底板、图标和文字承载面基于全局风格合同具体展开造型、材质、表面、光照和配色，同时保持明确不同的视觉职能。
- 逐素材描述只写该对象实际采用的风格表现和颜色，不重复完整合同；设定图、棋盘图和下游视觉素材继续统一消费同一 LockedStyle。
- 风格要求与可读性、固定布局或实体不透明规则冲突时，保持风格身份并按本 Reference 的布局与可读性合同处理，不改变功能结构。
- Draft 不承载 Style RAG 结果；Draft 确认后的视觉生产直接消费独立链路提供的 LockedStyle，并由 UI Brief 投影和展开。
- LockedStyle 应实际作用于 HUD、题目容器、选项、按钮、结果容器、标签和图标的轮廓、结构关系、材质表现与表面细节，不得只替换颜色后继续复用无差别的默认胶囊结构。
- 风格适配不得改变 UI Brief 已确定的对象身份、尺寸容量、坐标、安全区、点击区域、层级关系和运行时职责。

### 5.1 视觉描述过滤与默认项

- 视觉资产描述不得包含背景音乐、音效、配音、背景乐或语音等听觉内容。
- `配色/抠图色` 从全局配色约束中选择该素材实际使用的具体颜色，同时保留危险、奖励和透明抠图等功能要求；运行时文字颜色按第 3.7 节的可读性合同处理。
- 默认禁止输出暂停、设置、分享、帮助、聊天、好友、广告、活动弹窗和确认键，除非玩法明确需要。
- 设定图代表性状态中的主体使用静止待机或稳定停驻姿态；运行时状态不受该限制。

### 5.2 通用配色纪律

`## 全局风格合同` 继续逐字保存 LockedStyle，不追加字段或改写内容；Planner 按以下规则将其中的配色约束展开到 Visual Assets 和文字规格，设定图、棋盘与场景直接消费这些已落盘结果，不再各自维护第二套配色规则。

- **配色比例**：LockedStyle 未明确比例时，默认以主色调 `65%`、配件色调 `22%`、警告色与道具色合计 `8%`、文字色与必要中性灰合计 `5%` 作为视觉面积参考；LockedStyle 已明确比例时逐字遵守。
- **颜色数量**：同页面主色调不超过 `3` 种，配件色调不超过 `2` 种，警告色不超过 `1` 种，道具色不超过 `1` 种，文字色与必要中性灰不超过 `2` 种。
- **角色分工**：UI 底板、主要玩法对象、图标、文字和特效分别承担明确视觉角色；每个项目补充一句来自核心名词、动作、情绪、风险或幽默感的色彩 DNA。
- **角色推导**：按“主色调 → 配件色调 → 警告色 → 道具色 → 文字色”逐项应用合同规定的颜色与范围；合同未穷举具体色值时可在同一色彩方向内补齐，但不得将一种角色的颜色挪给另一种角色或引入冲突色。
- **可读性与克制**：UI 容器实体填充面禁止白色、近白色；其它对象同样避免大面积纯黑或纯白。文字与实际背景保持清晰明度或色相差；所有角色依靠色相、明度、轮廓和材质区分，不使用发光边框、发光图标、发光文字、发光特效、光晕、辉光或霓虹材质。
- **UI 容器禁止彩色灰**：禁止使用深蓝灰、橙灰、紫灰、绿灰等带明显色相的灰色；灰阶只允许 `R=G=B` 的纯中性灰。除全局风格合同明确采用的柔和低饱和、同色系浅色或奶感色系外，非灰色元素只使用合同定义的完全饱和纯色；不得把 SVG 合同颜色误判为彩色灰，也不得擅自提高其饱和度。
  - 正确：纯中性灰 `#999999`、纯橙色 `#FF8800`，以及 SVG 合同明确规定的浅紫色、浅米色和清透奶感色。
  - 错误：合同未定义的深蓝灰 `#4B5A6C`、橙灰 `#C4A8A0`，以及其它通过降低饱和度自行补出的带色灰。

## 6. Visual Assets (PNG) 规范

`design_brief_ui.md` 的 Visual Assets 表只记录素材身份和生产规格。静态位置、尺寸、容器、对齐和锁定状态统一写入 `Scene Layout Plan`；运行时状态和显隐统一写入 gamelogic Brief。

表头为：`视觉资产 key / 素材类型 / 运行时用途 / 描述/用途 / 生成尺寸（宽×高） / 构图/朝向 / 配色/抠图色 / 生成约束`。`视觉资产 key` 必须包含 `.png` 后缀，不兼容旧表头或位置列。

### 6.1 资产类型与分组
- `gameplay_sprite`：角色、目标、危险、道具、投射物、收集物。
- `hud_bar`：仅供非测试型游戏使用的顶部横向信息底板，承载通过 HUD 准入检查的 `1~3` 段实时指标，或非测试型游戏确实需要底板承载的首屏标题。测试型小游戏不得使用该素材类型。
- `ui_container`：按钮、卡片、牌匾、提示牌、面板。
- `ui_icon`：小功能图标。
- `state_variant`：同一对象整体表面发生替换时使用，例如待机、激活、正确、错误、正面、背面；该类型直接替换原对象视觉，不能作为独立叠加边框、光圈、描边或提示框使用。
- `effect_sprite`：命中、爆发、爆炸、奖励、错误反馈，以及独立显隐或动画控制的选中高亮框、选中描边、选中光圈和聚焦边线。
- 高亮框类 `effect_sprite` 的视觉资产 key 必须写明结构，例如“选项选中细线高亮框.png”或“卡牌选中粗线描边.png”，不得只命名为“高亮框”。
- 其描述和生成约束必须明确写出“细线框”或“粗线框”及线宽范围；中心必须为连续透明通孔，通孔全部像素 alpha 必须为 `0`。
- 不透明像素只允许位于边框、角标或局部特效上；禁止实体填充、白底、半透明色块、蒙层、玻璃面、阴影填充、渐变填充和文字。此类素材不承担文字容器职责。
- 场景分组写入 `Scene Layout Plan.Scene Group`，优先使用 `背景`、`玩法`、`UI界面`、`结算界面` 或 `音频`；同批阶段性对象确需整体显隐时可使用职责唯一的中文分组。AR 透传不创建背景 PNG。
- 初始场景至少有一张生成 PNG 可见，每张 PNG 都有明确用途。

### 6.2 资产拆分与复用
- 每张 PNG 只包含一个不可拆分的视觉结构，不把需要独立控制的元素打包成组合图。
- 先按运行时内容和交互职责去重，再判断视觉资产复用。同一阶段内，同一运行时字段只能有一个主要可见载体；只有承担独立上下文、对照、预览或反馈职责时才允许额外载体，并必须明确职责差异。不得通过不同外观的气泡、卡片或面板重复展示同一内容。外观与交互职责完全相同的多个实例只输出一个通用视觉资产 key。
- `运行时用途` 记录通用资产对应的全部实例或复用场景；实例数量、排列方式、位置和对象关系写入 `Scene Layout Plan`。
- 尺寸、比例、轮廓、内部结构、功能图标、现实材质、视觉身份或状态表现不同时，建立独立视觉资产 key。
- 不同主题、人物、象征内容、结果语义或状态表现不得合并为通用 `state_variant`。
- 面板只表达容器自身形状、LockedStyle 表面、填充和结构；内部图标使用独立资产，文字使用运行时 Text。
- 隐藏或背面状态必须隐藏答案身份，不得留下淡标签、弱数字等线索。
- 每个运行时可见对象、交互对象、UI 容器、功能图标、状态变体、结果变体和事件特效必须拥有视觉资产 key 或明确复用来源。

### 6.3 生成与验收
- 每个 PNG 必须有唯一视觉资产 key、唯一视觉结构、明确用途和生成约束。
- Visual Assets 表不得包含逐素材生图 Prompt。
- `生成尺寸（宽×高）` 先定义素材最终保留主体全部可见像素的最小轴对齐外接矩形比例，同时作为棋盘目标主体比例、正式图片请求尺寸框和审核恢复尺寸。尺寸缺失时才回退棋盘 crop，不因此阻塞生成。
- 普通素材不得拉伸、压扁或用透明留白凑比例。透明边距裁剪后，将实际主体比例 contain 到 Brief 尺寸框并写入 `Assets/visual_asset_final.md`；Scene 最终只认该文件记录的宽高比和推荐尺寸。
- `hud_bar` 是唯一结构性拉伸特例：图片后处理先规范到固定 `640px` 宽、高度不超过 `122px`，Scene 使用规范后尺寸；栏内文字与图标仍按独立安全区排版，不随底板拉伸。
- 所有可读文案必须使用运行时 Text 对象，不得烘焙进 PNG。
- 方向敏感资产必须记录视角、朝向、旋转策略和对称性。
- 隐藏或背面状态必须隐藏答案身份，不得留下淡标签、弱数字等视觉线索。
- 禁止规划全屏边框、闭合外框、角括号环绕框或全屏装饰叠层 PNG。
- 新项目不得定义独立全屏装饰叠层类型，也不得用 `ui_container` 或其它类型包装全屏边框、镂空叠层或纯装饰闭合外框。
- 纯装饰边角、侧边花纹、螺帽、铆钉、图腾、符号和无功能光点不独立规划；承担文字承载、状态提示、结果区分或玩法反馈职责的功能性元素除外。
- 验收透明区、文字污染、朝向、裁切、轮廓、主体比例和状态覆盖。纯文字容器必须核对裁切后最终比例是否仍能满足已计算的文字容量；同一横向交互组中声明为相同尺寸的按钮、分类槽或投放目标，必须核对裁切后的主体比例和最终显示高度是否一致。比例漂移导致容器过高、文字安全区异常或同组无法等高时，将对应素材判定为不合格并重新生成，不得写入 `visual_asset_final.md`。
- 每个运行时可见对象、交互对象、UI 容器、功能图标、状态变体、结果变体和事件特效必须拥有视觉资产 key 或明确复用来源。
- 每个 UI 容器生成前检查实体填充面：禁止白色、近白色。
- UI 容器完成白底抠图后必须验收主体填充面、边缘和内部结构是否完整；出现主体缺失、边缘被吃掉或内部误透明时，必须先更换为合规容器色并重新生成，不得使用描边、阴影或后期补洞掩盖。

### 6.4 模板与阶段布局
- clone/纹理素材源保持不可见且未激活，只作为运行时素材源，不承载可读信息。
- 阶段性 UI 直接放在最终显示位置，通过显隐控制；不得当作离屏模板。
- 运行时玩法实例按 gamelogic Brief 的创建方式生成；只有 `offscreen_template` 或脚本明确通过 `add.image`、`add.sprite` 或运行时纹理替换引用的 `state_variant` 才创建独立模板对象，有限候选显隐切换时直接使用最终位置对象。
- 模板本身不参与可见阶段布局校验，运行时可见实例按对应阶段的最终外接矩形参与。
- 完整状态入口、清理、RecordStart、RecordEnd 和 Runtime Visibility Plan 只由 gamelogic Brief 定义；本 Reference 只据此判断每个关键阶段的同时可见集合。
- 同批阶段性 UI 优先归入独立 `Scene Group` 并按 group 级 `visible` 控制；单个独立对象才用对象级显隐，同一阶段不混用父 group 隐藏与子对象显示。

## 7. 重叠、叠层与间距

### 7.1 禁止重叠

适用于同阶段可见、彼此独立、语义职责不同的模块，例如：
- HUD 与独立提示。
- 按钮与按钮。
- 结果卡与另一块独立说明板。
- 不同复合构图单元的可读内容。
- 两个独立点击热区。
- 无底板的提示文案位置严禁与其他UI容器和主体重叠。
- 不得用层级覆盖、透明度降低或部分遮挡伪装“未重叠”。

### 7.2 允许叠层

UI Brief 在 `Scene Layout Plan.布局约束` 中记录为同一复合构图单元的对象允许按明确层级组合，例如：
- 容器底板与绑定文字、图标。
- 结果面板、面板内有结果角色、标题、解释和揭晓特效共同组成一个结果复合单元，强制按“面板 < 后景特效 < 结果角色 < 前景特效 < 文字”创建。必须在 Scene Layout Plan.布局约束 中逐字列出对象 ID 顺序，不能只在 Layer Composition Plan 中写抽象层级。
- 棋盘与棋子。
- 角色与附属状态标记或局部反馈特效。

允许叠层必须记录前后关系、语义归属、点击区域以及允许遮挡和禁止遮挡的部分；Scene Builder 按同组对象的创建顺序落地，容器先创建，内部图片、图标和文字依次创建。关键文字安全区、点击热区和主体识别区域不得被遮挡。

### 7.3 冲突判断

不得只根据矩形是否相交判断冲突，必须检查：
- 是否属于同一复合构图单元。
- 是否遮挡关键文字或破坏阅读顺序。
- 是否覆盖或混淆点击热区。
- 是否破坏语义归属。
- 是否颠倒视觉主次。
- 是否遮挡主体识别区域。

只有独立模块之间的非预期相交才判定为布局冲突。

### 7.4 最小间距
- 测一测顶部不建立“标题与题号组”，只保留一个独立大标题。标题、题目或上下文容器、选项卡、待操作对象和主要视觉主体等相邻独立内容单元之间固定为 `16px`；绑定在题目容器内部的题号不作为独立内容单元计算间距。不得将这些数值仅作为下限后继续任意放大。
- 测一测的人脸软避让不得改变上述纵向间距；通过保持顶部内容流紧凑，为其下方主内容区域留下连续人脸空间。
- 不属于测一测紧凑内容流的普通独立 UI 模块之间 `≥16px`。
- 普通独立文字与其它重要对象之间 `≥12px`。
- 主要玩法主体与独立信息栏、提示或说明之间 `≥24px`。
- 危险物与奖励物之间默认 `≥8px`。

### 7.5 分阶段布局事实
- Planner 按 gamelogic Brief 的 Runtime Visibility Plan 规划各阶段可能同时可见的对象；不会同阶段显示的互斥对象不参与彼此布局。
- 模板对象是否参与布局取决于对应阶段的实际可见性；固定坐标对象保持不动，冲突只通过未锁定对象解决。
- Scene Builder 按各关键阶段的同时可见集合校验最终布局，不只检查初始帧；该校验不改变状态、显隐或 Brief。

## 8. Agent 执行规则

### 8.1 Planner
- 将视觉功能、资产、文字对象、布局、容器关系、锁定状态和复合构图写入 UI Brief 的 `Scene Layout Plan`。
- 每行 `布局约束` 中明确 `锁定` 或 `未锁定`；不新增位置列。
- 将完整 Runtime Visibility Plan 及其状态、事件和清理写入 gamelogic Brief。
- 不得在 Brief 中重新定义本规范的固定坐标和组件规则；需要自包含时必须逐字继承，不得改值。

### 8.2 Scene Builder
- 按 `design_brief_ui.md`、`design_brief_gamelogic.md` 和本规范执行场景组装。
- 使用 UI Brief 已记录的固定位置、组件排版和文字安全区，并使用 gamelogic Brief 的 Runtime Visibility Plan 设置真实初始显隐和校验关键阶段；不在 Scene Assembly 中改写 Brief。
- 只能对未锁定对象执行自主布局、缩放、间距优化和避让。
- 首次生成 `sceneOps` 时直接读取 `Assets/visual_asset_final.md`，按其中最终宽高比和推荐尺寸一次计算每个 Image 的等比显示尺寸及位置；工具比例校正只承担防御性兜底。
- 先添加图片容器，再添加绑定 Text 和图标，并使用对应文字安全区和图标安全区。
- 结算面板必须遵守“结算面板、结果页面”规则，不得套用通用文字对齐替代。
- `hud_bar` 使用后处理规范尺寸；其它 Image 保持 `visual_asset_final.md` 比例，只做等比微调。

### 8.3 最终验收
Planner 先在 Brief 中闭合以下事实，Scene Builder 对最终 `sceneOps` 和关键阶段进行执行校验：
- 固定坐标、区域和完整外接矩形正确。
- HUD 与结算面板使用各自唯一组件规则。
- 文字、图标和点击区域位于对应安全区。
- Runtime Visibility Plan 与运行时状态和事件逐项一致。
- 每个阶段的禁止重叠、允许叠层和最小间距通过校验。
- 所有视觉资产有明确用途、复用来源和场景绑定。
- 不存在迫使下游自行猜测的空白、冲突数值或重复规则。
- 禁止展示暂停、静音、关闭、重试、分享、设置、帮助、聊天、好友、广告或活动弹窗等脱离核心玩法的 UI；只保留实际核心状态流需要的控件。
