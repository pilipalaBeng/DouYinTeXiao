## 0. 先说三条"推翻直觉"的平台实测结论（本方案的骨架）

这三条是我读完像塑音频子系统后发现的、**会直接改写音效设计手法**的事实。先摆在最前面，因为它们决定了后面所有方案长什么样。

### 结论 ①：AudioComponent **没有音高（pitch）/播放速率 API** → 「音高阶梯」不能运行时实现

证据：`workspace/APJS/AudioComponent.d.ts` 中 `AudioComponent` 对外只有
`loopCount` / `volume` / `duration`(只读) / `isFinished`(只读) / `play()` / `pause()` / `resume()` / `stop()`。
`knowledge/schemas/component_schemas.json` 里 `AudioComponent` 的**全部**属性为：
`resourcePath` / `audioRef` / `playMode(ONCE|LOOP|INFINITE)` / `audioType(BGM|AUDIO_EFFECT)` / `loopCount` / `autoPlay` / `mute` / `volume(0–100)` / `isMobilePreview`。
`APJS.d.ts:508` 的 `speed` 属于**动画**类，不是音频。
→ **全平台没有任何"改音频音高/变调"的接口。**

**推论**：连击叠音的「音高递增」必须**预烘焙成若干个不同音高的独立 mp3 文件**，运行时靠"换文件"实现，而不是改一个文件的音高。这条直接决定了第 3 节的方案形态。

### 结论 ②：**没有运行时换音频文件的 API** → 「1 个音频资产 = 1 个 AudioComponent = 1 个场景对象」

证据：`AudioComponent` 无 `audioRef` / `resourcePath` 的运行时 setter；`DynamicComponent`（`APJS.d.ts`）是空类，没有通用 `setProperty`。`audioRef` 只能通过编辑器 DSL `set_component` 绑定（`skills/ability/Audio/SKILL.md` 步骤 2–3）。
另据官方 SKILL 已核实的行为：**`play()` 打在正在播放的组件上 = 从头重播**；**同帧 `stop()` 后 `play()` 会被引擎塌陷成"什么都不做"**（这是官方明确记录的坑）。
→ **一个 AudioComponent 是"单声道且只能放一个片段"的**。要叠音（polyphony）必须有**多个** AudioComponent，各绑不同资产，由脚本轮转调用。

**推论**：本方案共需 **26 个音频场景对象**（24 个 SFX + 2 段 BGM）。这不是浪费，是这个平台的唯一做法。

> **✅ 已确认（tech-architect / 柯桥良，已写入 `node-plan.md` §1.3）**：26 个音频对象**不占「图层 ≤6」、也不吃粒子预算**。
> **成立的依据只有一条：音频对象无渲染器、无 draw call、不参与视觉绘制顺序 → 不落在 L1–L6 任何视觉绘制带。**
> ⚠️ 注意：**不能**用"`renderGroupType` 是 `Utility`/`Music` 所以不在 L1–L6"作为依据 —— 同为 `Utility` 的 `Basic Particles` 等 VFX **是有视觉的**。只有"无渲染输出"这一条成立。
> **挂法红线见 3.1.1**（`AudioRoot` 必须常驻 `enabled`）。

### 结论 ③：平台"混音架构"只有 **2 条总线**，且**没有 EQ / 压缩器 / 限制器 / 声像 / 侧链**

证据：`audioType` 只有 `BGM` 与 `AUDIO_EFFECT` 两个值 —— 这就是平台给的全部总线。
DSP 侧无任何接口。
→ **防削波（anti-clipping）不能靠"挂个限制器"，只能靠三件事：① 资产本身留 headroom ② 每个组件设 `volume`(0–100) ③ 脚本级"并发衰减"**。
另：**无 pan API → 所有音频做单声道（mono）即可**，立体声纯属浪费包体。

**推论**：第 4 节"混音架构"必须落到"资产级 headroom + 脚本级软件限幅"，并给出可执行的并发衰减表。

> 补充事实（对设计有影响）：平台音频检测模块暴露 `AudioSourceType.Music = "设备当前播放的音乐源"`（`AudioComponent.d.ts` / `Audio/SKILL.md`）。
> 这说明**"特效音频与用户/宿主音乐共存"是抖音场景下的预期情况**。→ BGM 必须做"低姿态混音"（详见 3.3 与 6.2）。这是本方案对产品层的一个上报点。

## 一、声音基调

### 1.1 听觉定位（一句话）

**"一台 8-bit 街机，被塞进了一个 30 秒的竖屏短视频里。"**
—— 明亮、有弹性、像素味十足、**响但绝不刺耳**、**凶但绝不恐怖**。

### 1.2 为什么是这个基调（三条推导）

1. **服务玩法定位**：这是个"AR 当枪、30 秒速通、打完想 @ 朋友"的爽感射击。声音的第一职责是**打击即时感**（游有方把"打击即时感"列为乐趣来源第 1 位），所以整体音色要**短、亮、有瞬态**，不要大混响、不要"电影感"铺底。
2. **服务播放场景**：特效跑在抖音录制流程内，**声音会被录进用户视频**，且大概率是**手机小喇叭外放**。→ 三条派生规则：(a) 不做 60 Hz 以下的低频能量（小喇叭放不出，只会变成浑浊与嗡鸣）；(b) 不做长混响（短视频里只会糊）；(c) 整局响度不做大起大落，避免突然变响让人摘耳机。
3. **服务合规红线**：游有方已把项目定性为"去暴力化"（无血、无惨叫、Boss 归零是"认输"）。音频侧必须**同构执行**：禁一切真实惨叫/兽吼/枪声，全部换成卡通化、玩具化、像素化的音色。详见第六节。

### 1.3 音色规范（跨全包统一，防"音效各自为政"）

| 维度 | 规范 | 理由 |
|---|---|---|
| 音色引擎 | **8-bit / chiptune**：方波（pulse，占空比 12.5% 亮 / 25% / 50% 厚）+ 三角波（bass）+ 噪声（percussion） | 与像素美术同构；程序化可控；零版权风险 |
| 律制 | **12 平均律，A 小调为全包主调**（BGM 与 Boss 演出音统一）；UI 音用 A 小调五声避免听感冲突 | 全局同调 → 任意两个音叠在一起不"打架"（连击叠音的关键前提） |
| 频段分配 | 命中/开火 **600 Hz–5 kHz**（最亮的作战频段）；Boss 演出 **110–500 Hz**；UI **900–2 kHz**；BGM 走 **110 Hz–4 kHz** 全频但低姿态 | 让"信息优先级最高的命中音"独占最易辨识的频段 |
| 混响/延迟 | **不用混响**；允许 ≤60 ms 单次短延迟（仅 Boss 咆哮用，制造"体积"） | 短视频场景 + 省包体 + 避免糊 |
| 单声道 | **全部 mono** | 平台无 pan API；mono 省一半体积 |
| 采样率 | **44.1 kHz**（首选）/ 22.05 kHz（备选，更"8-bit"） | 44.1 kHz 兼容性最好；22.05 kHz 的 11 kHz 带宽对 chiptune 完全够 |
| 禁用的音色手法 | 真实兽吼、失真金属、人声采样、长混响铺底、jump-scare 突袭 | 合规（见第六节）+ 体验 |

### 1.4 情绪基线

- **阶段 1（常态试探）**：轻松的"教学感"。音乐密度低（八分音符），音效干净 → 玩家心态是"喔，我能打中"。
- **阶段 2（暴怒）**：节奏密度翻倍、音色变厚、加入小二度/增四度不安音 → 压力上来，但**BGM 旋律仍是同一动机**（"同一首歌变凶了"，不是"换了首歌"）。
- **阶段 3（护盾/假死）**：**BGM 不再变化**（沿用暴怒段），靠 SFX 讲故事 —— 破盾"咔啦"、假死识破"叮叮"、认输下行三音、胜利上行 jingle。**音效在这个阶段承担全部叙事**。
- **关键反差场景（重点设计）**：`命中"啪"的密集 → 突然的破盾"咔啦" → 咆哮"嗯——哇！"→ 认输"嘟-嘟-嘟↓"→ 胜利上行 jingle`。这条从"密集高频打击"到"低频仪式感"的动态落差，就是本特效的情绪高潮曲线。

### 2.3 逐条音效设计细节（合成思路 / 包络 / 频率走向）

> 包络记法：`A` = attack 时长，`D` = decay 时长（到 -40 dB 的时间）。峰值单位 dBFS（相对满刻度）。
> **所有资产在导出前统一做"非归一化"处理**：让峰值落在表中数值，**不要把每条都拉到 0 dBFS**（详见 4.1）。

#### (a) 命中类（★ 打击感核心）

| 文件 | 音色 / 合成思路 | 包络 | 频率走向 | 时长 | 峰值 | 备注 |
|---|---|---|---|---|---|---|
| `sfx_hit_light_*` | 噪声层（带通 2–5 kHz，占 70%）**叠**方波层（600 Hz，占 30%） | A **0.5 ms** / D 140 ms（指数，τ≈40 ms） | 方波固定 600 Hz 为基准档；阶梯档由**离线整体变调**派生（噪声层随之整体上移 → 保证 4 档音色一致，只是"音高"变） | 140 ms | **−9 dBFS** | 短促、脆、有"啪"的实体感。0.5 ms attack 是"打击感"的来源，不能软化 |

## 三、分层与触发规则（含 ★ 连击叠音设计）

### 3.1 音频对象架构（受结论 ①② 强约束）

**架构铁律：1 个音频资产 = 1 个 AudioComponent = 1 个场景对象，运行时无法换绑。**

因此按"用途池"建对象，脚本按下标轮转 `play()`：

| 用途 | 对象名 | 数量 | 绑定资产 | 归属总线 | playMode |
|---|---|---|---|---|---|
| BGM 常态 | `BGM_P1_Normal` | 1 | `bgm_p1_normal` | `BGM` | `INFINITE` |
| BGM 暴怒 | `BGM_P2_Enrage` | 1 | `bgm_p2_enrage` | `BGM` | `INFINITE` |
| **命中·轻击池** | `Sfx_Hit_L1..L4` | **4** | `sfx_hit_light_1..4` | `AUDIO_EFFECT` | `ONCE` |
| **命中·重击池** | `Sfx_Hit_H1..H3` | **3** | `sfx_hit_heavy_1..3` | `AUDIO_EFFECT` | `ONCE` |
| **开火池** | `Sfx_Gun_1..3` | **3** | `sfx_gun_shoot_1..3` | `AUDIO_EFFECT` | `ONCE` |
| 唯一音效（各 1 个） | `Sfx_<Name>` | 14 | 其余 14 条 SFX | `AUDIO_EFFECT` | `ONCE` |
| **合计** | | **26** | | | |

> 14 个"唯一音效" = land / roar / surrender / taunt / result_lose / result_win / gun_empty / gun_reload / shieldbreak / **shieldup** / crosshair / lock / click / combo_up。
> 其中 result_win / result_lose / surrender / taunt 互斥（不同终局状态），但因为**无法换绑**，仍各占一个对象。

**为什么命中要 7 个对象而不是 1 个**：这是"音高阶梯"和"叠音"两个需求在同一机制里的解 —— 见 3.2。

### 3.1.1 音频对象的挂法（★ 硬红线，与柯桥良 `node-plan.md` 对齐）

26 个音频对象统一挂在**常驻容器 `AudioRoot`** 下（Empty Object，非视觉、不占层），满足官方"结构收敛"要求。**三条必须照做，否则踩坑**：

1. **`AudioRoot` 必须常驻 `enabled`，且独立于任何状态页 / 视觉父节点。**
   原因：官方 Pitfall —— **父节点被 `setEnabledInHierarchy(false)` 会级联禁用所有子对象**。
   → 若把音频挂到 `StatePages`（READY / WIN / LOSE / RESET）或任何会切换显隐的视觉根下，**切页 / 开拍 / 结算时会把音频一起关掉 → 音频直接消失**。这是本项目音频侧最容易踩的一个坑，主程序接需求时务必注意。
2. **不要挂到 `ContentRoot`（震动父节点）下**，保持语义解耦 —— 音频不参与视觉震动，挂进去只会在代码上误导后续维护者。
3. **不占图层 / 不占粒子**：音频对象无渲染器、无 draw call → 零视觉开销；26 个是"场景对象数"开销（非图层、非粒子）。

> 待实测补充：平台是否对**场景对象总数**设上限。当前未见明文上限；若构建/提审报"对象数限制"，再考虑合并对象（但受结论 ② 约束，合并空间有限 —— 无法换绑资产就意味着很难压缩对象数）。

### 3.2 ★ 连击叠音设计（核心交付）

**问题重述**：射速 4 发/秒、combo 可达 24（过热前），若能连击 10+ 秒就是 40+ 发。若每发都独立播同一条音效 → 听觉上变成 4 发/秒的机械噪声墙，且全部同音高会"黏"成一个持续音，完全丢失"打击感"。

**方案总纲（4 条机制同时生效）**：

#### 机制 1 —— 音高阶梯：**预烘焙 4 档**（不是运行时变调）

受结论 ① 限制，音高只能靠"换文件"。所以把 `sfx_hit_light` 预烘焙成 4 个音高档，`sfx_hit_heavy` 预烘焙 3 档：

| 档位 | 轻击文件 | 音高偏移 | 倍频比 | 重击文件 | 音高偏移 | 倍频比 |
|---|---|---|---|---|---|---|
| 1 | `sfx_hit_light_1` | **0 半音（基准）** | 1.000× | `sfx_hit_heavy_1` | 0 半音 | 1.000× |
| 2 | `sfx_hit_light_2` | **+2 半音** | 1.122× | `sfx_hit_heavy_2` | +2 半音 | 1.122× |
| 3 | `sfx_hit_light_3` | **+4 半音** | 1.260× | `sfx_hit_heavy_3` | +4 半音 | 1.260× |
| 4 | `sfx_hit_light_4` | **+6 半音（★上限）** | **1.414×** | — | — | — |

- **上限 = +6 半音（1.414×）** 是硬规定，理由有三：(a) 阶梯不设上限会在十几发后升到"啸叫"，刺耳且像 bug；(b) +6 半音是"明显在升"与"仍然好听"的交界；(c) **不使用"无限递增"路线**，因为平台无变调 API，无限递增在物理上就得无限生成文件。
- **阶梯派生方式（重要，决定质量）**：只做 1 档的"基准设计"，其余档用**离线变调**从基准档派生（DAW 的 Change Pitch，或 `ffmpeg -af asetrate=...:atempo=...`），**不要**让 AI 分别生成 —— AI 无法保证"同一音色、精确 +2 半音"。这样 4 档音色严格一致，只有音高不同。

#### 机制 2 —— 轮转派发 = 音高阶梯 + 叠音"一箭双雕"

脚本维护 combo 计数 `c`（命中 +1；脱靶、超时、换弹、弹幕命中致盲 → 归零）。

```
档位选择：c ≤ 9 → 轻击池；c ≥ 10 → 重击池（★ 切"打击更重"的样本）
池内下标：idx = (c − 1) mod 池大小
派发：播放 池[idx]
```

**由此得到的音高走向（无需额外逻辑）**：
- 轻击期（c=1..9）：`0 → +2 → +4 → +6 → 0 → +2 → +4 → +6 → 0` —— 一个 **4 音上行循环，1 循环 = 4 发**。
  （循环时长随射速而定：250 ms 间隔 → **1.00 s**；220 ms 间隔 → **0.88 s**。★ 见 3.2.2「射速口径不敏感」证明。）
- 重击期（c≥10）：`0 → +2 → +4 → 0 …` —— 3 音上行循环。

**为什么"循环上行"比"单调升到顶再卡住"更好听**：在 4 发/秒下，4 音上行 = 每秒完成一次"旋律单元"，听觉上是一条**持续向上滚动的节奏 Riff**（很爽、很像街机连击）；如果做成"6 发升到顶然后一直卡在最高音"，就会变成"持续尖叫 + 突然不动"，又刺耳又呆。这是本方案刻意选"循环"而非"单调阶梯"的原因。

**同时，轮转天然解决了叠音**：
- 稳态下（4 发/秒、每发 140 ms），每个槽被重触发前它的片段早已播完 → **稳态零重叠**，不会累积能量造成削波。
- **同一帧出现 2 次命中**（阶段 2 打中 Boss + 小怪，或双目标）时，轮转会把它派给**两个不同的槽** → 自然叠成 2 个不同音高的音 → **"连续命中要有叠音"的需求在这里被满足**，而且听起来是"和弦"而不是"加倍的同一个音"。
- 同帧第 3 发：**丢弃**（只计 combo、不出声），保证不爆。

#### 机制 3 —— 同帧/并发硬上限 + 优先级丢弃（替代"限制器"）

| 参数 | 值 | 说明 |
|---|---|---|
| **同帧最大新启动音效数** | **2** | 第 3 个起只计 combo、不发声。防"一帧内多目标命中"叠爆 |
| **轻击池并发上限** | 3 | 由 4 槽轮转天然限流，脚本额外兜底 |
| **重击池并发上限** | 2 | 重击时长 250 ms，4 发/秒下最坏 1 并发，留 1 冗余 |
| **开火池并发上限** | 2 | 同上 |
| **全局 SFX 并发上限** | **4** | 超出时按优先级丢弃（不打断，只"不启动"） |
| **去抖**：`ui_lock` | 0.4 s | **命中态**在容差窗边缘会反复进出，必须去抖，否则"嘀嘀嘀"烦人 |
| **去抖**：`gun_empty` | 0.25 s | 空仓连点不能每点"咔"一次 |
| **去抖**：`combo_up` | 仅 c=10、c=20 各一次 | 不做"每 10 连击一次"的循环 |

**优先级丢弃规则**（脚本内执行，不是运行时打断）：
```
新事件到达时：
  if (全局并发 < 4) → 直接启动
  else if (新事件优先级 > 当前并集中最低优先级者) → 丢弃那个最低者（不 stop，等它自然播完）
  else → 丢弃新事件
```
- P0（绝不丢弃）：`result_win` / `result_lose` / `shieldbreak` / `shieldup` / `roar`
- P1：`hit_*` / `gun_shoot` / `gun_reload` / `gun_empty` / `boss_land` / `boss_surrender`
- P2（先被丢）：`ui_lock` / `ui_crosshair` / `combo_up` / `boss_taunt`
- P3（最先丢）：`ui_click`
- **唯一例外（可硬 stop）**：终局三音（`result_win` / `result_lose` / `boss_surrender`）起播时可硬 `stop()` 掉所有 P1/P2 SFX —— 终局必须干净。因为硬 stop 会咔哒，所以只允许在这一处用。

#### 机制 4 —— 音量抖动 + 脚本级软件限幅（替代压缩器/限制器）

- **音量抖动**：每次命中，该槽 `volume = 100 − randInt(0, 12)`（≈ 0 ~ −1.6 dB 抖动）。这是"同一动作 ≥3 变体 + 音高/音量随机化"里的音量随机化部分。**注意**：抖动范围故意做小（≤1.6 dB），因为 4 发/秒下大幅音量抖动会听成"忽大忽小"的故障感。
- **软件限幅（并发衰减表）**：平台无压缩器，所以削波只能靠脚本。规则：

| 同时播放的 SFX 数 n | 参与并发的每个 voice 的 volume 系数 | 等效衰减 |
|---|---|---|
| 1 | ×1.00 | 0 dB |
| 2 | ×0.72 | −2.8 dB |
| 3 | ×0.58 | −4.7 dB |
| ≥4 | ×0.50 | −6.0 dB |

  → **最坏相干叠加验算**：`hit_heavy`(−8 dBFS) + `hit_light`(−9) + `gun_shoot`(−12) 三声，各乘 0.58 后相干叠加峰值 ≈ **−3.2 dBFS**，安全落在 −1 dBFS 目标之下。**这张表必须实现，不能省**（见第 9 节验收项 3）。

| 并发衰减系数 | n=1:1.00 / n=2:0.72 / n=3:0.58 / n≥4:0.50 | 软件限幅，防削波 |
| 阈值提示音 | combo=10、combo=20 各播一次 `sfx_combo_up` | P2，可被丢弃 |
| combo 归零条件 | 脱靶、超时未命中、换弹开始、被弹幕致盲 | — |

#### 3.2.2 射速口径不敏感 —— 本音频设计对「4 发/秒」与「220 ms 冷却」**都成立**（证明）

**背景**：游有方数值表同时给了"射速 4 发/秒"与"单发冷却 220 ms"，而 `1/0.220 = 4.545 发/秒` —— 两者不自洽（QA 已登记为 `D-04` / `O-16`）。**已收口：闸门 = `250ms`**（原 220ms 已否决，见 `game-design` L139）。
**本方案结论：音频无需等这个口径定稿就能落地**，因为两种取值下稳态行为完全一致：

| 池 | 槽数 | 片段时长 | **220 ms 间隔** → 单槽重触发周期 | **250 ms 间隔** → 单槽重触发周期 | 稳态是否重叠 |
|---|---|---|---|---|---|
| 命中·轻击 | 4 | 140 ms | 4 × 220 = **880 ms** | 4 × 250 = **1000 ms** | **从不重叠**（880 ≫ 140） |
| 命中·重击 | 3 | 250 ms | 3 × 220 = **660 ms** | 3 × 250 = **750 ms** | **从不重叠**（660 ≫ 250，余量 410 ms） |
| 开火 | 3 | 100 ms | 3 × 220 = **660 ms** | 3 × 250 = **750 ms** | **从不重叠** |

**推论**：
1. **稳态零重叠**在两种射速下都成立 → **削波风险不变**，3.2 机制 4 的并发衰减表无需改动。
2. **同帧最多启动 2 / 全局并发 ≤4** 是**与射速无关**的硬上限 → 依然有效。
3. 唯一随射速变化的是**音高循环时长**（4 发一循环 = 880 ms @220ms / 1000 ms @250ms）—— 这是"更快或更慢地滚一遍上行"，**两种都成立、无优劣**。
4. 开火音 100 ms ≤ 单发间隔的一半（110 ms @220ms / 125 ms @250ms）→ **两种口径下都满足**（我原稿按更严的 220 ms 写的，已天然合规）。

→ **对 QA 的 D-04 / O-16 的意义**：射速口径是**玩法数值问题**（谁定闸门），**不是音频风险**；音频侧可从该风险的"影响面"里划掉。**（该口径已收口为 `250ms`，见 §3.2.2 背景注。）**

### 3.3 BGM 设计

#### 3.3.1 风格取向

**纯 NES 风格 chiptune，4 声道**：`方波 1 = 主旋律` / `方波 2 = 和声或琶音` / `三角波 = 贝斯` / `噪声 = 鼓`。
不引入采样音色、不引入管弦、不做电影化铺底 —— 与 DB16 像素美术同构。

#### 3.3.2 结构、时长、循环点

| 项 | 常态段 `bgm_p1_normal` | 暴怒段 `bgm_p2_enrage` |
|---|---|---|
| 调性 | **A 小调** | **A 小调**（同主音，不换调） |
| 速度 | **120 BPM**，4/4 | **120 BPM**，4/4（★ 与常态段**同 BPM**，这是能"对齐切换"的前提） |
| 长度 | **8 小节 = 16.0 s** | **8 小节 = 16.0 s** |
| 和声 | i–VI–III–VII 循环 | 同和声，但**加小二度倚音与增四度经过音** |
| 方波占空比 | 12.5%（明亮、轻快） | **50%（厚、凶）** |
| 节奏密度 | 八分音符为主 | **十六分音符持续跑动（密度翻倍）** + 噪声改十六分军鼓 |
| 贝斯 | 三角波单根音，四分音符 | 三角波八分音符推动 |
| 循环点 | 第 8 小节末拍为过门（fill），**尾音在第 8 小节第 4 拍前完全衰减**（不留混响尾巴越界）；第 1 小节第 1 拍为强拍起音 | 同 |

**★ 速度感靠"密度"而不是"改 BPM"**：这是关键设计选择。如果暴怒段改成 132 BPM，两段的小节网格就不同，切换只能硬切在拍中间（会听出"跳曲"）；保持 120 BPM 则两段共用同一时间网格，**可以在任意拍点对齐切换**，听感是"同一首歌编曲变凶了"。

#### 3.3.3 单局只有 20–40 s，BGM 要不要做成完整曲子？—— **不要**

**判断：不做完整曲，只做两段各 8 小节（16 s）的无缝 loop。理由（四条）**：
1. **放不完**：完整曲（60–90 s）在 20–40 s 的单局里永远播不到一半，投入产出比为负。
2. **有终点**：BGM 在阶段 2 就被换成暴怒段，实际播出窗口 ≤ 玩家打掉 66% 血的时间；完整曲的"第二主题/桥段/结尾"根本用不上。
3. **重复次数有限**：最短局 12 s（BGM 只播 0.75 个循环）；最长局 40 s 且卡在常态段（BGM 循环 2.5 次）。16 s 的 loop 在这两种极端下都成立 —— 12 s 局听不到循环，40 s 局最多听 2.5 次，**重复疲劳风险低**。
4. **省包体**：BGM 是音频里最大的两笔（各 128 KB）。做完整曲只会成倍放大而收益为零。
→ **仪式的收尾（WIN 的完成感）由 `sfx_result_win` 的 2 s jingle 承担，不需要 BGM 写结尾。**

#### 3.3.4 变奏怎么切？—— **同网格「最近拍线硬切 + roar 掩蔽」**

**方案**：在阶段 2 触发时切 BGM，切点**量化到最近的"拍"线**（0.5 s 网格），并用 `sfx_boss_roar`（1.0 s）盖住接缝。实现上先 `stop()` 常态段，**下一帧**再 `play()` 暴怒段（★ 必须分帧，平台已核实同帧 stop+play 会被引擎塌陷，见官方 Audio SKILL）。

**为什么不用交叉淡化（crossfade）**：
1. 平台 **没有内置淡入淡出 API**，交叉淡化必须靠脚本逐帧改 `volume`，实现成本与抖动风险都高；
2. chiptune 两轨交叉会让**两条贝斯线重叠**，听上去浑浊、像"卡带";
3. 两段同 BPM 同网格 → 硬切本身就是"编曲变化"，是 chiptune 的标准语汇（街机游戏换段落就是这么干的）。

**为什么量化到"拍"而不是"小节"**：小节线是 2.0 s，若切点等下一个**小节**线，最坏要等 2.0 s —— 视觉上"眼睛已经红了、画面已经震了"，音乐却 2 秒后才变，玩家会感到"声画不同步"。量化到拍 → 最大等待 **0.5 s**，可接受。
→ **前提约束（给程序/动画）**：常态段所有声部必须**按拍量化且无跨拍长音**，否则在拍上硬切会出现咔嗒。这条要写进 BGM 制作要求。

**降级路径**：若实测发现低端机帧率导致脚本无法在 0.5 s 内完成切换 → 退化为**"暴怒触发帧立即硬切"（0 延迟）**。因为两段同网格，切在任意拍上仍然"合拍"，只是不落在整拍点，听感略糙但可接受。

#### 3.3.5 BGM 与用户音乐的冲突（★ 需产品决策）

**事实依据**：平台音频检测暴露 `AudioSourceType.Music = "设备当前播放的音乐源"` —— 说明**"特效音频与宿主/用户音乐共存"是平台预期场景**。抖音用户极可能在剪辑里叠自己的热门 BGM。

**风险**：我们的 BGM 会与用户的音乐打架，且特效不联网、无法感知用户是否在放歌。

**本方案的处理（三层）**：
1. **低姿态混音**：BGM 混音峰值压到 **−16 dBFS** 级（见 4.2），刻意避开低频轰鸣区，**不写"会抢戏的强旋律钩子"** —— 用节奏型 + 轻旋律，保证"有它更好、没它也行"。
2. **必须提供开关（v1.4 定案）**：`mute` 属性**运行时不可改**（team-lead 定案）→ **全局静音 = 遍历 26 个 `AudioComponent` 设 `volume = 0`**（幂等、可逆，恢复时写回原 volume）；**"关闭音乐" = 只对 2 个 `audioType=BGM` 组件设 `volume=0`**。结算页 / 暂停页提供这两个入口。
3. **✅ team-lead 已裁决：BGM 保留，不砍。**
   依据：包体实测 ≈1.45 MB < 2 MB，余量充足；已做低姿态混音 + 关闭开关；需求 14 明确要求 BGM。**砍 BGM 属设计变更，不应由体积驱动**，而体积当前不告急。

> **🔻 BGM 降级登记（显式保留的降级路径，仅一行）**
> **`bgm_p1_normal` + `bgm_p2_enrage` 是「真机体验不佳时的第一顺位砍项」。**
> 触发条件：真机实测发现 **BGM 与用户音乐打架严重**（听不清命中音 / 整体浑浊）或影响完播。届时由 **游有方** 拍板砍（设计变更），砍掉后音频从 349 KB 降至 **93 KB**、26 对象降至 24，**打击感 100% 不受影响**（全部音效保留）。
> 在此之前 **不动** —— BGM 保留，逐级降级顺序为：先降码率 64→48 kbps（−64 KB）→ 再缩短至 8 s（−128 KB）→ 最后整段砍。

### 3.4 与 animation-spec 对齐点映射（跨文档收口）

`animation-spec` 给音频提了对齐需求："`HURT` 每发命中；**'咚 / 当 / 咔 / 叮铃'**分别对齐 `SPAWN f5` / `SHIELD_UP f4` / `RELOAD 上膛` / `DEFEAT f8`"。逐条映射如下（**三条对齐，两条我做了解释性调整**）：

| animation 需求 | 对齐点 | 本方案的资产 | 状态 |
|---|---|---|---|
| 落地"**咚**" | `SPAWN f5`（触地冲击） | `sfx_boss_land` | ✅ 直接对齐 |
| 护盾"**当**" | `SHIELD_UP f4`（盾到位） | **`sfx_boss_shieldup`（新增命名）** | ✅ 已对齐，见下 |
| 换弹"**咔**" | `RELOAD 上膛` | `sfx_gun_reload`（3 声咔嗒，末声 = 上膛 +3 半音） | ✅ 直接对齐（我的 0/300/600 ms 三声里末声语义即"上膛"） |
| 胜利"**叮铃**" | `DEFEAT f8` | **并入 `sfx_result_win` 的颗粒层** | ⚠️ 我改为**合并**（见 2.3 (c) 的说明），不新增独立资产 |
| 命中（每发 `HURT`） | 命中判定帧 | `sfx_hit_light_*` / `sfx_hit_heavy_*` | ✅ 直接对齐 |

**两条调整的理由（需要 animation-director 确认）：**
1. **护盾"当"→ 命名定为 `sfx_boss_shieldup`**（原稿我自造的 `sfx_phase_switch` 已废弃）。因为阶段 2→3 的机制变化本身就是"开护盾"，"盾成形的当"天然就是阶段切换提示音；若再叠一个抽象的"扫频切换音"，两个音会在同一帧互相糊掉。**合并后资产数不变（仍 24）**，且与你的 `SHIELD_UP f4` 精确对齐。
2. **彩带"叮铃"→ 合并进 `sfx_result_win`**，理由同 2.3 (c)：同帧同事件，拆开只会多占一个对象（而对象数正有上限风险）且必然重叠。

**另外两条纪律（给程序，也请 animation 侧知悉）：**

**★ 纪律 1（v1.3 新增，team-lead 拍板，与 `animation-spec §5.5` 对齐）—— 动画序列驱动音必须挂"动作播放时钟"，不是墙钟。**

`BossAnimPlayer` 按**累计非暂停播放时长（played-time）**驱动派发，**hitstop 期间同步冻结** → **音效与视觉帧永远严丝合缝**。我方**只登记"播放时刻(ms)"**，**不自己算墙钟**；`BossAnimPlayer` 累计播放时长跨过该毫秒时回调音效 `play()`：

| 播放时刻(ms) | animation mark | 我的音效 | 说明 |
|---|---|---|---|
| **100** | `shield_set` | `sfx_boss_shieldup` | 护盾成形"当"（与 `SHIELD_UP f4` 同一拍） |
| **333** | `spawn_land` | `sfx_boss_land` | 落地"咚"（与 `SPAWN f5` 同一拍） |
| **600** | `flag_drop` | *（暂不新增资产）* | 旗帜升起点；无独立音需求，视觉驱动即可 |
| **950** | `flag_land` | **牌子"啪落地" → 触发 `sfx_result_win`**（该资产的颗粒层即"叮铃"） | 见 §2.3(c)（**已定案：不独立**，守 26 对象）。时刻以 animation 权威表 `§5.2` 为准：`flag_drop` 600 → **`flag_land` ≈950** → `win_card` ≈1100 ms |

> **为什么不能用墙钟（这条对我尤其致命）**：破盾/命中都有 hitstop（普通 **50** / 破盾 **83** / 击杀 **0 ms**，已定案）→ 若按墙钟累加，动画序列里**每个后继音会整体漂后一个冻结窗**。例：`flag_land` 若在其之前吃过一次 50 ms 破盾 hitstop，墙钟应算 **1000 ms** 而非 950 ms；按 played-time 则永远是 950 ms。**结论：动画序列音一律登记播放时刻，冻结窗自动对齐。**

**⚠️ 纪律 1 不波及判定驱动音**：`sfx_hit_*` / `sfx_gun_shoot_*` / `sfx_gun_empty` / `sfx_combo_up` / `sfx_ui_*` 仍由脚本在**判定帧 / 输入帧**直接触发，**与动画时钟无关**（详见 7.2 / 7.3）。两类触发源**不要混用**。

**纪律 2（保持）—— 不得监听 AnimationEvent（引擎帧事件）。**

animation-spec 里标注的 `f#★` 对齐点是**给程序的对齐参考**，**不是"动画事件触发器"**。
- ✅ **正确触发源** = `BossAnimPlayer` 的**播放时钟回调**（脚本侧按累计播放时长跨点调度）。
- ❌ **错误触发源** = 引擎 **AnimationEvent**（帧事件时序可能晚 1–2 帧 → 音频延迟 33–66 ms → 直接"发飘"，见 7.3 第 2 条）。
- 两者是**不同机制**（一个是脚本侧计时器回调，一个是引擎帧事件），**不要混用**。

## 四、混音架构

### 4.1 平台真实可用的"混音台"（先划清能力边界）

| 能力 | 平台是否支持 | 依据 |
|---|---|---|
| 两条总线：`BGM` / `AUDIO_EFFECT` | ✅ 支持 | `AudioComponent.audioType` 枚举（`component_schemas.json`） |
| 每组件音量 0–100 | ✅ 支持（运行时可通过脚本改） | `volume` 属性 + `APJS.AudioComponent.volume` |
| 全局静音 | ✅ 支持（**走 `volume`，不用 `mute`**） | `mute` **运行时不可改**（已定案）→ 静音 = 遍历 26 个 `AudioComponent` 设 `volume = 0`；"关音乐" = 只设 2 个 BGM 组件 |
| BGM / SFX 独立音量 | ✅ 通过 `volume` 分设 | — |
| **压缩器 / 限制器** | ❌ **无 API** | — |
| **EQ / 滤波** | ❌ **无 API** | — |
| **混响发送** | ❌ **无 API** | — |
| **声像 / 3D 空间化** | ❌ **无 API** | → 故全包 mono |
| **侧链 / 闪避** | ❌ 无内置 → **只能脚本改 volume 实现** | — |
| **淡入淡出 / 交叉淡化** | ❌ 无内置 → **只能脚本逐帧 lerp volume** | — |

**结论**：本项目的"混音架构"= **资产级 headroom 设计 + 组件级 volume 分层 + 脚本级软件限幅/闪避**。没有任何"挂个总线处理"的捷径。

### 4.2 总线与响度目标

| 总线 | 承载 | 组件 `volume` | 资产峰值 | 混音后目标峰值 | 说明 |
|---|---|---|---|---|---|
| `BGM` | 2 段 BGM | **30**（≈ −10.5 dB） | −6 dBFS | **≈ −16.5 dBFS** | 低姿态；闪避时降到 20（≈ −3.5 dB 闪避） |
| `AUDIO_EFFECT` | 24 条 SFX（26 − 2 BGM） | 见 2.3 表 | −4 ~ −18 dBFS | 单发 ≈ −9 dBFS 级 | 命中音比 BGM **高出 ≥6 dB**（验收项 14） |
| **主输出** | 两者相加 | — | — | **≤ −1.0 dBFS** | 硬目标；靠 3.2 机制 4 的衰减表保证 |

**整体响度参考（移动短视频场景）**：整局集成响度落在 **−18 ~ −14 LUFS**。理由：会被录进用户视频 + 手机外放，过响会让人调小音量甚至划走；过轻则"打击感"消失。

`volume` → dB 换算速查（若 `volume 100 = 0 dB` 线性）：

| dB | −2 | −3 | −4 | −6 | −8 | −10 | −12 | −14 | −16 | −18 |
|---|---|---|---|---|---|---|---|---|---|---|
| volume | 79 | 71 | 63 | 50 | 40 | 32 | 25 | 20 | 16 | 13 |

### 4.3 优先级与打断规则

- **优先级分级**：见 2.1 表的"优先级"列（P0–P3）。
- **实现方式**：脚本维护"当前播放中的 SFX 槽"集合；新事件到达时按 3.2 机制 3 的规则**选择"不启动"还是"抢占名额"**。
- **不做运行时打断**：原因 —— 唯一能停的手段是硬 `stop()`，会产生咔哒声；除终局三音外一律不打断。
- **唯一可硬 stop 的场景**：`result_win` / `result_lose` / `boss_surrender` 起播时，可硬停掉所有 P1/P2 SFX（终局必须干净）。
- **BGM 闪避（ducking）**：只在 **P0/P1 重事件**（`shieldup` / `shieldbreak` / `roar` / 终局）触发：BGM 组件 `volume` 30 → 20（约 −3.5 dB），150 ms 后线性回升。**命中轻击不闪避** —— 4 发/秒下逐发闪避会让音乐"抽气"（pumping），比不闪避更糟。

## 五、音频规格与命名

### 5.1 格式与压缩（先给依据）

**唯一可用格式 = MP3。**
依据：资源 schema 中音频类型只有 `ResItemMP3`，`extnames: [".mp3"]`（`knowledge/schemas/resource_type_schemas.json:1779+`）；全库所有音频示例路径都是 `.mp3`（`skills/ability/Audio/SKILL.md`、`VFX/SKILL.md`、`MP4/SKILL.md`）；平台内置 `generate_audio` 的产物也是 MP3。**全库没有任何 `.wav` / `.ogg` 的引用。**
→ 所以不存在"wav 保瞬态 / ogg 无缝循环"的选项，**MP3 是唯一选择**，设计和体积核算都按 MP3 来做。

| 类别 | 格式 | 采样率 | 声道 | 码率 | 播放模式 | 总线 |
|---|---|---|---|---|---|---|
| 短促音效（≤300 ms：hit / shoot / empty / click / crosshair / lock / combo_up） | MP3 CBR | **44.1 kHz** | **单声道** | **64 kbps** | `ONCE` | `AUDIO_EFFECT` |
| 中长音效（>300 ms：land / roar / surrender / taunt / reload / shieldbreak / shieldup） | MP3 CBR | 44.1 kHz | 单声道 | **64 kbps** | `ONCE` | `AUDIO_EFFECT` |
| 结算音（win / lose） | MP3 CBR | 44.1 kHz | 单声道 | **64 kbps** | `ONCE` | `AUDIO_EFFECT` |
| **BGM** | MP3 CBR | 44.1 kHz | 单声道 | **64 kbps** | **`INFINITE`** | **`BGM`** |

- **为什么 CBR 而不是 VBR**：短促打击类音效需要**可预测的帧长与稳定的瞬时响应**；VBR 在极短文件上帧长波动，且不利体积核算。CBR 简单可预测。
- **为什么 64 kbps**：chiptune 是方波/噪声，频谱极简单，64 kbps mono 对它而言是"高配"。再高纯属浪费包体。
- **为什么单声道**：平台无 pan / 3D 空间化 API（见 4.1），立体声只会在两声道里存一份几乎相同的数据 → 纯浪费一倍体积。
- **关于 MP3 的两个已知副作用（必须写进给程序的说明）**：
  1. **编码器固有延迟 ~13–25 ms**：所有 MP3 都有，且每个文件一致 → 是"全局统一延迟"，不破坏音效之间的相对同步，但会**推高端到端延迟**（见第七节）。
  2. **MP3 循环不是样本级无缝**：`playMode=INFINITE` 循环时可能有极短接缝。本方案已用"尾部不越界 + 首拍强起"在**资产层面**缓解，但**最终必须真机听审**（第 10 节待实测 ③）。

### 5.2 音频总体积核算（★ 必须回答的包体问题）

**核算口径**：`MP3 CBR 64 kbps 单声道 = 8.0 KB/s`（64000 bit/s ÷ 8）；每文件另计 **+0.5 KB 开销**（编码器延迟/填充；建议剥离 ID3 标签）。

**A. SFX（24 个文件）**

| 分组 | 文件 | 单条时长 | 条数 | 小计时长 |
|---|---|---|---|---|
| Boss 演出 | land / roar / surrender / taunt | 0.60 / 1.00 / 0.80 / 0.60 | 4 | 3.00 s |
| 结算 | result_lose / result_win | 1.20 / 2.00 | 2 | 3.20 s |
| 武器 | gun_shoot ×3 / gun_empty / gun_reload | 0.10×3 / 0.06 / 0.70 | 5 | 1.06 s |
| 命中 | hit_light ×4 / hit_heavy ×3 / hit_shieldbreak | 0.14×4 / 0.25×3 / 0.40 | 8 | 1.71 s |
| UI/提示 | ui_lock / ui_crosshair / ui_click / shieldup / combo_up | 0.20 / 0.15 / 0.05 / 0.40 / 0.30 | 5 | 1.10 s |
| **SFX 合计** | | | **24** | **10.07 s** |

```
SFX 数据量 = 10.07 s × 8.0 KB/s                ≈ 80.6 KB
文件开销   = 24 × 0.5 KB                       ≈ 12.0 KB
→ SFX 小计                                     ≈ 93 KB
```

**B. BGM（2 个文件）**

```
每段 16.0 s × 8.0 KB/s = 128 KB；两段 = 256 KB
→ BGM 小计                                     = 256 KB
```

**C. 音频总计**

```
93 KB (SFX) + 256 KB (BGM) = 349 KB ≈ 0.34 MB
```

**D. 与 2MB 红线对照**

| 组成 | 估算 | 依据 |
|---|---|---|
| 贴图 + 序列帧（美术/动画实际产出） | ≈ 1.07 MB | **实测**（含 53 序列帧文件，远超早期"贴图 ≈0.13 MB"的粗估） |
| **音频（本方案）** | **≈ 349 KB** | 上文（MP3 CBR 64 kbps 单声道逐条核算） |
| 工程/脚本/场景/元数据 | ≈ 20 KB | 保守 |
| **总包体（实测）** | **≈ 1.45 MB** | team-lead 实测反馈 |
| **红线** | **2048 KB（2 MB）** | 硬约束 |
| **余量** | **≈ 550 KB（占总容量 27%）** | ✅ **相容** |

> **⚠️ 口径更正（v1.2）**：本节 v1.0 版曾按柯桥良早期"贴图 ≈0.13 MB"估算总包体 ≈0.49 MB —— **该值偏低了约 3 倍**，原因是当初未计入 53 个序列帧文件的独立体积。**以 team-lead 的实测 1.45 MB 为准**（剩余余量约 550 KB）。
> **音频占比的正确表述**：音频 349 KB = **实测总包体 1.45 MB 的 ≈24%**（不是 70%）。音频**仍有充足余量，无需为体积让步**；但余量已从"4.1×"收窄到"550 KB"。→ 因此**砍序表（5.3）从"仅预案"升级为"真实待用"**，尤其第 1–2 条（BGM 降码率 / 缩短）随时可用。
> **诚实声明**：音频 349 KB 基于**设计规格时长**。若走 AI 生成（第 8 节），输出时长不受"约 x s"精确控制 → **拿到真实文件后必须实测并复核此数**。这是本核算唯一的不确定项。
> 另：写更低的采样率（22.05 kHz）对 MP3 体积**无影响**（体积由码率决定，不由采样率决定），所以"降采样率省体积"在本平台是无效手段 —— 要省只能**降码率或砍时长/砍文件**。

### 5.3 若超预算，先砍哪条（砍序）

> **结论（v1.2 更新）**：按 **team-lead 实测总包体 1.45 MB**（余量 550 KB），**音频当前不需要砍**，BGM 已裁决保留。

### 6.3 三条可执行的"音频合规闸门"（写进验收，供提审举证）

1. **惊吓闸门（防 jump scare）**：任何音效的 `attack` **不得快于 5 ms**；且**任意 1 s 窗口的响度不得比前一秒的 1 s 平均响度高 12 LU 以上**。→ 这条把"突然的响"这个惊吓核心机制从工程上掐掉。
2. **低频闸门（防恐怖/嗡鸣）**：**禁止 <60 Hz 的持续（>200 ms）能量**；全包最低音为 `sfx_boss_land` 的 55 Hz 瞬时下扫（≤120 ms）。→ 兼顾合规与"手机小喇叭放不出"的物理事实。
3. **零人声闸门**：全包 **不含任何人类语音/人声采样**（含 TTS、含"哈哈"式真人笑声）。拟人声一律用方波合成。→ 用频谱听审 + 文件来源清单双重确认（验收项 15/16）。

## 七、音频与特效的时序对齐（毫秒级）

### 7.1 为什么射击游戏的音频延迟是"发飘"的根源

射击的"手感"= 输入 → 视觉 → 听觉三者在 **~50 ms** 内闭环。**音频若晚于视觉**，玩家感觉"枪是空的 / 声音飘在后面"；两者同时延迟则会觉得"整个游戏卡"，但不会"飘"。
→ **因此对齐的第一原则不是"让音频绝对早"，而是"让音频和视觉落在同一帧"。**
行业经验值（移动射击类）：**touch → 出声 ≤50 ms 为"不发飘"上限，理想 ≤35 ms。**

### 7.2 命中事件的毫秒对齐表

`T0` 定义为**脚本内执行"命中判定成立"的那一帧**（不是触摸帧，不是动画事件帧）。

| 相对 T0 | 事件 | 所属层 | 容差 |
|---|---|---|---|
| −16.7 ~ 0 ms | 触摸/开火输入被处理 | L3 武器层 | ≤1 帧 |
| **0 ms** | **命中判定成立**（`worldToViewportPoint` 视口容差窗判定，见 `tech-spec §2.7`） | 脚本 | 基准 |
| 0 ms | combo 计数 +1、伤害结算、血条数值更新 | L5 HUD | 0 |
| **0 ms** | **命中音 `play()`（同帧调用，不得延后）** | L4 | **0 ~ +33 ms（≤1 帧，绝不可更晚）** |
| 0 ms | `hitstop` 开始（**0–83 ms**，按事件分级；**只暂停 Boss 动画 provider** —— 音频**播放**与 L4 照常跑，但**动画序列音的派发时钟同步冻结**，见下表注） | L4 | ≤1 帧 |
| 0 ms | Boss 闪白（材质提亮） | L2 | ≤1 帧 |
| 0 ms | 伤害数字弹出 | L4 | ≤1 帧 |
| 0 ms | 像素星粒子 emit | L4 | ≤1 帧 |
| 0 ms | **屏幕震动（ScreenShake）**启动（作用点 = `ContentRoot`，**全局单点**；本项目**不动任何相机**） | 全局（`ContentRoot`，**不占层**） | ≤1 帧 |
| 0 ~ +16.7 ms | 开火音 `play()`（**若命中与开火同帧，先调开火音、再调命中音**，保证包络先后正确） | L3 | ≤1 帧 |
| +50 ~ +83 ms | `hitstop` 结束（**已统一定稿**：普通命中 50 / 暴击·破盾核心 67 / 破盾成功 83 / 击杀 0 ms —— 上限 83 ms） | L4 | — |
| +70 ~ +120 ms | Boss 抖动结束，回 IDLE | L2 | ≤2 帧 |
| 0 ~ +0.4 s | `ui_lock` 去抖窗口（命中态在容差窗边缘反复进出只响一次） | L3 | — |
| 0 ~ +0.25 s | `gun_empty` 去抖窗口 | L5 | — |

> **⚠️ hitstop 对音频的两种作用必须分清（v1.3）**：
> - **音频"播放"照常跑**（不受 hitstop 影响，不降速、不变调）→ 已入队的声音正常播完（见 7.3 要求 1 的 ✅ 说明）。
> - **动画序列音的"派发时钟"随 Boss 动画同步冻结**（§3.4 纪律 1）→ `sfx_boss_land`/`sfx_boss_shieldup`/`sfx_result_win` 等**序列点**在 hitstop 内不会被提前或推迟，永远钉在视觉帧上。
> - 本表所有 0 ms 事件都是**判定驱动**（命中音/闪白/粒子/震屏），故全部**照常**。

### 7.3 三条硬性实现要求（否则时序一定会崩）

1. **命中音必须在 `hitstop` 开始的同一帧入队。**
   理由：`hitstop` 会暂停 Boss 视觉最长 83 ms。若音效晚于它，玩家的主观顺序会变成"画面停住了 → 然后才听到啪"，就是从"打到"变成"打到之后有事发生"，打击感立刻掉档。
   ✅ **已核实无额外风险**：引擎无全局 timeScale（`timeScale` 属 `Physics3D`），hitstop 走 `AnimatedTextureProvider.pause()`，**只暂停 Boss provider，不动全局时间** → **音频与 L4 特效在 hitstop 期间照常跑**，音效不会被拖慢或变调。
2. **不得把音效挂在动画事件（AnimationEvent）上。**
   理由：动画事件的时序可能比判定帧晚 1–2 帧 → 音频延迟 +33~66 ms → 直接"发飘"。
   → **两类触发源必须分清（v1.3 细化，与 `animation-spec §5.5` 对齐）**：
     - **判定/输入驱动音**（`sfx_hit_*` / `sfx_gun_shoot_*` / `sfx_gun_empty` / `sfx_combo_up` / `sfx_ui_*`）：由脚本在**判定帧或输入帧**直接触发，**与动画时钟无关** → **不受 hitstop 影响**。
     - **动画序列驱动音**（`sfx_boss_land` / `sfx_boss_shieldup` / `sfx_gun_reload` / `sfx_result_win` 序列点）：由 **`BossAnimPlayer` 的播放时钟回调**驱动 —— 我方只登记**播放时刻(ms)**（见 §3.4），BossAnimPlayer 按**累计非暂停播放时长**跨过该毫秒时回调 `play()`（**hitstop 期间冻结** → 与视觉帧同帧）。**这是脚本侧调度，不是 AnimationEvent。**
   → animation 侧 `f#★` 对齐点仍是**给程序的对齐参考**：程序据此换算成上述两类触发源之一，**一律不得监听 AnimationEvent**。
3. **命中音时长必须 ≥ `hitstop` 上限**，让声音"扛过"停顿。
   本方案已满足：轻击 **140 ms**、重击 **250 ms**（均 > 上限 **83 ms**），余量分别 1.7× / 3.0×。

> **✅ 跨文档口径已统一（team-lead 裁决，以我的建议为基准）**：`hitstop` 时长定稿为 ——
> **普通命中 50 ms / 暴击·破盾核心 67 ms / 破盾成功 83 ms / 击杀 0 ms（上限 83 ms）**。
> - 「普通命中 50」正是我推荐的整帧值（= 3 逻辑帧 @60fps，`AnimatedTextureProvider.pause()` 恢复点落在整帧；原 `vfx-spec` 的 40 ms ≈ 2.4 帧会落在帧中间）。
> - `vfx-spec` v1.2 已是此值；`implement-plan` 由 40/60/70 改为 50/67/83。
> **对音频无影响**（我原判断成立）：命中音 140/250 ms 均 > 83 ms，仍满足"声音扛过停顿"。本次仅把文档里的 70 ms 上限同步为 83 ms，**无资产变更**。

### 7.4 平台限制下如何保证（含降级方案）

**限制**：平台**没有引擎级音频调度 API**（无"在 X 秒后播"、无"与动画自动同步"）。音频**只在脚本调用 `play()` 的那一帧出声**。
→ **v1.3 补充**：脚本侧**可以自建**这一层调度 —— 动画序列音用 `BossAnimPlayer` 的**播放时钟回调**（见 §3.4），判定音用判定帧直调。**可用的是"脚本计时器"，缺的是"引擎原生同步"**，本方案的触发模型正是建立在前者之上。

**保证路径**：
1. **同帧触发**（上面的要求 1–3）→ 把音频钉在判定帧。
2. **预热播放（消除首触发延迟）**：`onInit` 完成后，把所有 SFX 槽以 `volume = 0` 各 `play()` 一次，随即恢复音量。
   理由：首次 `play()` 一个未解码的资产可能有额外的解码/IO 延迟；预热后每次触发都是"已就绪"状态。**这是本方案对"端到端延迟"最有效的一招。**
3. **`play()` alone**：绝不 `stop()`-then-`play()`（平台已核实同帧会被塌陷成"什么都不做"）。
4. **开火音提前**：开火音不依赖命中判定，**在触摸 `Began` 帧就直接触发**，比命中音更早 → 让"扣扳机"的感觉最即时。**按住期间由 250ms 闸门节流，每发触发一条**（闸门见 `game-design §五`，原 220ms 口径已否决）。

**端到端延迟预算（含降级）**：

| 环节 | 典型值 | 最坏值 |
|---|---|---|
| 触摸 `Began` → 脚本处理（**含命中判定与同帧 `play()` 调用**，同一个 update tick 内完成） | 0–33 ms（1 帧 @30fps） | 33 ms |
| MP3 编码器固有延迟 | 13–25 ms（所有文件一致） | 25 ms |
| 设备音频输出链路（Android 各机型） | 15–40 ms | 40 ms |
| **合计（串行可加）** | **≈ 28–65 ms** | **≈ 98 ms** = 33 + 25 + 40 |

> **⚠️ v1.5 算式澄清（qa-lead 核出，实为我原稿的错）**：原表把"命中判定 → `play()`"**单列一行、最坏写 33 ms**，导致 **行和 131 ≠ 合计 98** —— 自相矛盾。
> **根因**：那一行的 `33 ms` 是**容差（≤1 帧）**，**不是可加的串行增量**。命中判定与 `play()` **必须在同一个 tick 内完成**（§7.3 硬要求 1），其帧量化**已计入上一行**；再单列相加 = **把同一帧量化计了两次**。故本行**合并进第一行**，判定→`play()` 的串行增量 = **0**，合计 = **33 + 25 + 40 = 98 ms**。
> **容差劣化上限（如实给出，供 QA 记录）**：若实现**违反**"同帧"硬要求、判定音**晚 1 帧**，则最坏劣化为 **33 + 33 + 25 + 40 = 131 ms**。这是**不达标实现的后果**，**不是合格预算上限**；§9 验收项 11（≤1 帧）正是这条容差的边界。
> → **对 QA 的 O-03 / D-02 建议记法**：**"最坏 ≈98 ms（合格实现的串行上限）／劣化上限 ≈131 ms（判定音延迟 1 帧）"**。两者**都** > "不发飘"上限 50 ms，故无论取哪个，**端到端延迟都是音频侧头号风险**。

→ **最坏值 98 ms 已超出"不发飘"上限**。**这是本项目音频侧的头号风险**，必须真机实测（第 10 节待实测 ①）。
→ **降级预案（按顺序启用）**：
  1. 开火音改为**触摸帧直接触发**（不等判定）—— 已包含在主方案；
  2. **预热播放**消除首触发解码延迟 —— 已包含在主方案；
  3. 若仍超标：把命中音改为**在"开火帧"预测触发**（因为射速 4 发/秒、命中率高，可把"命中音"与"开火音"合并为同帧触发的双音层）—— 代价是脱靶时也会响命中音，需音色上区分"打中"与"落空"；
  4. 仍超标 → **上报 team-lead 作为阻塞项**，而不是悄悄交付一个"手飘"的版本。

## 八、音频侧 AI 生成可行性

**本机可用工具（依据 `skills/assets/AudioGeneration/SKILL.md`）**：`generate_audio(name, prompt)` 生成**单段**音频并直接导入工程（产物为 mp3）；多段走 `generate_assets_batch` / `AssetBatchGeneration`。

### 8.1 逐类判断

| 目标 | AI 能否达标 | 判断与做法 |
|---|---|---|
| **单个短促 chiptune 音效**（hit / shoot / click / land / roar） | ✅ **能，达"可用"水平** | 做法：按 SKILL 规定的 prompt 结构 `即刻响起 + 时长词 + 带声学质感的声源（1–2 修饰, 约xs）`。例：`即刻响起一声短促的像素电子击中声（清脆, 穿透力强, 约0.2s）`。**生成 3–5 条挑 1 条**。风险见 8.2 |
| **音高阶梯（4 档 +2 半音）** | ❌ **不能，不要靠 AI** | 生成式模型无法保证"同音色 + 精确 +2/+4/+6 半音"，4 条分别生成会得到 4 种不同音色，叠起来像 4 个不同乐器。**正确做法：AI 只出基准档（0 半音），其余 3 档用离线变调从基准档派生**（DAW Change Pitch 或 `ffmpeg -af asetrate=<r>:atempo=<1/r>`）。→ **这是本方案"音高阶梯"的唯一落地路径，必须写进音频预处理流程** |
| **BGM 循环点无缝** | ❌ **不能，AI 不可控** | 生成式产物起止点是黑盒，"第 8 小节末 = 第 1 小节头"无法保证。三选一：<br>**(a) 推荐**：AI 生成 ≥15 s 的 chiptune loop → **人工在 DAW 里按小节裁成 8 小节（16 s）并把尾部对齐头部**（成本 30–60 min/段）<br>**(b) 最可控**：用 tracker / 合成脚本**程序化生成**（chiptune 天生适合，循环点样本级精确、零版权风险，但工具链成本高）<br>**(c) 兜底**：接受非严格无缝，靠"尾拍过门 + 首拍强起"掩盖 |
| **精确时长** | ⚠️ **部分可控** | prompt 里可写 `约xs`，但输出会有偏差。**生成后必须实测时长**（`AudioComponent.duration` 可读，或读文件），不符则重生成或离线裁切 |
| **统一响度 / 留 headroom** | ❌ **不可控** | AI 输出通常接近 0 dBFS（归一化），与本方案"资产要留 headroom"的策略**冲突** → **必须离线统一降增益**到 2.3 表的目标峰值 |
| **音色跨文件一致性** | ⚠️ **需人工横比** | 同一批 prompt 生成的不同音效音色可能差很远（land 与 hit 材质不统一）。**挑选时要横向对比，并统一"音色方向词"** |

### 8.2 风险（必须处理，不能忽略）

1. **版权 / 授权归属（最高优先）**
   - **优先只用平台内置 `generate_audio`** —— 属平台能力，授权链路最清晰，提审时最容易说明。
   - **禁止**在未确认条款的情况下使用外部第三方 AI 音频生成器（其商用授权、平台内使用授权均不明确）。
   - **所有音频的实际来源必须登记 `assets/SOURCES.md`**（平台内置 / 人工制作 / 离线处理步骤），供提审版权核查。**音频侧的合规凭证就是这份文件。**
2. **旋律撞车**：AI 可能"撞"到训练数据里的已知旋律（**chiptune 尤其容易撞老游戏主题**）。→ **必须人工听审**，任何疑似与已知作品相似的片段一律重生成。
3. **时长不可控 → 体积核算要复核**：第 5.2 节的核算基于设计规格时长；AI 输出的真实时长会偏 → **拿到真实文件后必须实测并复核一次体积**。
4. **响度归一化 → 破坏 headroom** 且可能**破坏"命中音与 BGM 的 ≥6 dB 关系"** → 必须逐条离线处理到目标峰值，不能直接用 AI 输出。
5. **循环不无缝**（见上）。
6. **一致性**：需统一音色方向词 + 横比挑选。

### 8.3 结论（一句话）

**AI 可以承担 60–70% 的"基底音色"产出，但不能承担"① 精确音高阶梯 ② BGM 循环点 ③ 响度归一 / headroom"这三件确定性工作。**
→ 交付流程必须是：**`AI 出基底` → `离线确定性处理（变调 / 裁切循环点 / 统一增益）` → `写回工程` → `真机听审` → `SOURCES.md 留痕`**。
→ 对最关键的**命中音**，我建议额外保留一条"程序化合成"备选（用脚本合成方波/噪声 PCM 再转 MP3）——它能给出**样本级精确的音高阶梯与时长**，是唯一能保证第 3.2 节参数表被 100% 实现的路径。这条交给主程序评估工具成本。

## 九、音频验收标准（可核对）

| # | 验收项 | 通过标准（可判定） |
|---|---|---|
| 1 | **同帧并发** | 任意一帧内**新启动**的音效 ≤ **2**（第 3 个应被丢弃且不发声） |
| 2 | **全局并发** | 任意时刻同时播放的 SFX 组件数 ≤ **4** |
| 3 | **无削波 / 无音爆** | 以最坏叠加（轻击任一档 + 重击任一档 + 开火 + 破盾）离线合成检查：混音峰值 **≤ −1.0 dBFS**；真机整局录屏听检**无噼啪、无爆音** |
| 4 | **音高上限** | 命中音音高不越过基准的 **1.414×（轻）/ 1.260×（重）**；无"啸叫/尖叫"听感 |
| 5 | **无重复疲劳** | 任一 2 s 窗口内，同一（文件 + 音高档）组合**不连续出现 ≥3 次** |
| 6 | **失败音不吓人** | `sfx_result_lose` 无恐怖元素（无 <80 Hz 持续低频、无 >1.5 s 长混响、无 jump-scare、无惨叫）；**盲测 5 人，"是否被吓到"100% 未受惊** |
| 7 | **咆哮"凶但不恐怖"** | `sfx_boss_roar` 盲测被描述为"凶/搞笑/卡通"而非"恐怖/害怕"，**≥4/5 人** |
| 8 | **总音频体积** | ≤ **360 KB**（24 SFX + 2 BGM）；实测 Σ 文件大小 |
| 9 | **总包体** | ≤ **2048 KB**（音频 + 贴图 + 工程） |
| 10 | **无无声/漏配** | 所有 `play()` 点都有"组件为空"兜底日志（`[audio] missing channel=<name>`）；`get_script_logs` **无 missing 记录**（平台 SKILL 明确：音频验收必须靠脚本日志，截图/MP4 无法证明音频） |
| 11 | **起播延迟** | 触摸开火 → 出声 **≤50 ms**（目标 ≤35 ms）；命中判定 → 出声**同帧为目标（0 ms）**，容差 **≤1 帧（≤33 ms @30fps）**；两者均以真机实测为准 |
| 12 | **BGM 循环无缝** | 连续播放 ≥60 s（≥3 次循环）**听不出接缝**；常态↔暴怒切换瞬间**无咔嗒** |
| 13 | **静音开关** | 全局静音 / "关闭音乐"（**遍历组件设 `volume=0`**，非 `mute`）生效，**0.2 s 内**可听出静音；**恢复后音量回到原值**（不被衰减表残留污染） |
| 14 | **BGM 不抢戏** | 模拟"用户音乐同时播放"场景下仍能清晰辨识命中音；**命中音比 BGM 高 ≥6 dB** |
| 15 | **零人声** | 全包内**不含任何人声采样（含 TTS、真人笑声）**；用频谱 + 听审确认 |
| 16 | **版权留痕完整** | `assets/SOURCES.md` 每条音频都有来源登记（AI 平台/prompt/人工处理步骤），**无空项** |
| 17 | **命名合规** | 全部文件满足 `sfx_<类别>_<名称>[_变体].mp3` / `bgm_p<阶段>_<情绪>.mp3`，全小写 + 下划线，无中文/空格 |
| 18 | **格式合规** | 全部为 **.mp3**，44.1 kHz，单声道，CBR 64 kbps（BGM 可 48 kbps）；无 .wav / .ogg 混入 |
| 19 | **状态重置** | 开拍/录制开始触发 RESET 时，所有音频组件被 `stop()`，combo 与槽位下标归零 |
| 20 | **★ 动画序列音挂播放时钟（v1.3 新增）** | 在 Boss 动画序列内**注入一次 hitstop（如 50 ms 破盾）**，`get_script_logs` 里 `sfx_boss_shieldup`(100) / `sfx_boss_land`(333) / `sfx_result_win`(950) 的**播放时刻相对动画 played-time 的偏差 ≤1 帧**，且**不随 hitstop 漂移**（对比：若按墙钟实现，`flag_land` 会漂 +50 ms） |

## 十、给主程序 / 引擎的需求清单 + 待实测项 + 风险

### 10.1 音频播放逻辑需求（可直接实现）

1. **对象架构**：按 3.1 表建 **26 个音频场景对象**（2 BGM + 24 SFX），**统一挂到常驻容器 `AudioRoot`**（Empty Object）。**1 资产 = 1 对象**（平台无运行时换绑，这是唯一做法）。
   ★ **`AudioRoot` 必须常驻 `enabled`，不得挂在任何状态页 / 视觉父节点下** —— 父节点 `setEnabledInHierarchy(false)` 会级联禁用音频，**切页/开拍/结算时音频会一起消失**。详见 3.1.1，与柯桥良 `node-plan.md` §1.3 一致。
2. **总线设置**：BGM 两个对象 `audioType=BGM`；其余 24 个 `audioType=AUDIO_EFFECT`（这是平台唯一的"混音分组"）。
3. **播放模式**：BGM 用 `playMode=INFINITE`（★ 不要用 `loopCount=-1`，官方明确禁止）；SFX 用 `playMode=ONCE`。
4. **`autoPlay=false`**（全部），由脚本在 `onInit` 之后统一 `play()`，避免早于首帧。
5. **预热播放**：`onInit` 后一次性把所有 SFX 槽以 `volume=0` 各 `play()` 一次，随后恢复音量（消除首触发解码延迟）。
6. **快速重触发**：SFX 一律 `play()` alone —— **禁止同帧 `stop()` + `play()`**（平台已核实会被引擎塌陷成"什么都不做"，音就没了）。
7. **槽位轮转**：轻击池 4 槽 / 重击池 3 槽 / 开火池 3 槽，按 3.2 机制 2 的公式派发。
8. **并发衰减表**：脚本维护"播放中的 SFX 槽"计数，按 4.1 的系数表在启动前设 `volume`（**软件限幅，替代压缩器，不可省**）。
9. **优先级丢弃**：按 3.2 机制 3 的规则执行（不打断、只不启动）。
10. **BGM 切换**：阶段 2 触发时，**先 `stop()` 常态段 → 下一帧 `play()` 暴怒段**（必须分帧）；切点量化到最近拍线。
11. **BGM 闪避**：`shieldup` / `shieldbreak` / `roar` / 终局事件时，BGM `volume` 30 → 20，150 ms 后线性回升（只在这些重事件闪避，命中轻击不闪避）。
12. **状态重置**：RESET 时**显式 `stop()` 所有音频组件**，清零 combo 与槽位下标。
   ★ 注意：因为 `AudioRoot` 常驻 `enabled`（3.1.1），**不能依赖"停用父节点"来重置音频** —— 必须逐个组件 `stop()`，否则上一局的 BGM / 长音效会跨局串声。
13. **日志规范**（★ 平台官方要求）：每个 `play()` 点打 `[audio] action=play channel=<name> voice=<idx>`；组件未绑定打 `[audio] missing channel=<name>`。**音频验收以脚本日志为准**，因为截图/MP4 无法证明音频（这是官方 SKILL 的明确验收规则）。
14. **★ 动画序列音的派发时钟（v1.3 新增，与 `animation-spec §5.5` 对齐）**：`sfx_boss_land` / `sfx_boss_shieldup` / `sfx_gun_reload` / `sfx_result_win` 序列点由 **`BossAnimPlayer` 按累计非暂停播放时长（played-time）回调触发**（跨过登记毫秒时 `play()`），**不用墙钟、不用 AnimationEvent**：
   - ✔ **复用 `BossAnimPlayer` 已定稿的对齐点回调，不新增接口**（team-lead 定案）。`implement-plan` §2.0.2 已有该机制：内部 `actionElapsedMs` + `alignTable` + 派发回调 —— 音频直接订阅它，**同一根时钟**。audio 侧登记：`shield_set 100 / spawn_land 333 / flag_drop 600 / flag_land 950`（见 §3.4）。
   - **hitstop 期间该时钟冻结**（`actionElapsedMs` 累计非暂停时长），音频自动与视觉帧同帧。
